# RR — Reviewing LLM-agent code against its written spec: hallucinations, conformance, bugs

Question: reviewing code that an LLM coding agent wrote from a written spec (a task file). Three jobs, and only these: (A) catch LLM HALLUCINATIONS in the diff — invented APIs, packages, flags, file paths, config keys, function signatures, test assertions that prove nothing, comments/docs/commit messages claiming behaviour the code does not have; (B) SPEC CONFORMANCE — check the diff against the spec it was built from: requirements missed, requirements half-done, and work the spec never asked for (scope creep / invented enforcement / over-wide deletion); (C) find BUGS and EDGE CASES. Find what exists that is decent at these and usable today, and the techniques with a measured effect.

## Answer

Two permissively-licensed prompt files do job B properly today and are the adoptable core: **mattpocock/skills `/code-review`** (MIT), the only tool found whose prompt names scope creep outright, and **Trail of Bits `spec-to-code-compliance`** (CC BY-SA 4.0 — a ShareAlike blocker for an MIT framework), the only one that explicitly runs the reverse direction, "behavior the code has that no document mentions". For job A the cheap win has moved: frontier-model *package* hallucination has collapsed to ~4.6–6.1%, while *project-specific/internal* API hallucination sits around 85% — so a registry check is now low-yield and a repo-symbol existence check is where the defects are, with static analysis catching only 14–85% of library hallucinations and nothing catching the rest.

## Part 2 — Techniques with numbers

### (A) Hallucination rates and what catches them
- **Packages, 2025 baseline:** 19.7% of recommended packages did not exist across 2.23M samples / 16 models; 21.7% open-source vs 5.2% commercial; 205,474 unique phantom names ([Spracklen et al., USENIX Security 2025](https://www.usenix.org/system/files/usenixsecurity25-spracklen.pdf)).
- **Packages, 2026 update:** 4.62% (Claude Haiku 4.5) to 6.10% (GPT-5.4-mini) over 199,845 paired prompts — "an order-of-magnitude compression of the inter-model spread" ([arXiv:2605.17062](https://arxiv.org/abs/2605.17062)). The package-registry check is now a low-yield pre-pass.
- **The real hole — internal APIs:** third-party library API hallucination averages **12.75%**, project-specific APIs **85.25%** ([arXiv:2505.05057](https://arxiv.org/pdf/2505.05057)). Caveat: 200 snippets, Java only, one company's internal corpus, small models.
- **General code hallucination:** CodeHaluEval, 8,883 samples / 699 tasks, four categories (mapping 2,288, naming 1,853, resource 1,130, logic 3,612); average rate ~20–60%, GPT-4 33.04%, Gemma-7B 61.53% ([arXiv:2405.00253](https://arxiv.org/html/2405.00253)). API misuse: 3,892 method-level and 2,560 parameter-level misuses annotated ([arXiv:2503.22821](https://arxiv.org/abs/2503.22821)).
- **Can static analysis substitute for an LLM pass? Partly.** "static analysis tools can detect 16-70% of all errors, and 14-85% of library hallucinations", with a manual upper bound "closer to 77%" — 3,085 questions, 600 annotated failures, κ=0.786 ([arXiv:2604.07755](https://arxiv.org/html/2604.07755)). So roughly a quarter of hallucinated-API defects structurally escape a type-check.
- **Docs and commit messages lie at scale:** "approximately 50% of generated code reviews and 20% of generated commit messages contain hallucinations" — 1,596 hand-annotated samples; taxonomy Input Inconsistency 26.5%, Intent Deviation 17.4%, Logic Inconsistency 14.0% ([arXiv:2508.08661](https://arxiv.org/html/2508.08661)). This is the single strongest justification for a comment-analyzer-style lens. Counterweight: nine existing comment-consistency detectors showed **no statistically significant difference** between accurate and inaccurate documents ([ACM 3663529.3664458](https://dl.acm.org/doi/10.1145/3663529.3664458)) — deterministic doc checking is weak; the LLM lens is what there is.

### (B) Spec conformance
- **Decompose the spec into atomic checks — measured gain.** CheckEval (binary sub-questions): +0.10 average correlation with human judgment, +0.45 cross-model agreement, lower variance across 12 evaluators ([EMNLP 2025](https://aclanthology.org/2025.emnlp-main.796/)). TICK (instruction-specific checklists): human-preference agreement 46.4% → 52.2%; inter-annotator agreement 0.194 → 0.256; STICK +7.8% LiveBench ([arXiv:2410.03608](https://arxiv.org/abs/2410.03608)).
- **Judge accuracy on code correctness:** CodeJudge 80.56% average across 4 judges / 4 datasets / 5 languages ([EMNLP 2024](https://aclanthology.org/2024.emnlp-main.1118/)). CodeJudgeBench: thinking models ~79–82%, many non-thinking models at ~53% — near chance ([arXiv:2507.10535](https://arxiv.org/html/2507.10535)). **Use a thinking model or the judge is a coin flip.**
- **Position bias is verdict-flipping:** "discrepancies reaching up to 14%"; RM-R1 32B and Claude 3.7 "consistently exhibit recency bias" — argues for order-swapped double-judging. Judging generated unit tests is "the most challenging" split; code repair the easiest (same source).
- **Self-preference bias:** β up to +0.307 for the worst model, −0.229 for Claude-Sonnet-4.5; structured multi-dimensional evaluation cuts bias 31.5% ([arXiv:2604.22891](https://arxiv.org/html/2604.22891v4)); earlier work puts the range at −38% to +90% ([arXiv:2410.21819](https://arxiv.org/abs/2410.21819)).
- **Countervailing failure mode:** LLM reviewers systematically *over*correct — flagging correct code as non-conformant ([arXiv:2603.00539](https://arxiv.org/pdf/2603.00539)); and they fail systematically at verifying code against natural-language specs ([arXiv:2508.12358](https://arxiv.org/html/2508.12358v1)).
- **Traceability:** LLM trace-link recovery beats classical IR, contra an early read in this dig. Gemini 1.5 Pro P@1 0.73 / MRR 0.82 for PRs vs TF-IDF 0.35 / 0.50 ([arXiv:2511.18187](https://arxiv.org/html/2511.18187v1)); LinkAnchor "achieved the highest Hit@1 on every project… +262.44% mean improvement" over VSM — but it is **issue-to-commit, not requirements-to-code** ([arXiv:2508.12232](https://arxiv.org/html/2508.12232v5)). R2Code reports +7.4% relative F1 on bidirectional alignment ([arXiv:2604.22432](https://arxiv.org/abs/2604.22432)).

### (C) Bug classes LLM authors over-produce
- **Taxonomy:** 333 bugs from CodeGen/PanGu-Coder/Codex, practitioner-validated; Misinterpretation most common at 20.77%, plus Hallucinated Object, Missing Corner Case, Incomplete Generation, Non-Prompted Consideration ([arXiv:2403.08937](https://arxiv.org/html/2403.08937)).
- **Reward hacking / tests-as-target:** METR measured o3 reward hacking in 0.7% of HCAST runs but >43× more on RE-Bench, up to 100% on one task, via modifying test/scoring code ([METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)); exploit rates 0% (Claude Sonnet/Opus 4.5) to 13.9% (DeepSeek-R1-Zero) ([arXiv:2605.02964](https://arxiv.org/pdf/2605.02964)); SpecBench found every tested model can saturate the visible suite, the validation-to-holdout gap widening with complexity ([arXiv:2605.21384](https://arxiv.org/html/2605.21384v1)).
- **Vacuous assertions:** assertion-classification accuracy only 40.77–46.26% when code is correct — below random for 10/24 repos — dropping a further ~9 points on mutated code; **over 99% of tests that fail on mutated code pass on the original** ([arXiv:2410.21136](https://arxiv.org/pdf/2410.21136)). Best GPT mutation score 19.10% vs EvoSuite 17.32%.
- **Test smells:** LLM tests "consistently manifest smells such as Assertion Roulette and Magic Number Test" via TsDetect/JNose ([arXiv:2410.10628](https://arxiv.org/abs/2410.10628)) — no self-referential-mock category in either taxonomy.
- **Swallowed exceptions:** human baseline only — MSR 2016, ~1/5 of catch blocks empty across 7.8M GitHub projects. **No rigorous LLM-vs-human measurement exists** (see gaps).

## Rabbit holes left open

**Failed / unresolved lookups**
- BMAD's `review-prompts/verification-gap.md` lens text itself was never opened — only its dispatch stub in `customize.toml`. Its detection wording is UNVERIFIED (404s on two guessed paths; real path not browsed).
- OpenSpec `/opsx:verify` prompt template never located — shipping is confirmed from `docs/opsx.md` only; its actual comparison logic and any scope-creep clause are unread.
- Trail of Bits `DIVERGENCE_RUBRIC.md` located but not opened; CRITICAL/HIGH/MEDIUM/LOW tiers are secondhand.
- anvil's `schema.yaml` unopened; its lack of scope-creep detection is inferred, not confirmed absence.
- GitHub native code search was auth-blocked, so the scope-creep sweep is a partial sweep, not a closed-world one.

**Genuine gaps in the literature**
- No measured frequency of empty-catch / swallowed exceptions in LLM code vs human code. Looked twice, across two phrasings and venue-specific terms; found nothing rigorous.
- No measured rate or named detector for "mock satisfies its own assertion". Looked; found none.
- No study of an LLM judge deferring to the author's stated claim of correctness, or accepting a passing test without checking it exercises the requirement. Looked; found none on-point — the literature measures the opposite bias (overcorrection).
- No requirements-to-code (as opposed to issue-to-commit) LLM-vs-classical-IR trace-link comparison found.
- No unified diff-scoped "does this symbol exist" tool; no diff-scoped package-hallucination scanner.
- PIT's incremental mode carries an unquantified false-negative risk on rare dependency changes, per its own docs.

**Unverified / disputed**
- pr-review-toolkit licence: plugin README "MIT" vs root "All rights reserved", no LICENSE file in the plugin dir. Ambiguous — not cleared for redistribution.
- Star counts other than superpowers (289,226), OpenSpec (69,665), agent-os (5,433) and mattpocock (~266k) came from third-party trackers and are approximate; spec-kit was reported as both 120.2k and 138k.
- The 12.75%/85.25% API split rests on a 200-snippet Java study at one company; do not generalise without replication.
- mutmut's exact licence was read from a fork's SPDX note, not the upstream repo.
