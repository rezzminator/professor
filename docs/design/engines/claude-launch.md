# Claude interactive launch

Every Claude Code chat pfm starts in a tmux pane is described by one table, the launch registry `claudelaunch.Knobs` (`pfm/internal/claudelaunch/knobs.go`), and rendered by one function, `claudelaunch.Render` (`pfm/internal/claudelaunch/render.go`). Every flag, environment variable and settings key pfm hands Claude at launch is a row there; nothing else in pfm spells one. This file holds the registry's shape, where each value comes from, how it reaches Claude, the code paths that launch a chat, the managed `claude` launcher, and the doctor audit. Headless runs are in [claude-headless.md](claude-headless.md); files pfm places on disk are in [claude-config-dir.md](claude-config-dir.md).

## Decisions

- **One table owns every launch value.** To change what a Claude chat starts with, edit a row in `claudelaunch.Knobs` or a key in `pfm.config.json` — nowhere else. A test (`TestNoLaunchLiteralOutsideRegistry`) fails when any Go file outside `pfm/internal/claudelaunch/` emits a Claude launch flag or sets or unsets a `CLAUDE_CODE_*` / `ANTHROPIC_*` / `ENABLE_PROMPT_CACHING_*` / `FORCE_PROMPT_CACHING_*` variable for a Claude process; code that only reads a variable Claude itself sets (`CLAUDE_CODE_SESSION_ID`, `CLAUDE_CONFIG_DIR`) is not an emitter.
- **One `--settings` payload carries almost everything.** Environment variables ride its `env` block and every other setting rides its own key. `--settings` outranks the project and account settings files, and its `env` overwrites the shell's value, so a launch value cannot be shadowed by a project file or an exported variable.
- **Three things stay outside it.** `CLAUDE_CONFIG_DIR` is process environment because it chooses where Claude reads settings from; the unset list is `env -u` because a settings `env` block can set a variable but not remove one; `--system-prompt-file`, `--mcp-config` and the session verbs (`--session-id`, `--resume`, `--fork-session`, `--name`) are flags because no settings key replaces them; the autonomy pair, `--model` and `--effort` stay flags because a flag outranks its settings key.
- **Defaults come only from `pfm.config.json`.** A per-launch choice changes one launch; no door carries a default of its own ([pfm-home.md](pfm-home.md#decisions)).
- **Helper calls run on Haiku, always.** Claude Code's helper calls (the page summary behind WebFetch, session and tool-use-summary titles, a hook's prompt, and the WebSearch call while its server flag `tengu_plum_vx3` is true) take their model from one resolver that reads `ANTHROPIC_SMALL_FAST_MODEL` first; unset, a gateway host runs them on the main chat's model. `helperModel` carries the variable through every door, defaulting to the full id `claude-haiku-5-5`, and the hygiene unset stays so an exported value never reaches a launch the settings do not carry. `ANTHROPIC_DEFAULT_HAIKU_MODEL` is not used: it redefines the `haiku` alias, so it would move Haiku sub-agents too. A caller's own `--settings` on a headless run replaces pfm's whole payload, this key included.
- **Remote Control rides a flag, not a settings key.** Claude documents `remoteControlAtStartup` only for the user and managed settings scopes, and whether the `--settings` payload honors it is unverified, so pfm uses the documented `--remote-control` CLI flag (a registered `WireFlag`) rather than relying on that behavior. pfm does not bypass Claude's own eligibility rules and leaves the host gateway unchanged; [Remote control](#remote-control) holds the placement and the doctor audit.
- **Agent teams are off, always.** `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=0` is a constant row, not a config key, and no project file needs to carry it.
- **The plugin env rides the launch.** `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1` and the auto-compact window are launch values, never account `settings.json` keys; keys an older install wrote there stay, outranked by `--settings`. The variable does not override a cached `cachedGrowthBookFeatures.tengu_plugin_hooks_modules: false` in `{configDir}/.claude.json`, which a gateway host never refreshes; `pfm doctor`'s `function-hook-modules` row reports it.

## How Claude layers its settings

Claude Code's own precedence, highest first: managed settings (`/etc/claude-code/` on Linux, `/Library/Application Support/ClaudeCode/` on macOS) → command line (`--settings`, flags) → `.claude/settings.local.json` → `.claude/settings.json` → the account's `settings.json`. A settings `env` entry overwrites the same variable exported in the shell. A flag beats its settings key (`--model` over `model`). Hooks merge across every layer rather than replacing each other.

pfm supplies launch values at two layers: managed settings for retention through every launch path, and the command line for the other launch values. Claude's plugin commands also write shared user plugin state through the primary account ([claude-config-dir.md](claude-config-dir.md#what-pfm-does-not-write)).

## The registry

```go
// pfm/internal/claudelaunch/knobs.go
type Knob struct {
    Name      string // the config key, or the constant's name
    Wire      Wire   // how it reaches Claude
    Target    string // settings path, env name or flag
    Source    Source // where its value comes from
    Default   any
    Reason    string // one line: why pfm sets it
}
```

`Knobs` lists every row. `Render(Request, pfmconfig.Config) (Launch, error)` resolves each row for one launch and returns `Launch{Unset, Env, Wrapper, Binary, Argv}`. `ClaudeSpawn.ShellCommand` (`pfm/internal/action/claude_spawn.go`) prints it as `env -u … NAME=value … [wrapper] claude <argv>` for a tmux pane; `ClaudeSpawn.Command` execs it directly, the wrapper first when there is one. Neither adds a word of its own. The wrapper is the cost ledger's launcher ([cost-ledger.md](cost-ledger.md#the-launch)); it execs Claude and keeps its pid, so the process a live chat shows is Claude's own.

`--mcp-config` names a per-launch file carrying every `mcp.thirdParty` entry and, when enabled, separate `chat-professor` and `harvester-professor` entries with family-scoped stdio commands: `{type: stdio, command: ~/.local/bin/pfm, args: [mcp, serve, --stdio, --family, chat|harvester]}`. When both families are off, third-party entries still ride the file; with no entries neither file nor flag exists. The payload never sits on argv, where `ps` and `/proc/{pid}/cmdline` would show a third-party `env` value or `Authorization` header to every local user: Render writes `{"mcpServers":{…}}` atomically (scratch file, then rename) to `~/.local/state/pfm/mcp-config/claude-mcp-{random}.json`, mode 0600 in a 0700 directory it refuses when that path is a symlink, and passes the path. Claude reads the file once at startup; each write first prunes the directory's launch files older than seven days. Separately, install inspects existing account `.claude.json` files found through configured accounts, the account roster, ambient config and default paths. It removes exact pfm-owned legacy entries, emits or reconciles enabled family entries, preserves and reports foreign `professor` entries, and leaves absent registry files uncreated. Doctor uses the same inspector and reports account state, foreign entries and unreadable files. Config validation reserves the names `chat-professor` and `harvester-professor` and requires each third-party value to be a JSON object.

The interactive cache handoff stays in process environment beside `CLAUDE_CONFIG_DIR`, outside the settings `env` block. Claude re-applies that block on a settings reload; putting the handoff there would hand the plugin a value it already consumed. The cache-live-control plugin owns subsequent main and sub-agent TTL changes. pfm sets no Claude TTL variable and never `CACHE_LIVE_CONTROL_AGENTS_TTL`; hygiene clears inherited values. Headless keeps the handoff in its settings `env`.

### CheckConfigDir

Before rendering an account launch, `CheckConfigDir` (`pfm/internal/claudelaunch/render.go`) requires that account's directory to exist and never creates it. It classifies the directory with `InspectConfigDir` (`pfm/internal/claudelaunch/configdir.go`). Install's store wiring, the `account-is-store` and `account-entry-real` host checks and doctor's account rows use the same predicate, so a directory launch refuses is one doctor names. A symlinked directory is followed: it launches when its resolved real path is a directory that is neither the store nor inside it, and `CLAUDE_CONFIG_DIR` keeps the literal path. Refusals:

- Missing: `account {id}: {config dir} does not exist — run pfm install`.
- Not a directory: `account {id}: {config dir} is not a real directory — run pfm doctor`.
- Resolves to the store or into it: `account {id}: {config dir} resolves to the Claude store — run pfm doctor`.
- Inspection error, including a dangling link: `account {id}: inspect {config dir}: {cause}`.

`Render` refuses an unknown nonzero account in a configured roster with `account {id} is not in the configured roster`. `CLAUDE_CONFIG_DIR` is set for every configured account, including account 1. An explicit directory-only request receives the same check without the account prefix. Headless account requests also call `CheckConfigDir`.

## Sources

- **config** — `pfm.config.json`'s `claude` block, overridden by the launching account's own `claude` block.
- **machine config** — the `mcp` block's enabled families decide whether `--mcp-config` carries `professor`; `mcp.thirdParty` supplies every other entry. The HTTP port plays no part in pfm's stdio entry.
- **launch → config** — a choice made for this one launch (the picker's cache toggle, `pfm chat new --cache 1h|5m`, `pfm chat reload --cache`); absent a choice, the config value.
- **launch** — only a per-launch choice; unset means the flag is omitted.
- **constant** — fixed in the registry; changing it is a code change.
- **host** — the launch's own environment, else the host's `PATH` (`shell`): `pfm config claude` shows `source=env` for a kept inherited value, `source=PATH` otherwise.
- **account / door** — the chosen account's roster entry, or for `noFlicker` its `settings.json` (`WantsFullscreen`: absent file off; an unreadable one logged and launched without the knob, and shown as its error by `pfm config`); the verb that launched.

No inherited environment variable decides a value but `CLAUDE_CODE_SHELL` (the `shell` row): the unset list clears them first.

## The launch record

pfm remembers what it launched in `pfm.db`, table `launch` — one row per session: `session_id`, `engine`, `account`, `cache1h`, `launched_at`, `updated_at`. It is the source every later reader uses; nothing reads a launch value back out of a running process's environment.

- **One writer.** `fleetdb.RecordLaunch(ctx, values, launch, at)` inserts or updates a row. Every door calls it before exec: a fresh chat with the id it passes as `--session-id`; a resume or reload with the resumed id, updating `account` and `cache1h`; a fork once its new session id resolves.
- **One reader.** `(*fleetdb.Launches).LaunchFor(ctx, sessionID)` returns the row, `ErrNoLaunch` for a session pfm never launched, or the read error.
- **Readers:** the picker's ⚡1h badge; `pfm chat reload`, which carries the chat's account and cache into the respawn unless overridden; the statusline's cache window, keyed by the `session_id` in the statusline payload; account attribution of rows that are not live (compose), which is how a transcript in the shared store is tied to the account it ran on.
- **No record** — a chat pfm did not launch — shows no badge and no medal. **A failed read** renders as an error marker (`⚠`), never as a 5-minute cache or a missing account.
- Spawn-audit does not read the record: it audits what actually runs, through `claudelaunch.Parse` over the live argv with the binary first.

## Sub-agent status line trace

`claude.subagentStatuslineTrace` (machine-wide, default `false`) renders `PFM_SUBAGENT_STATUSLINE_TRACE=1` into the settings `env` block of a Claude launch; the registry source is `EnvSubagentStatuslineTrace` in `pfm/internal/claudelaunch/knobs.go`. Exporting `PFM_SUBAGENT_STATUSLINE_TRACE=1` by hand enables it too. Turn it on by setting `"subagentStatuslineTrace": true` inside the machine config's `claude` object; it takes effect at the next launch.

Claude Code ignores the stderr of a `subagentStatusLine` command that succeeds, so the trace is a file the diagnostics can be read from afterwards:

- **Path and bounds:** `paths.SubagentStatuslineTrace(home)` = `~/.local/state/pfm/log/subagent-statusline.jsonl`, beside `cost-sink.log`. `obs.OpenRotatingLog` keeps two generations of 4 MiB (8 MiB in all) under a cross-process lock, mode 0600. The writer is `pfm/internal/statusline/subagents_trace.go`.
- **Records:** a `start` record before stdin is read; the input shape plus, per task, `id`, `type`, `status`, `model` and the pointer-typed `tokenCount` and `contextWindowSize`, so an absent value stays distinct from zero; the emitted ids; a final `result` record with stage, `elapsed_ms` and count. Each carries PID and timestamps.
- **Never recorded:** raw stdin, labels, prompts, descriptions, cwd, transcript paths or bodies, rendered content.
- **Failure:** a trace that cannot open or write reports the cause on stderr and rendering continues.
- **Rendering independent of the trace:** the sub-agent renderer emits a `pfm` row for every task id. A task with zero tokens and an unknown window shows context `?/?`, and an unknown token count never prints `0%`.

The trace records what the status line received and emitted; it does not by itself establish the cause of the transient sub-agent row symptom.

## The system prompt

- **The generated file is assembled at install, never at build.** `pfm install` joins `share/head.md` + `{engine}/professor.md` + `share/tail.md`, taken from the source parts embedded in the binary, and writes `{clone}/pfm/harness-prompts/generated/{claude,codex,opencode}.md` before any consumer runs. `generated/` is gitignored and not embedded. The assembly tests check the expected output of the source parts; the install lifecycle tests prove the files exist after install.
- **Launch points at the generated file.** `--system-prompt-file` is `{clone}/pfm/harness-prompts/generated/claude.md`, `{clone}` from the source-repo record (`paths.GeneratedHarnessPromptIn`). Nothing is copied to a staged location at install.
- **Workbench launches** replace the generated file with the manifest prompt; explicit `--system-prompt-file` / `--harness-prompt` win, and a role seat composes on that base (`internal/workbench/persona.go`, `internal/agentrole/base_prompt.go`).
- **Role seats** compose the claude prompt with the role into a seat file under the SID dir and pass that instead (`agentrole.ComposeSeatPrompt`); `pfm chat reload` refreshes it before respawning.
- **Missing file fails open, loudly:** the launch omits the flag and starts on Claude's own prompt, and the starter is told why (`claudelaunch.PromptWarning`, the one verdict) on the surface they launched from: stderr for `chat new` / `chat branch` / the picker / the launcher, the tool message for `open`, the pane for agent resume, the reload worker's log plus a pane display for reload; spawn-audit reports it too. A surface that attaches next (the picker, the launcher, `chat new --attach`) holds for Enter when stdin and stderr are both a terminal, so the attach cannot cover the warning (`internal/launchnotice`); off a terminal it only prints, and Ctrl-C at the launcher's prompt kills the server it made. Agent resume prints in the pane without waiting, since a detached pane has nobody to press Enter. A caller-stated `--system-prompt` or `--system-prompt-file` is deliberate and never warned.

## Remote control

`claude.remoteControl` (`config.ClaudePrefs.RemoteControl`, default `true`, `applyRemoteControl` in `pfm/internal/config/remote_control.go`) asks Claude to start an interactive session with Remote Control requested. The machine value is overridden by `accounts[].claude.remoteControl`; an account that omits it inherits the machine value (the `nativeCursor` rule). Key `claude.remoteControl` is registered in `pfm/internal/config/keys.go` and carried by `example.pfm.config.json`. The key postdates the last release, which refuses an unknown key, so `config.marshalClaude` writes it only when the file set it or it is `false`, and the first-install seed (`seedNewClaudeKeys`, `seedWithoutDefaultNewKeys` in `pfm/internal/installer/install_config.go`) omits the example's default `true`; a `false` stays. A fresh config therefore rolls back to that release, and an omitted key loads as `true`.

- **Placement.** `Render` ends with `RefreshRemoteControl` (`pfm/internal/claudelaunch/remote_control.go`), which strips any existing `--remote-control` and its optional value, then re-adds it when enabled. A named launch passes the chat name as the flag's value (`--remote-control {name}` in front of the other words). A name beginning with `-` uses the equals form `--remote-control={name}`, so Claude does not read the label as a command-line option. An unnamed one puts the bare flag directly before the first other flag, because the flag's argument is optional and a positional prompt would otherwise be consumed as its value; a minimal recipe with no flag at all gets `--remote-control --` ahead of its positional words. The name is `cmp.Or(Request.RemoteControlName, Request.Name)`: `RemoteControlName` is independent of `Name`, so a resume can carry a Remote Control name without `--name`, which would retitle the session. A name already on the argv (`--remote-control {name}` or `--remote-control={name}`) is kept when the caller passes no name and the argv has no `--name`; the argv's `--name` outranks it, a caller's name outranks both. `claudelaunch.Parse` reads the flag back as `RemoteControl` and `RemoteControlName`.
- **On and off.** On for interactive `Render` doors (fresh, resume, `claudeRun`, `LauncherRun`). Off for `PurposeQuery`, headless runs and any argv carrying `-p` / `--print`.
- **Stored recipes recheck the knob.** A saved native recipe (`seats/{seatid}.json`) never freezes the flag: `reload.RefreshRecipeRemoteControl` (`pfm/internal/reload/remote_control.go`) reapplies the current account-effective value at each start. Callers: `resumeNativeRun` and the restore path in `pfm/internal/chat/restored.go`, and `pfm internal seat-host` (`pfm/internal/hookentry/seathost.go`), which rereads the machine config before every engine start. The account comes from the recipe's own environment, not the picker's primary account or a launch record. Native reload re-renders through the registry and takes the same value.
- **Failure semantics.** Remote Control is additive: a policy that cannot be resolved never stops the chat. When the recipe's account is missing, ambiguous or no longer configured, or the seat host's config reread fails, `reload.DisableRecipeRemoteControl` removes the flag, prints `pfm WARN: chat {name}: Remote Control disabled: {reason}` to stderr, logs `launch.remote-control.disabled`, and the chat starts without it. Beyond that, pfm requests the feature and does not enable what Claude refuses: Claude decides eligibility at runtime (only a first-party `api.anthropic.com` login qualifies), so a gateway base URL or a disable setting leaves the session running without Remote Control. No pfm path validates a login or a connection.
- **Pass-through door.** `pfm internal launch` (`pfm/internal/hookentry/launch.go`) bypasses `Render` for an interactive forced or inside-pfm run and calls `RefreshRemoteControl` on its arguments with the account-effective value; print mode, help, version and the exempt subcommands (`launchRunsNonInteractive`) never get the flag.
- **Doctor, accounts.** `printRemoteControlDoctor` (`pfm/internal/doctor/remote_control.go`) prints one `doctor: remote_control claude[{id}]` row per configured account. A rosterless install gets one `claude[0]` row (`printRuntimeRemoteControlDoctor`): it takes the machine preferences, as `Render` does for account zero, and reads `{home}/.claude/settings.json` from `runtime.Paths.Home`. Each row reads the account's `settings.json` through shared-store symlinks, the managed policy, and the launch environment as it is after hygiene: the incoming process environment is filtered through `claudelaunch.Hygiene()` first, because the launch unsets those names, so an exported gateway variable the launch strips cannot raise a false BLOCKED; the account's `settings.env` is checked too, since Claude applies it after the cleanup and it overrides a surviving process value of the same name. Managed `env` and `apiKeyHelper` are merged over both: a managed value for a checked variable replaces the account's `settings.env` value and the surviving launch value of that name, and a managed `apiKeyHelper` replaces the account's. The reasons then name `managed settings env` or `managed settings apiKeyHelper` as their source. States:
  - `off by config (claude.remoteControl=false)`.
  - `on (knob on; no blocker seen; login and connection not verified)`: intent, not a connection check.
  - `BLOCKED: {reasons}` (a warning) for `disableRemoteControl=true` (managed or account), an effective `apiKeyHelper` (managed, else account), an `ANTHROPIC_BASE_URL` whose host is not `api.anthropic.com` (only the host is printed, never a credential or the full URL), `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` or `DISABLE_GROWTHBOOK` set true, or `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` set, each from the merged managed `env`, `settings.env` or a launch-env name hygiene does not strip.
  - `FAIL` (counted) for an unreadable or malformed account settings file, a dangling link included, or an unreadable or malformed managed policy.
  - A missing account `settings.json` is not a failure and hides no surviving launch-env blocker.
- **Doctor, managed policy.** `readManagedRemoteControlPolicy` (`pfm/internal/doctor/remote_control_managed.go`) reads `managed-settings.json` beside the managed directory plus every visible regular-file or symlink `*.json` drop-in in `runtime.Paths.ManagedSettingsDir`. Managed `disableRemoteControl` outranks the account's. It also collects managed `env` values for the checked variables and the managed `apiKeyHelper`. Sources that disagree report BLOCKED and the row never claims `on`: differing `disableRemoteControl` values give "effective managed policy precedence not verified"; differing values of one managed `env` variable or of `apiKeyHelper` give "managed settings have conflicting Remote Control environment or helper values; precedence not verified". pfm guesses no precedence.
- **Doctor, stored recipes.** `printRemoteControlRecipeDoctor` (`pfm/internal/doctor/remote_control_recipe.go`) scans the native Claude stored recipes of Herdr seats. A recipe whose account is unknown (in a configured roster) gets its own `doctor: remote_control recipe[{seatID}] BLOCKED` warning, `Remote Control not requested`; an unreadable recipe or a failed enumeration is `FAIL`. It ends with `doctor: remote_control recipes checked={n} native Claude stored recipes`.

## Doors

Each door builds a `claudelaunch.Request` — account, purpose, door verbs, per-launch choices — and calls `Render`.

A launch that resumes a session in place (`Resume`, or `--resume`, `-r`, `--continue`, `-c` in its args, with no `--fork-session`) carries no `--name`: the session restores its own name from its transcript, and Claude applies a launch name only once its session registers, so one landing then would revert a `/rename` the user typed meanwhile. A fresh launch and a fork keep theirs.

### PlanClaude

`pfm chat new` and MCP `new`. Verbs: `--session-id`, `--name`, the prompt positional. Per-launch: `--account`, `--cache 1h|5m`, `--model`, `--effort`, role seat file.

### HeadlessFork

`pfm chat branch`. Verbs: `--resume {id} --fork-session --name {name}`; model from the running chat. Its account is `--account`, else the parent's launch record, else the account its live seat runs on; with none of them and more than one configured account it refuses and asks for `--account`. It records the launch once the fork's new session id resolves. Claude writes the fork's transcript at its first prompt, so until then the fork is listed by its crumb under the window name it was launched with.

### Synthesize

The picker and `pfm chat open` / MCP `open`: `NewClaude` (`--session-id`, prompt), `ResumeClaude` (`--resume {id}`), `Agent` (`pfm internal agent-open`). Per-launch: the picker's account and cache toggle, whose initial state is the config value.

### AgentOpen

`pfm internal agent-open` inside the pane: `--resume {id}`, direct exec.

### claudeRun

`pfm chat reload` respawns the pane in place: `--resume {id}`, `--model`/`--effort` when given, the refreshed seat file. Account and cache come from `--account`/`--cache` when given, else from the chat's [launch record](#the-launch-record); the respawn updates the record.

### LauncherRun

A `claude` typed at a shell, through [the managed launcher](#the-managed-launcher). Values from config; never the autonomy flags. A fresh launch gets an assigned `--session-id` and a launch record; `--resume {id}` records that id; a launch whose session id pfm cannot know (`--continue`) records nothing.

### PurposeQuery

`claude agents --json` for the reaper, inject-resume and agent-open listings: the `--settings` payload, hygiene and account environment; no session-start flags.

### The Herdr seat door

A Claude, Codex or OpenCode chat born in a Herdr pane can be a **Herdr seat**: the engine runs in the pane's own terminal under Herdr, with no tmux server between them, so Herdr shows its state natively. Claude is detected and prompted natively (`HerdrNativePrompt` in its engine descriptor); Codex and OpenCode run the same seat host and are driven by the raw keystroke path (see Call and wait). Backend selection itself is unchanged.

- **Backend choice.** `spawn.ChooseBackend` (`pfm/internal/spawn/backend.go`) takes an explicit `--backend auto|tmux|herdr`, else `chat.backend` ([pfm-home.md § chat](pfm-home.md#chat)), else `auto`. `auto` picks Herdr only when `HERDR_ENV=1`, `HERDR_SOCKET_PATH` and `HERDR_PANE_ID` are set, `TMUX` is unset and a `pane.get` probe reaches the pane; `TMUX` set wins and means tmux. Under `auto`, a Herdr pane the probe cannot use prints one warning and starts in tmux; `selectBackend` names the state in that warning: `unreachable` when the probe error is a transport failure (a typed `net.OpError`, the socket cannot be dialed) and `probe failed` when the socket answered but with a refusal, a decode failure or a malformed `pane_info` identity. A forced `herdr` that cannot use its pane exits 1 with the same state word and the probe error as the wrapped cause, and creates no fallback chat. A requester that is itself a seat sets the socket, pane and workspace in place of the process environment (a Herdr requester) or keeps `auto` on tmux (a tmux requester).
- **Doors that choose it.** The managed launcher ([LauncherRun](#launcherrun)) reaches `pfm internal launch`, whose `--backend` defaults to `chat.backend` and feeds `launchBackend` (`pfm/internal/hookentry/launch_native.go`): on `herdr` it renders the same typed `claudelaunch` recipe and does not build the tmux server wrapper, and it refuses a pane that already has a live seat row (`SeatByPane`). `pfm chat new` parses `--backend` (`pfm/cmd/pfm/chat_new_command.go`).
- **Recipe and seat first.** `launchNative` writes the recipe, then the seat row, then runs the host. The recipe is a private (0600), atomic JSON file `seats/{seatid}.json` beside `pfm.db` holding `Binary`, `Args` (without argv0), `Env`, `CWD` and `cost_ledger` (`SeatRun.CostLedger`, the producer's account-effective cost-ledger choice; a legacy or hand-written recipe without the field means disabled); the seat id passes `^[a-zA-Z0-9_-]+$`. The seat row (`fleetdb.Seat`, table `seat`, `pfm/internal/fleetdb/seat.go` and `migration_v6.sql`) is addressed by backend: `tmux_socket`/`tmux_pane` or `herdr_socket`/`herdr_pane`/`herdr_workspace`, plus `session_id`, `name` and `state` (`live`, `lost`, `failed`). A store failure reads as an error, never as a missing seat. `PutSeat` and `UpdateSeat` each admit at most one `state='live'` Herdr row per socket and pane in one guarded SQL statement, for the launcher, the picker's `PrepareHerdr` reservation and a pane bind alike; a second live owner is refused, and a stale live owner blocks the pane (nothing supersedes or recovers it). `SeatByPane` returns the error `herdr pane … has multiple live seats` for historical duplicate rows rather than choosing one. The account launch registry stays the only producer of the recipe; nothing parses a shell command line.
- **The host.** `pfm internal seat-host {seatid}` (`pfm/internal/hookentry/seathost.go`) starts the engine from the recipe with argv0 taken from the registry descriptor (the executable may be a version path), in its own process group that is the terminal's foreground group. The engine's environment is the recipe's, except that the pane owns the Herdr and tmux identity and the terminal identity (`TERM`, `COLORTERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION`, `LANG`, every `LC_*`, `TERMINFO`): the pane's value wins and a name the pane lacks is dropped, never taken from the recipe, because a recipe born in the launchd daemon captured no terminal (`seatPaneKeys`). `/dev/tty` serves only as an ioctl handle to resolve the pane's concrete terminal device (`seatTerminalPath`); the engine's stdin, stdout and stderr (fds 0-2) are that concrete device, not `/dev/tty`. Immediately before starting the engine it arms the cost ledger from the recipe's `cost_ledger` with its own (the supervisor's) process, never the requester that planned the birth; no shell wrapper or creator-bound sink is involved. It forwards `HUP`, `INT`, `TERM` and `QUIT` to that group. When the engine ends normally the host removes the seat row and recipe and the pane closes. A start that cannot happen (a missing or malformed recipe, a missing executable) leaves the seat `failed` with the cause in `LostNote`, the recipe kept where one exists.
- **The reporter.** `pfm internal herdr-state` (`pfm/internal/hookentry/herdr_seat.go`) handles a native seat before the tmux bridge: the event must match the seat's socket and pane. `SessionStart` stores the session id and sends `pane.report_agent` with `resume_argv` `[pfm, chat, open, --restored, {sid}]`; native attach, detach and sync events are ignored. The tmux bridge is unchanged. A native hook (no `TMUX`, `HERDR_ENV=1`, socket and pane set) never reports from the environment alone: an absent store, a degraded store, or no durable owner matching the pane is a visible `native seat ownership unproved` error that points to `pfm chat open --restored`; the tmux-owner bridge and the shell bootstrap keep their own authority. The lookup is read-only (`fleetdb.OpenSharedStateReadOnly`); a writable store opens only for `SessionStart`, `SessionEnd` or a changed session id, and a state-only hook (working, idle, blocked, `agent-start`, `agent-stop`) writes no durable `UpdatedAt`. Claude's sub-agent tracking (`agent-start`, `agent-stop`; running agents keep the pane working with `N agents running`) uses the same shared session lock and private persisted state in a native seat, under tmux and in a direct run ([hooks.md](../hooks/hooks.md#herdr-reporter)). A seat with an unreadable or newer store is a visible error and the reporter stays fail-open. For a tmux-launched seat, `herdr-state` runs its durable `SessionStart` and `SessionEnd` bookkeeping after the unchanged tmux bridge, so a durable read or write failure is joined into the error but never suppresses or consumes the bridge's report. The first `UserPromptSubmit` that is not an interrupt clears the seat's `LostNote`; an OpenCode seat clears it on the plugin's `chat.message` event instead (Loss note below).
- **The socket facade.** `herdr.SeatRequest` (`pfm/internal/herdr/seat.go`) is the JSON socket call; only `agent.wait` takes a caller-bounded deadline longer than the ordinary reporter timeout.
- **`--then`.** On both backends `--then` keeps its ordered same-target steers. Pfm sends no automatic transcript reply: an answer comes back as an explicit, ordinary call in the other direction.
- **Birth from the CLI, MCP and picker.** `chat.BirthBackend` and `chat.BirthHerdr` (`pfm/internal/chat/birth.go`) keep a native birth out of the tmux-only tail of `pfm chat new`: they record the launch, then call `spawn.SpawnHerdr` (`pfm/internal/spawn/herdr.go`), which reserves the seat row and recipe through `spawn.reserveHerdr`, then asks Herdr for the tab with `layout.apply`: a Herdr refusal deletes the reservation, while a transport, decode or response error keeps it because the tab may exist. `spawn.PrepareHerdr` is the picker's reservation only; it performs no tab cleanup. The recipe is the typed `fleetdb.SeatRun` from `ClaudeSpawn.SeatRun` (`pfm/internal/action/claude_spawn.go`) or `HeadlessPlan.SeatRun` (`action.PlanCodex` and `action.PlanOpenCode`, `pfm/internal/action/headless.go`; `HeadlessPlan.Engine` carries the canonical engine id so a custom binary keeps its identity), built from the launch registry and never from a shell line. `herdr.CheckProtocol` (`pfm/internal/herdr/protocol.go`) runs on the chosen socket in `BirthHerdr` and again in `spawn.reserveHerdr`, so the MCP, picker (`PrepareHerdr`), dead-seat open and restored reservations share it: an unreachable, malformed or non-`herdr.SupportedProtocol` (22) server refuses the native reservation. `ClaudeSpawn.SeatRun` emits the registry's `launch.Binary`, `Argv`, environment and `CWD` with `cost_ledger` from `Machine.EffectiveClaude(Account).CostLedger`, with no managed shim or cost wrapper in it. `spawn.reserveHerdr` resolves the actual engine executable before the seat row, recipe or layout exists, so tmux planning stays engine-independent: Claude through `gather.ResolveClaudeBinary` (`pfm/internal/gather/claudebinary.go`; `installer.ResolveClaudeBinary` is its facade), Codex and OpenCode through `exec.LookPath` made absolute. The summary says the chat is starting, not delivered. `pfm chat new` under a Herdr backend reaches `PlanCodex` and `PlanOpenCode` for Codex and OpenCode, while OpenCode on tmux still refuses headless chat. With `await`, `BirthHerdr` waits through `headless.Await` over a native target (`nativeBirthTarget`) that proves the persisted seat's liveness (`nativeAlive`) independently of transcript availability, and takes the transcript path and CWD when one is indexed: a live Claude seat with no transcript yet is a starting seat, not an absent conversation. A Claude seat sitting at its folder-trust dialog before the first transcript makes the wait return `headless.ErrTrustDialog` and the chat state `blocked`, never gone: `pfm chat new --await`, `pfm chat ask` and `pfm chat stream` report the pane, the socket and that the chat is alive, with the manual remedy `pfm chat open {id}` (answer the dialog yourself) or a launch in a trusted directory. `chat.CheckAwait` (`pfm/internal/chat/status_pane.go`) reads the current visible pane frame through `call.CaptureHerdrVisible`, not `recent` history, so a dismissed trust selector never blocks; an active one still does. Pfm never trusts a folder and presses no keys. The exit code is 6 (`codeUndelivered`: the message was not delivered, or the chat is blocked at trust), never 3 for a live chat; a truly dead chat stays 3 (`codeDeadChat`) and a timeout 5 (`codeAwaitTimeout`). With `attach`, it opens the new seat through `viewNative` (see Open). The picker and `pfm chat open` inside a Herdr pane prepare the same pane's seat host (see Picker pane). Only the backend choice is request-local: the MCP `new` path binds `spawn.WithBackendEnvironment(ctx, nil)` (`pfm/internal/mcpserv/actions.go`), so `spawn.BackendEnvironment` never falls back to the daemon's environment and the socket, pane and workspace come from the requester seat's metadata (`chat.ScopedSelf`); an MCP proxy requester carries its own backend. The recipe is not request-local: `ClaudeSpawn.SeatRun` builds `Env` from `launchEnvironment(os.Environ(), launch)` and `spawn.reserveHerdr` resolves the binary over the process `PATH`, so in the MCP daemon both read the daemon's ambient environment, as the tmux recipe in `ClaudeSpawn.Command` does.
- **Picker pane.** A picker, or `pfm chat open`, running inside a Herdr pane ends with the chat in that pane — no new tab, nothing closed after an open elsewhere. A new or resumed chat is born in place: `action.Executor.Open` reserves the seat for the caller's own pane through `spawn.PrepareHerdr` and returns `exec pfm internal seat-host {seat}`, which the pane's shell runs, so the pane id, terminal and `HERDR_PANE_ID` stay (the seat host binds only when the pane's `shell_pid` is itself or an ancestor); the pane's tab, when the pane sits in it alone, takes the chat's label (`spawn.BirthTabLabel`: the launch or row name, else the project folder) through `herdr.LabelPaneTab`, and a failed label is a named stderr line, the birth proceeding. A dead native seat resumes in place through `restoreNative` (`pfm/internal/chat/restored.go`), which proves its old supervisor dead and rebinds the seat to the caller's pane. A live native chat on the caller's Herdr server comes to the caller's place (`moveNativeHere`, `pfm/internal/chat/open_herdr.go`): from the caller's tab its pane trades places with the caller's (`pane.swap`), from another tab of the workspace it moves in beside it (`pane.move`, which keeps its pane id, terminal and agent), and then the caller's pane closes, proved its own first by `call.ProveHerdrOwnPane` (Herdr's `pane.process_info` names this process among its foreground processes); a chat in another workspace (a move there re-ids its pane), a zoomed tab or an unproved own pane moves and closes nothing and names its cause. A caller pane hosting a chat of its own views by focus instead. A live tmux chat attaches in place, and before the attach `retireOtherHerdrViews` closes each other Herdr view the session's `@pfm_herdr` record lists on the caller's server only when `call.ProveHerdrBridge` names that very client of the chat's tmux server; an unproved view stays, named on stderr.
- **Identity, listing, status, name.** `pfm chat whoami` resolves a Herdr seat only from the live seat row at the caller's `HERDR_SOCKET_PATH` and `HERDR_PANE_ID` (`fleetdb.Store.SeatByPane`: `state='live'`; several matching rows are an error, not a pick) when a pid in the caller's process ancestry is one of the `foreground_processes` that `pane.process_info` returns for that pane on the seat's socket (`pfm/internal/resolve/herdr.go`); the seat row stores no engine pid, and inherited `HERDR_*` variables alone confer no identity. Otherwise it prints `ERROR: this chat is not inside tmux ($TMUX unset, and no ancestor carries it) nor a pfm Herdr seat`. Discovery (`gather.ProbeHerdrSeats`) lists each socket's panes once per invocation for all its live seats: a transport failure is a `HERDR UNREACHABLE` row and an answered refusal such as a missing pane is a `HERDR ERROR` row, both keeping `pfm chat ls` nonzero; a `failed` or `lost` seat stays visible as a non-addressable diagnostic without failing the listing; a durable-store read failure is appended as an error while the fleet and live tmux rows survive; a transcript row is preserved, and every seat of one session keeps its own socket. Status prefers the transcript and falls back to `agent.get` for a native seat. `compose` registers native seat identities before Agent classification, so a process agent matching a native session yields one durable addressed row; unmatched Agent, tmux and distinct native rows survive. A native Codex seat's explicit seat name wins over the indexed auto-generated title (`compose` `herdrRows`; a Claude `/rename` custom title still wins over the seat name); the auto-title stays in the indexed metadata and names a seat without a name of its own. `pfm chat name` types `/rename`, sets the pane label, a unique agent name and the durable seat name, converging without a tmux window.
- **Native kill and end.** `kill.Manager` (`pfm/internal/kill/manager.go`, `herdrTarget` in `pfm/internal/kill/herdr.go`) routes by the durable seat row, never by environment or an absolute socket name: a missing or mismatched ownership is a visible error. The existing composer ratchet (`Finisher.Run`, `pfm/internal/kill/finisher.go`) runs over `herdrKiller`: `/exit` is typed once the composer is empty, the gone-check is `pane.get` (`pane_not_found` means gone) plus `pane.process_info` read through `herdr.EngineForeground` (`pfm/internal/herdr/foreground.go`, shared with the tab painter): the pane exists while the engine is in `foreground_processes`; an engine absent from a validated nonempty list, an empty or missing list and a malformed entry are each an error (`herdr foreground evidence unavailable … live supervisor engine exit is unproved`), never "gone" (`herdrKiller.enginePresent` keeps this stricter pane-presence policy), and the last resort is `pane.close` on that pane only. A transport or malformed answer is an error, never "gone". When the optional seat lookup itself fails (a degraded store), `warnTmuxSeatFallback` keeps an explicit tmux target (a canonical absolute socket directly under the tmux directory plus a `%{digits}` pane) and writes the full cause to the kill log; a native, ambiguous or non-canonical target, and a failed tmux probe, still error. Every native mutation revalidates the seat, session and engine first. `chat.EndResolved` on a Herdr chat (`endHerdr`, `pfm/internal/chat/kill_server.go`) revalidates the durable seat, sends `pane.close` (`pane_not_found` tolerated), then deletes the seat's recipe and row; it never touches an unrelated pane. `chat.KillServer` still refuses an absolute (native) socket name, with an error that directs the caller to `EndResolved`. The picker's deactivate calls `EndResolved`; the UI keys a live seat by socket and pane for native rows (`liveSeatKey`, `pfm/internal/ui/model.go`) because panes share one Herdr server. `pfm chat kill` reaches this ratchet through `pfmchat.KillResolved` for a Herdr chat. `pfm chat modal {target} deny {n}` on a Herdr chat calls `call.DenyModal` (`pfm/internal/call/modal.go`): `Down` {n} times (200 ms apart), then `Enter`, each through `pane.send_keys`; a tmux target keeps its tmux commands. Unkill is unchanged.
- **Native reload.** `pfm chat reload` on a Herdr seat resolves the durable exact socket and pane (never an ambient guess) and forwards the typed request, with `AccountGiven` and `CacheGiven` recording which flags were typed. `reload.RunHerdr` (`pfm/internal/reload/command_herdr.go`) restarts the engine in the same pane for Claude and Codex (Codex resumes through `HeadlessRequest.ResumeSessionID`; OpenCode is refused at the engine level, like tmux). It serializes per pane through a lock in the SID directory (`lockNativeReload`: the directory is opened with `O_DIRECTORY|O_NOFOLLOW` and its owner and mode are validated, the lock leaf is opened with `Openat` `O_NOFOLLOW` and its owner validated before the `flock`, so a planted symlink or foreign-owned leaf fails closed), rewrites the canonical typed recipe from the launch registry (Claude) or `action.PlanCodex` (Codex), sets `reload_pending`, gracefully ends the engine and waits for the seat host to start the next engine in the same `herdr_pane`. An omitted account or cache keeps the current `SeatRun` environment's value (`nativeReloadDefaults`), an explicit flag overrides it. `pfm internal seat-host` clears `reload_pending` only after the new engine starts and the seat is recorded `live`; a start that cannot happen leaves `failed`, the cause in `LostNote` and a retry prompt (`press Enter to retry, q to close`) in the pane. The picker's reboot calls `RunHerdr` (`rebootRow`, `pfm/internal/picker/picker.go`); the UI applies it to native rows through the same applier. Tmux reload is unchanged.
- **Call and wait.** A call to a native seat first refuses a blocked or unknown target (`... is blocked; nothing was typed`). A busy native Claude seat takes the raw pane composer transport below, never `agent.prompt` (idle-only): the signed message and `Enter` queue with no `Escape`, and `force_now` sends `Escape` up to `InterruptTries`, delivering even when the cap leaves the pane busy (tmux parity). Before any interrupt and after each redraw the composer must be empty (an ANSI placeholder counts as empty) and a native Claude seat must show its full bounded box; a selector, menu or trust dialog refuses, and a draft is never overwritten. An idle engine with `HerdrNativePrompt` (Claude) sends `agent.prompt` once and reports `agent_prompted` (an acknowledgement without new-turn proof is followed by same-terminal, same-session `agent.get` observations within `ProofSettle`, default 500 ms, `CHAT_CALL_PROOF_SETTLE` in seconds: a working state-change seq or a completion seq beyond the pre-submit frontier confirms delivery, and a timeout, identity mismatch or read failure stays `delivered_unproven` with its cause, never resubmitted); an unconfirmed send is `typed_unconfirmed`; a composer that holds a draft, a menu or the trust dialog is `undelivered` with nothing typed (`pfm/internal/call/herdr_delivery.go`; the `--then` wait is in `herdr.go`). An engine without it (Codex, OpenCode; `callHerdrRaw`) reads the composer over `pane.read`, queues behind a busy footer as above, refuses a non-empty or menu composer and an unreadable pane with nothing typed, sends the prepared signed message verbatim through `pane.send_input` (`herdrSendText`, no bracketed-paste wrapping), presses `Enter` through `pane.send_keys` and confirms delivery on a second `pane.read` (retrying only the Enter; the paste is never retried); an unacknowledged write is `typed_unconfirmed`. `--then` on an idle-delivered native Claude seat waits with `agent.wait` under a caller-set deadline and honors the producer's `until` states; on a raw seat, a busy-delivered native Claude seat included (it goes through `callHerdrRaw`), it polls raw pane snapshots and needs an observed busy-to-idle transition, refusing an unobserved boundary (`raw Herdr turn boundary for … was not established`) with the steer retained. A turn that goes working to idle between the stale-idle reply and the second until-working request can be missed (a known low residual, not a claimed success), and a raw turn that finishes before the first busy snapshot is refused (fail-closed). All four directions (tmux or Herdr to tmux or Herdr) run the same call path; a reply is an explicit, ordinary second call, never an automatic callback. `Engine.SendKey` sends one named key to a Herdr seat through `pane.send_keys`. A delivery with `ask` and its `await`, and a `stream` follow, retain the resolved Herdr thread ID rather than the shared socket alone, so several seats on one socket stay distinct; an ambiguous target refuses.
- **Open.** `chat.openNativeRow` (`pfm/internal/chat/open_herdr.go`) checks the seat with `pane.get` and the foreground processes (`nativeAlive`), not the reporter's cached state. A live seat whose Herdr is the caller's own (`HERDR_ENV=1` and the same `HERDR_SOCKET_PATH`) is focused with `agent.focus`; elsewhere `herdr agent attach {pane}` runs with the seat's socket, and a failing attach prints `{name} lives in Herdr pane {pane} ({socket})` and exits nonzero. A seat is dead when `pane.get` answers `pane_not_found` or the old endpoint is missing or refuses the connection (`ENOENT`, `ECONNREFUSED`); any other probe failure is an error. A dead seat resumes by the caller's current birth rule: under a Herdr backend through `chat.OpenRestoredID`, otherwise as a tmux resume that drops the stale native address. A degraded shared state store still aborts `open` before its tmux path (a named residual: the fleet scan has no per-seat fallback).
- **Restored recovery.** `pfm chat open --restored {sid}` (`runChatOpen`) calls `chat.OpenRestoredID` (`pfm/internal/chat/restored.go`), the resume argv the reporter registers. It is non-interactive for every backend (`restoredGate` declines every confirmation, so a tmux restore never prompts either; a non-Herdr choice falls to `OpenID`). Under a Herdr backend it runs `herdr.CheckProtocol`, then: with no seat row it rebuilds the recipe from the indexed chat (`prepareRestoredSeat`: `ClaudeSpawn.SeatRun`, `PlanCodex`, or `Synthesize` for OpenCode; an indexed chat with no display name takes its complete session id as the seat name here only, never a prompt-derived title or an inferred model, and an existing name is unchanged) and reserves it with `spawn.PrepareHerdr`; with a row it rereads the stored typed recipe. `resumeNativeRun` rebuilds that recipe for the registered engine without the birth session id, name or initial prompt (the prompt is never resent), classifying Codex and OpenCode argv by the arities their launch producers emit so a stored yolo or no-model recipe restores to exactly one `resume {sid}` on every repeat and an unregistered value-taking flag fails closed, the reporter variables are stripped and the current shell's `HERDR_SOCKET_PATH`/`HERDR_PANE_ID` set. When the stored address differs from the current pane, the old owner is probed first (`nativeAlive`): a live engine, or a probe failure other than a missing or refusing socket, refuses the rebind; an absent or stopped owner permits it. The seat row is then rebound to the current pane (state `lost` until the seat host starts the engine and records `live`), the name is re-applied, and `pfm internal seat-host {seatid}` is exec'd in place. A changed owner before the rebind is an error, never an overwrite. Two simultaneous restores of one session are not serialized: both can start an engine before the seat host marks the seat `live` (a named residual).
- **Loss note.** `chat.lossNote` (`pfm/internal/chat/loss_note.go`) streams the engine's transcript (Claude and Codex files, OpenCode's snapshot): an unanswered last user message gives `your last message was not answered — re-send it`, an unresolved Agent/Task tool use gives `a sub-agent was running and ended`; the notes join with `; `, and prompt text is never quoted. A malformed or incomplete record keeps the loss already recognized before it and appends the fixed `restart loss unknown`; an unreadable, unindexed or unsupported producer persists and notifies that fixed note instead of an empty one, and no producer payload is copied into it. Pfm never resends or replays the lost message. The note is stored as `fleetdb.Seat.LostNote`, sent to Herdr with `notification.show` (a not-shown answer is reported, the stored note kept), shown by `pfm chat status` (a tab-separated tail on the status line) and by `pfm chat ls` (an indented `loss note:` line under the row), and carried through the additive `lost_note` field (`headless.Status.LostNote`, `compose.Row.LostNote`, the MCP status and row projections; never `Last`, `Error` or `BackendError`). The reporter clears it on the next non-interrupt `UserPromptSubmit` hook; an OpenCode seat's plugin (`pfm/internal/workbench/opencode_herdr_plugin.mjs`) reports each prompt creation (`chat.message`) as `working` with `hook_event_name: chat.message` and no prompt text, and the reporter accepts that marker only for an OpenCode `working` event that is not an interrupt.
- **Doctor.** `pfm doctor` (`printHerdrBackendDoctor`, `pfm/internal/doctor/herdr.go`) observes, never starts or changes a server: `doctor: herdr backend ok (protocol 22, {socket})`, `doctor: herdr backend UNREACHABLE — {reason}`, `doctor: herdr protocol {n} DIVERGES from supported 22 — herdr seats disabled`, a `resume_agents_on_restore` row read from Herdr's on-disk config (`false` warns that chats will not come back after a restart), and the `doctor: herdr-integration:` rows of `herdr_check.go` for Herdr's own bundled integration. On macOS (`herdrLifetimeUnverified` is set only in `service_manager_darwin.go`) it warns `doctor: herdr macOS lifetime fix (#5236) UNVERIFIED in this Herdr build ({version}) — no supported fixed release established`: no known Herdr release carries that fix, so no minimum version is enforced and protocol 22 support does not imply it.

### Every door that starts a Claude session

1. Render doors: `PlanClaude`, `HeadlessFork`, `Synthesize` (fresh, resume and agent fallback), `AgentOpen` resume, `claudeRun` and `LauncherRun` call `claudelaunch.Render`.
2. Headless: `claudelaunch.RenderHeadless` supplies `--settings` for `pfm headless exec`, `pfm ask`, the limits ACK and the doctor capture.
3. Passthrough that starts a session: `pfm internal launch` supplies the two plugin values in its process environment and, for an interactive start, arms the cost ledger itself (`costsink.PrepareCurrent`: the exporter variables and the `PFM_COST_LEDGER` marker, [cost-ledger.md](cost-ledger.md#doors)).
4. VS Code terminal: its `PATH` finds pfm's `claude` shim, so a typed session takes a render or passthrough door.

Query-purpose `agents --json` and the exempt subcommands start no session.

### Doors pfm does not own

The VS Code Claude extension's panel is not a pfm launch door. pfm never launches it. With `pfm install --yes --vscode`, pfm writes `claudeCode.environmentVariables` in owned VS Code settings to supply the primary account's `CLAUDE_CONFIG_DIR`. The panel reads the shared files through that account's links and does not receive pfm's rendered flags.

## The managed launcher

1. `~/.local/bin/claude` links to `~/.local/share/pfm/install/bin/claude`, which runs `pfm internal claude-launch "$@"`, first giving an unset `CLAUDE_CONFIG_DIR` the login default ([claude-config-dir.md](claude-config-dir.md#launches-outside-pfm)).
2. `claude-launch` resolves the real binary — `claude.binary`, else the newest native version under `~/.local/share/claude/versions/`, else `PATH` — never the launcher itself.
3. **Passthrough** — `PFM_LAUNCH_PASSTHROUGH=1`, already inside a pfm tmux socket, `-p`/`--print`/`--output-format`/`-h`/`--help`/`--version`/`-v`, or the subcommands `agents mcp update install doctor setup-token plugin config` — execs the real binary. Such a run carries no pfm settings except, when it starts a session, the two plugin env values in its process environment and, unless it is a print-mode run, the cost ledger's exporter variables and marker; the managed `cleanupPeriodDays` still applies to it.
4. Otherwise it renders `LauncherRun` into a fresh `cc-` tmux socket.

The `SessionStart` hook `launcher-repair` re-links a displaced launcher. Version retention keeps the newest two versions plus any a live process runs.

## The zsh shim

`~/.zshrc` sources `{clone}/pfm/internal/installer/assets/shim/pfm.zsh` directly; the file is static — nothing is rendered into it at install. It exports `CLAUDE_DISABLE_ADOPT=1`, `CLAUDE_CODE_DISABLE_BG_EXIT_HANDOFF=1`, `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP=2` into the interactive shell, and defines `claude()`, which calls `~/.local/bin/claude` and closes the terminal after a TUI session, `codex()`, which runs `command codex` with the transport `pfm internal codex-transport` answers (`--no-daemon` for a TUI; [Codex pane registry](../hooks/hooks.md#herdr-reporter)) and closes the terminal the same way, and `cx()`, which hands off to `pfm internal codex-launch`. The Codex launch reads each account's yolo setting from `pfm.config.json` and strips the registry's hygiene rows in Go; the shim carries no env list of its own.

## Long launch lines

A pane run over 8 KiB goes through a one-shot `/bin/sh` script under the tmux dir that deletes itself and `exec`s the run (`pfm/internal/tmux/launch.go`). The `--settings` payload with hooks is the common reason a run crosses the budget.

## pfm config claude

`pfm config claude [--account N]` prints every knob for that account — knob, wire, target, resolved value, and the source that won (`config`, `account`, `default`, `constant`). It is the answer to "what does a chat start with, and where do I change it".

## pfm doctor spawn-audit

Reads each live `cc-` chat's Claude argv from `/proc`, decodes it with `claudelaunch.Parse` — the inverse of `Render`, and the only parser of a Claude launch line — and classifies it:

| Verdict | Meaning |
| --- | --- |
| `INJECTED` | argv carries `--settings` with `outputStyle:"default"` and the registry's hook set, plus the prompt material the account's `systemPrompt` names (`--system-prompt-file`, or `env.CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT` inside the `--settings` payload) |
| `VIOLATION` | a fresh launch without the registry payload, or professor prompt material missing because the generated prompt is unavailable; that reason names the resolve error and blames no spawn site |
| `PREDATES-LAYER` | the process started before the current spawn door, with its age named, or its hook set differs from the registry at any age; reload to carry it |
| `ROLE-OK` / `ROLE-MISMATCH` / `ROLE-CHECK-FAILED` | a seat prompt file against its role |

Account attribution matches the process environment's `CLAUDE_CONFIG_DIR` to a roster entry by physical path, falling back to the cleaned spelling when either path cannot be resolved, before grading against that account's effective settings. A trailing slash or a symlinked spelling still matches. An empty roster grades against the primary account with no note. A missing or unmatched value is graded against the primary account with `account unmatched; graded against primary`. An unreadable environment reports `account environment unreadable; graded against primary`. No account is attributed to the store.

Values set through the `--settings` `env` block are read from argv, never from `/proc/{pid}/environ`: Claude writes them into its environment after exec. A probe that cannot run reports `CHECK FAILED to run … — live chats unaudited`, never "no chats".
