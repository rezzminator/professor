# Claude config dir

`~/.claude` is the only shared store. Each account has its own identity directory and a link to the store for every shared entry. pfm installs registry items once into the store and supplies launch values through the command line ([claude-launch.md](claude-launch.md)).

`{config dir}` means one account's `configDir` from `pfm.config.json`, `~/.cc/{id}` by default. It never means `~/.claude`. `{store}` means `~/.claude`; `{clone}` means the recorded framework clone.

## Decisions

- **One store, separate identities.** Every account shares transcripts, rewind history, tasks, plans, pasted content and prompt history. Reloading onto another account resumes the same session through that account's links.
- **The store holds no login.** Every account, including account 1, has its own directory. The directory may be a symlink when it resolves outside the store. An account resolving to the store, or into it, is a blocking host check, and a dangling account link is an inspection error. `claudelaunch.InspectConfigDir` is the one rule that launch, install, the host checks and doctor apply.
- **pfm wires shared links.** Install creates missing links. A link to existing data outside the store is kept and named for a merge; a dangling link or a link to the wrong store entry is repointed atomically, without touching its old target, only when that account has no live chat. An aliased account is skipped. Doctor checks the store and every account's links.
- **Unknown entries stay where they are.** A name on neither list reports `UNCLASSIFIED`; pfm does not share or delete it. `EntryClass` also recognises ignored entries: `ide`, `.cc-new-children`, `.cc-pane-children`, `settings.local.json`, and Claude Code's own runtime entries `debug`, `daemon.lock`, `daemon.status.json`, `.claude.json.lock` (the state file's transient write lock), `tmp`. A dir named after an installed plugin is that plugin's and reports nothing. A regular `*.md` file at the store's top level is the user's own instruction material, shared by construction, and reports nothing; the same name in an account reports `UNCLASSIFIED`.
- **Settings are shared by link.** Claude layers the shared user settings under project files, launch settings and managed policy. Per-account launch overrides live in `pfm.config.json`.
- **MCP definitions ride the launch.** `mcp.thirdParty` supplies operator servers beside pfm's `chat-professor` and `harvester-professor` entries. Trust, onboarding and login remain Claude's per-account state.
- **Retention applies outside pfm too.** The managed `cleanupPeriodDays` protects launches through other paths.
- **A managed drop-in must not demote the person's plugins.** Claude Code 2.1.299+ seats its built-in `cc-plugin-sec-default@builtin` ahead of the person's plugins on any machine with managed settings unless a managed `prependPlugins` is set, and the seated plugin skips user-tier plugin hooks. pfm's drop-in carries `"prependPlugins": []` so it is not seated.

## How Claude finds its files

The config directory is `$CLAUDE_CONFIG_DIR`, falling back to `~/.claude` when unset. User memory, registries, plugins, rules, themes and user settings are read under that directory. pfm's account launches always set `CLAUDE_CONFIG_DIR`; shared entries reach them through their links.

Claude's state file is `${CLAUDE_CONFIG_DIR:-$HOME}/.claude.json`. With the variable unset it is `~/.claude.json`, outside the store. `settings.local.json` is a project file, `{project}/.claude/settings.local.json`, rather than an account settings file. Claude also checks `~/.claude/ide` for IDE locks. Claude writes user `settings.json` through its symlink, preserving the link.

## The store

`ClaudeStore`, `StoreEntries`, `AccountEntries` and `IgnoredEntries` live in `pfm/internal/installer/claude_store.go`. `StoreEntries`, in source order:

| Entry | Type | Holds |
| --- | --- | --- |
| `agents` | directory | user agents and pfm registry items |
| `commands` | directory | user commands and pfm registry items |
| `skills` | directory | user skills and pfm registry items |
| `rules` | directory | user rules |
| `plugins` | directory | the shared plugin installation |
| `themes` | directory | custom palettes |
| `projects` | directory | transcripts: `{cwd slug}/{session id}.jsonl` |
| `file-history` | directory | rewind checkpoints by session id |
| `tasks` | directory | task lists by session id |
| `session-env` | directory | per-session environment captures |
| `plans` | directory | plan files |
| `paste-cache` | directory | pasted content by content hash |
| `shell-snapshots` | directory | shell environment snapshots |
| `uploads` | directory | attached files |
| `downloads` | directory | fetched files |
| `teams` | directory | agent team state |
| `settings.json` | file | shared user settings; seed `{}\n` |
| `CLAUDE.md` | file | user memory; empty seed |
| `history.jsonl` | file | prompt history; empty seed |
| `stats-cache.json` | file | statistics cache; empty seed |
| `.last-cleanup` | file | cleanup marker; empty seed |
| `gh-pr-status-cache.json` | file | pull-request status cache; empty seed |
| `tool-visibility-controller.json` | file | the tool-visibility-controller plugin's user scope file; seed `{}\n` (a missing file is no rule, an empty one is invalid JSON) |

Every missing entry is created empty (apart from the `settings.json` and `tool-visibility-controller.json` seeds). Existing entries are left intact. Transcript readers use `~/.claude/projects` (`engine.claudeDefaultRoots`); `PFM_CLAUDE_ROOTS` is a jail override. The transcript path does not identify its account; the [launch record](claude-launch.md#the-launch-record) does.

## Account dirs

`AccountEntries`, in source order, are never linked to the store:

| Entry | Holds |
| --- | --- |
| `.credentials.json` | login token |
| `.claude.json` | account identity, folder trust, onboarding and flags |
| `.claude.json.backup` | Claude state backup |
| `backups` | Claude state backups |
| `sessions` | live-process registry and process tokens |
| `daemon` | account daemon state |
| `daemon.log` | daemon log |
| `daemon-auth-status.json` | daemon authentication state |
| `daemon-auth-cooldown` | daemon authentication cooldown |
| `jobs` | daemon background jobs |
| `cache` | account model catalog |
| `state` | account state, including `mcp-discover-verdicts.json` |
| `mcp-needs-auth-cache.json` | MCP servers awaiting account OAuth |
| `telemetry` | queued account telemetry |
| `feedback` | queued account feedback |
| `.last-update-result.json` | the native updater's last result |

`.last-update-result.json` was a store entry until Claude's native updater was seen writing it by temp file and rename at the account path, which replaces a link with a real file. It is the first of `RetiredStoreEntries` (`pfm/internal/installer/retired_store_entries.go`): an entry once linked from every account and now per-account. A real file in an account dir is the healthy shape; a leftover link into the store and the store copy are `retired-store-entry` warnings, which `pfm install` migrates ([Install build](#install-build)). A future retirement is one more row in that list and its name in `AccountEntries`.

`sessions/{pid}.json` describes a live process, rather than the conversation transcript. On reload, the new process registers in the selected account's directory. For `state` inside the store, `store-identity` checks only `state/mcp-discover-verdicts.json`, and it skips `cache` there (a rebuildable cache that other tools' hooks also write under the store). While account 1's dir resolves to the store, each identity path in the store is the same file as its account path, so `store-identity` prints no delete: the entry moves into the real dir that `account-is-store`'s fix makes ([host-checks.md](host-checks.md#store-identity)). Unknown names in either the store or an account report `UNCLASSIFIED` and remain untouched, except a regular `*.md` file at the store's top level.

## Settings

Claude's effective layers, highest first:

1. Managed settings, including pfm's retention drop-in.
2. Command-line flags and pfm's `--settings` payload.
3. The project's `.claude/settings.local.json`.
4. The project's `.claude/settings.json`.
5. The account's `settings.json` link to `~/.claude/settings.json`.

A settings `env` value overrides the shell's value; a flag overrides its settings key. Hooks merge across layers. `/config` writes shared user settings through the account link, so every account sees the change. An account-specific launch value belongs in that account's `claude` block in `pfm.config.json`. With `$HOME` as the working directory, the store's `settings.json` is also read as that project's `.claude/settings.json`.

## MCP servers

`--mcp-config` carries every `mcp.thirdParty` entry, plus pfm's `chat-professor` and/or `harvester-professor` server when the corresponding family is enabled. Third-party entries remain present when both families are off. The key is a map from server name to a JSON object in Claude's `mcpServers` shape; validation reserves both pfm server names.

Install inspects existing account `.claude.json` files found through configured accounts, the account roster, ambient config and default paths. It removes only exact pfm-owned legacy entries, emits or reconciles enabled `chat-professor` and `harvester-professor` entries, preserves and reports foreign `professor` entries, and does not create absent registry files. Doctor reuses this inspector and reports each account's registry state, foreign entries and unreadable files.

## Launches outside pfm

- The terminal's `claude()` shell function calls pfm's managed launcher (`pfm/internal/installer/assets/shim/pfm.zsh`). Its rendered account launch chooses the ambient account directory or the primary account and sets `CLAUDE_CONFIG_DIR`. Passthrough preserves the ambient environment and supplies only the session plugin values; it does not choose an account.
- `pfm install --yes --vscode` sets `claudeCode.environmentVariables` in owned VS Code settings to include `CLAUDE_CONFIG_DIR` for the primary account. `vscode-ownership.json` records the prior value. Other environment entries are preserved; an operator edit relinquishes ownership on an ordinary install. `--vscode` reclaims the entry in that run, preserving the operator's value for uninstall. Uninstall restores the prior value only while pfm's value is still present. A malformed environment array skips only its upkeep; profile, default and scalar settings still update.
- `pfm install` writes the login default, so a Claude started from a login shell, a systemd user service or a desktop launcher lands in the primary account's dir (the one VS Code and the plugin step use) instead of the store. `~/.config/environment.d/pfm-claude-config-dir.conf` carries `CLAUDE_CONFIG_DIR=${CLAUDE_CONFIG_DIR:-{config dir}}` and `PFM_CLAUDE_CONFIG_DIR_DEFAULT={config dir}`; `~/.profile` and `~/.zshenv` each carry one block fenced by `# BEGIN pfm claude-config-dir — installer-owned` and `# END pfm claude-config-dir — installer-owned` that sets and exports both only when `CLAUDE_CONFIG_DIR` is unset or empty (`if [ -z "${CLAUDE_CONFIG_DIR:-}" ]`). The condition is load-bearing: `~/.zshenv` runs in every zsh, including the shells of panes pfm launched on another account and every tool shell of a running chat. environment.d has no conditional that sets one variable on another's absence, so its sentinel is unconditional; `claudelaunch.InheritedConfigDir` counts the sentinel only where `CLAUDE_CONFIG_DIR` equals it, so a preset dir never reads as the default. Every pfm launch strips the sentinel and sets `CLAUDE_CONFIG_DIR` itself.
- Install creates a missing file, keeps every other line and replaces the block in place (appending it the first time; a changed existing file is backed up as `{file}.pre-professor-{stamp}`); a second install prints `ok` and changes nothing; a preview prints the same `change` lines and writes nothing. A symlinked `~/.profile` or `~/.zshenv` is never written through: a skip names the link, its target and the block to add or remove by hand. With no roster or no primary account, install prints `skip    login default: {reason}` and removes the blocks and environment.d file an earlier install wrote. A `--config-dir` install on a roster host leaves the login default as it is; on a host with no roster it removes it like any install without a roster. The primary dir failing the launch refusal, a value with a space, quote, backslash, `$` or backtick, or a damaged fence (a begin with no end, an end with no begin, two begins, or a second end marker) prints `FAIL    login default: …` and fails the run after every other step, the file untouched. Uninstall removes both blocks, deleting a file left empty, and the environment.d file.
- The `claude` wrapper (`~/.local/bin/claude`, staged from `pfm/internal/installer/assets/bin/claude`) gives an unset or empty `CLAUDE_CONFIG_DIR` the login default's value: it reads `PFM_CLAUDE_CONFIG_DIR_DEFAULT` from the environment.d file above and exports both variables, so a `claude` started by a process that never ran a login shell still lands in the primary account's dir. A set value is kept; a host without the file (no primary account) runs unchanged.
- Calling a binary under `~/.local/share/claude/versions/` directly bypasses the wrapper. Launched without `CLAUDE_CONFIG_DIR`, it reads shared files from the store, writes state to `~/.claude.json` and backups to `~/.claude/backups/`. Doctor warns about that home state file and blocks on identity entries inside the store, each row naming the file's mtime and `firstStartTime`, with a fix that moves it aside under `~/.local/state/pfm/stray-claude-state/` ([host-checks.md](host-checks.md#stray-state-birth)). A bare binary needs an explicit account directory to use that account's identity.

## Install build

The [host checks](host-checks.md) run before any install write in preview, apply and `--check`. A blocking finding refuses the install; its fix is an operator action printed by doctor. Warnings allow install to continue.

After the gate, `wireClaudeStore` builds the shared entries and links:

1. Create missing store directories with mode `0700`; create missing files with mode `0600` and their `Seed`. Leave existing entries intact.
2. Create each missing account directory as a real directory with mode `0700`.
3. Create an absent shared-entry link to the store; report a correct link as `ok`. Keep a link to existing data outside the store and name its merge. Repoint a dangling link or a link to the wrong store entry atomically, only when that account has no live chat. Skip an aliased account with `skip    account {id} {config dir} is the same directory as account {first id}`. Leave every real file or directory untouched: the host gate already refused that shape.

The install transcript uses `change  create {path}`, `change  link {config dir}/{entry} -> {store}/{entry}`, `change  repoint {config dir}/{entry} -> {store}/{entry} (was {old})`, `ok      {config dir}/{entry}`, `skip    {config dir}/{entry} links to {target} outside the store — pfm doctor names its merge`, and `skip    repoint {config dir}/{entry}: live chats {pids} on {config dir} — close them and rerun pfm install --yes`.

Then `retireStoreEntries` migrates each `RetiredStoreEntries` entry:

1. In each account, by ID, remove a link at `{config dir}/{entry}` resolving to `{store}/{entry}`: `change  unlink {config dir}/{entry} (a per-account file now)`. A real file, a link elsewhere and an absent entry are left alone; Claude writes the account's own file.
2. After every account's link is gone, move `{store}/{entry}` into `{home}/.local/state/pfm/retired-store-entries/{entry}.pre-professor-{stamp}` (a `.N` suffix when taken): `change  archive {store}/{entry} -> {archive}`. Nothing is deleted. While an account resolves to the store, the copy stays: `skip    keep {store}/{entry}: account {id} {dir} resolves to the store — pfm doctor names the fix`. With no roster to check its links, the copy also stays: `skip    keep {store}/{entry}: no account roster to check its links — pfm doctor names the fix`.

A preview prints the same lines and writes nothing. A failed remove, mkdir or rename returns the error naming its paths. A second run finds nothing to do and prints nothing.

## Managed settings

`pfm install` writes `pfm.json` in `/etc/claude-code/managed-settings.d/` on Linux or `/Library/Application Support/ClaudeCode/managed-settings.d/` on macOS (`PFM_MANAGED_SETTINGS_DIR` overrides the directory in a jail):

```json
{ "cleanupPeriodDays": 36500, "prependPlugins": [] }
```

`cleanupPeriodDays` comes from `claude.cleanupPeriodDays` and also rides launch `--settings`. An empty `prependPlugins` counts as set: Claude Code 2.1.299+ then does not seat `cc-plugin-sec-default@builtin`, which skips user-tier plugin hooks (`session.compact`, `classic.Stop`, `classic.SubagentStop`, `prompt.attachment`) on a machine with managed settings. pfm owns only its drop-in and merges into it: other keys survive, an existing `prependPlugins` value is never rewritten, and the key is added only when no managed source sets it. Only a list of plugin ids counts: Claude Code reads any other `prependPlugins` value, `null` included, as unset, so pfm keeps such a value in its drop-in but install prints `warn    managed-cleanup prependPlugins in {file} is not a list of plugin ids, which Claude Code ignores; left alone` and doctor warns. Another managed source — any other `*.json` Claude Code lists in `managed-settings.d/` (a regular file or symlink, not hidden), or `managed-settings.json` in the directory above — setting `prependPlugins` to a list is an organization's own plugin order; install leaves the key out, prints `skip    managed-cleanup prependPlugins is set by {file}; left alone`, and doctor reports the source. A source that cannot be read also blocks the key: install prints `warn    managed-cleanup prependPlugins not added: {file}: {cause}`. It attempts a direct write, then `sudo -n` when needed, printing the command; a refusal is advisory and doctor warns. Linux uses `install -D`; macOS uses `mkdir -p` and `install`, quoting the path's space. Managed policy applies through every launch path and outranks the other settings layers.

## What pfm does not write

pfm writes no launch setting or env key into user settings, no account trust, onboarding or identity in `.claude.json`, no `settings.local.json`, `output-styles/` or `keybindings.json`, and no user `CLAUDE.md` content. It creates the shared `CLAUDE.md` empty when absent. Account trust, onboarding and identity are Claude's.

The plugin step runs once through the primary account for the plugins `claude.plugins` lists (unset: `cache-live-control`, `sub-agent-compact`, `auto-effort-control`, `tool-visibility-controller` and `engine-sync`; `[]`: none). An entry is a bare name of ours, a full `name@marketplace` id, or `{"id": "name@marketplace", "source": S}`. A bare name installs from `rezzminator/{name}`, except `auto-effort-control`, whose repository is still `rezzminator/auto-effort` (an explicit alias in `pfm/internal/installer/claude_plugins.go`, dropped once the repository is renamed). A full id installs as named: `claude plugin marketplace add S` runs first when the entry has a `source` (an already-added marketplace is no failure), then `claude plugin install {id} -y`; with no `source` only the install runs, and only when Claude Code already knows the marketplace (a key of `plugins/known_marketplaces.json`). A full id that is not yet installed and enabled, has no `source` and names an unknown marketplace is not attempted: install prints `FAIL` for it, naming the id, the marketplace and the repair (give the entry a `source`, or run `claude plugin marketplace add`), and goes on with the rest. No other id in `settings.json` is read for change or written: a plugin neither the list nor, on an alpha build, the marketplace names keeps the value of its `enabledPlugins` and `pluginConfigs` entries (a retirement edit below re-encodes the whole file, so key order and spacing may change, never a value). Claude's plugin commands write shared `plugins/**` and `enabledPlugins` in shared `settings.json` through that account's links. An already installed and enabled plugin needs no command. On an alpha build (version ending `-alpha`), each bare name installs as `{plugin}@{plugin}-dev` from the marketplace `~/.local/share/{plugin}-dev`: pfm writes its `.claude-plugin/marketplace.json` and mirrors `{root}/{plugin}/plugins/{plugin}/` into `plugins/{plugin}` as a real directory on every install — `{root}` is `claude.pluginCheckoutRoot` when set, else the source clone's `plugins/` (install's own clone, else the recorded marker, else `~/.professor`; doctor reads the marker, else `~/.professor`) — skipping `node_modules` and `.DS_Store` and replacing a symlink (the copy is the checkout's files on disk, committed or not: pfm reads no git state, so an edit in the working tree reaches Claude at the next install, by design for a development loop), since Claude refuses plugin files outside its marketplace. Claude does not run that copy in place: `claude plugin install` and `claude plugin update` snapshot it into `{config}/plugins/cache/{plugin}-dev/{plugin}/{version}` and record that `installPath` and `version` per scope (`user`, or `project` and `local` with their `projectPath`) in `plugins/installed_plugins.json`, and a chat runs the snapshot. Claude takes a new snapshot only when the version changes, so for an installed copy, after the copy refresh (and callmeter's binary step, below), and after a fresh install for the scopes it leaves, pfm runs `claude plugin update {id} --scope {scope} -y` once per scope whose entry records a version other than the checkout's `plugin.json` version (a `project` or `local` entry from its `projectPath`) and reads the record back: an entry still behind fails the plugin naming both versions. An entry pfm cannot move — a `projectPath` that is not an absolute directory (repair: recreate it, or `claude plugin uninstall {id} --scope {scope}` from that project), a scope `update` does not take — or whose update fails fails the plugin naming its repair, every other entry still updated. A non-string `scope`, `projectPath` or `version` in the record reads as empty. A snapshot at the checkout's version whose content differs from the checkout (compared without `node_modules`, `.DS_Store` and `.orphaned_at`), before the updates or after them, is a `warn` line naming the repair, bump the version: `update` leaves it, since Claude caches by version. A checkout whose `plugin.json` names no version is a skip line naming why and the repair, add a version: nothing is compared or updated. Claude keeps a replaced snapshot on disk, marked `.orphaned_at`, so an open chat keeps running the version it loaded; the new version reaches a chat when it restarts. It then sets the GitHub id `false` in `enabledPlugins` (never uninstalling it) and copies that id's `pluginConfigs` entry to the `-dev` id when the `-dev` id has none. With a checkout missing, that plugin falls back to its GitHub copy, with one line in install and doctor naming the root it tried (`claude.pluginCheckoutRoot` or the source clone's `plugins/`). With the key unset and the source clone unresolved, or a checkout that cannot be read, neither copy is decided: install leaves both ids' `enabledPlugins` and `pluginConfigs` as they are and fails the plugin step naming the error, and doctor warns that the plugin cannot be checked, naming the error. Release and unstamped builds always use the GitHub copies. An alpha build also plans every plugin the source clone's `.claude-plugin/marketplace.json` lists (`ClaudePluginBuild.WithMarketplacePlugins`): with `claude.plugins` unset the list is all of them, in the manifest's order; with it set, each one the list names in no form (bare or `name@marketplace`) is planned install-only. An install-only plugin is installed from its checkout like any bare name (with no checkout it is never installed, from GitHub or otherwise: install prints one skip line naming the root it tried and doctor warns), and every copy of it (`{plugin}@{plugin}`, `{plugin}@professor`, `{plugin}@{plugin}-dev`) is set `false` in `enabledPlugins` — the install enables it, the edit after it disables it — its `pluginConfigs` carried as for any copy. An alpha build treats `{plugin}@professor` as a third copy of a bare name, retired like the GitHub one, unless `claude.plugins` lists that id itself. A manifest that cannot be read, parsed or validated (an empty list, a name that is not one safe path element, a name listed twice), a source clone that is unresolved, or a missing manifest with `claude.plugins` unset is a `FAIL` line, the list or the release default still planned. A `-dev` marketplace Claude Code knows from another source is re-pointed for an installed copy by `claude plugin marketplace add {dir}` (Claude re-points a known name and keeps its plugins and their options; `marketplace remove` would delete those, so pfm never runs it) and read back after: still foreign, it fails naming the remove and what it deletes. For callmeter, whose wrapper runs `{CALLMETER_HOME, else XDG_STATE_HOME when absolute, else ~/.local/state, plus /callmeter}/bin/{plugin.json version}/callmeter` and downloads a release binary only when that file is missing, pfm builds `./cmd/callmeter` from the checkout's module (`go build -trimpath -buildvcs=false -ldflags "-s -w -buildid= -X main.version={version}"`, `CGO_ENABLED=0`, `GOWORK=off` and `GOFLAGS=-mod=readonly`, without the inherited `GOEXPERIMENT`, `GOOS` and `GOARCH`; a `plugin.json` version of `.` or `..` is refused) into a scratch dir beside that path before the copy is refreshed: equal executable bytes are left alone; otherwise the binary in place is hard-linked to `callmeter.prev` and the build renamed over it, holding the wrapper's download lock `bin/.lock-{version}` (a live holder fails the plugin, to rerun; one older than 120 seconds is taken over). A failed build fails the plugin and leaves its copy unrefreshed; the database beside it is never touched; a preview builds nothing. After an applied alpha pass, every bare name `claude.plugins` lists that the pass did not already fail is read back with doctor's own checks: one not installed from its `-dev` copy and enabled — a fallback, a disabled id, a stale copy, a foreign marketplace — prints `FAIL    claude plugin {id} in {dir}: not installed from its -dev copy and enabled after this install: {each problem}` and fails the run; the summary line then ends `failed={n} (each FAIL line above)`. A retired default is disabled the same way once its successor is ensured: the ids `{plugin}@{plugin}`, `{plugin}@{plugin}-dev`, `{plugin}@professor` and `{plugin}@rezzminator` of each of `agent-effort`, `auto-effort` and `effort-live-control` are set `false` in `enabledPlugins` when enabled (never uninstalled) after `auto-effort-control` is installed and enabled; doctor flags an enabled one whether or not the successor is ensured. The same edit settles `pluginConfigs` on the successor's id, since the plugin warns on every duplicate entry of one plugin name: the first entry among the successor's other copies and then the retired ids' (in `retiredClaudePlugins` order) is copied to the successor's id when that id has none, never overwriting, and then every other-copy and retired entry is deleted, a deleted entry that differs from the successor's named `(differs)` in the change line; the successor's id always holds an entry before any other goes, so no user's only copy is lost. Doctor flags a lingering entry (`pluginConfigs of {ids} still in {file}`, repaired by `pfm install`). Every build keeps exactly one copy of each bare name enabled (a full id has no twin to retire): when it ensures the GitHub id it sets an enabled `-dev` id `false` the same way, carrying that id's `pluginConfigs` to the GitHub id when the GitHub id has none. Doctor checks the build's ids and flags two or more copies of a bare name enabled at once, a missing, symlinked or stale local copy (one whose content differs from its checkout), a snapshot behind its checkout (an `installed_plugins.json` entry recording another version, repaired by `pfm install --yes`) or at its version with other content (repaired by a version bump), an install-only plugin enabled under any copy, and on an alpha build each fallback; on an alpha build every gap of a plugin `claude.plugins` lists is a failure, printed `doctor: claude_plugins FAIL {problem} — {repair}`, and every other gap a warning. It also flags any other plugin enabled under two or more keys, pfm's or not, unless `claude.plugins` lists every one of them (install would enable a disabled one again), with the repair `claude plugin disable` on each extra key, and a listed plugin whose marketplace `plugins/known_marketplaces.json` registers from a source other than the one install adds (an entry with no `source` adds none and is not compared; an `owner/repo[#ref]` source matches a `github` record of that repo, an absolute path a `directory` record of that path, and a URL a record holding that URL; a URL against a `github` record and a relative or `~` path against a `directory` record are not compared, since pfm cannot rebuild what Claude Code recorded for them; a key or source read from either file prints with its control characters escaped): `plugin marketplace add` answers already-added for a same-named marketplace, so its repair is `claude plugin marketplace remove {marketplace}` before `pfm install --yes`; for a local `-dev` copy pfm install re-points it, so its repair is `pfm install --yes`. No live chat holds a plugin command or settings edit back: a running chat keeps the snapshot it loaded. A chat may still write `settings.json` while pfm edits it: each of pfm's retirement edits reads the file again just before its rename (`atomicfile.WriteIf`) and, when its bytes changed, re-applies the edit to the new content, at most three times; a fourth change fails the plugin naming the file and the repair, rerun `pfm install`. A failed command returns an error. An unreadable settings file or install record prints `FAIL` and fails the run after every later step; an unreadable `plugins/known_marketplaces.json` fails only the full ids with no `source` still to install and each installed `-dev` copy (its re-point and read-back read that file), and the rest go on.

The fullscreen canary clear skips an account with a live chat; unreadable settings or registry state prints `FAIL` and fails the run after every account and every later step have been handled.

On a host with an account roster the step's dir passes `claudelaunch.CheckConfigDir`, the refusal every launch applies: with no primary dir resolved, the fallback to install's config dir (the store) prints `FAIL    claude plugins in {store}: {store} resolves to the Claude store — run pfm doctor`, runs no command and fails the run after every later step. A preview passes a primary dir install would create first. A `--config-dir` install on a roster host uses that dir and applies the same refusal. A host with no roster whose install config dir is the store runs no claude command and prints one `skip` line (`claude plugins: not run — no account roster, so the only config dir is the Claude store {dir}, where a claude process writes account identity; add an account to pfm.config.json and rerun pfm install --yes`), no warning: a claude process on the store writes `.claude.json` and `backups` into it, and without `CLAUDE_CONFIG_DIR` it writes `~/.claude.json`, which doctor warns about as `home-state-file`. A rosterless `--config-dir` outside the store runs the step in that dir. Each plugin command's environment sets `CLAUDE_CONFIG_DIR` to its dir and drops `PFM_CLAUDE_CONFIG_DIR_DEFAULT`.

## Registries

Each item is written once under the store. Every account sees the same agents, commands and skills through its shared-entry links.

| Path under `{store}` | Target or content |
| --- | --- |
| `commands/reload.md` | `~/.local/share/pfm/install/reload.command.md` |
| `commands/*` | `{clone}/templates/global/commands/` entries |
| `skills/handoff/SKILL.md` | `~/.local/share/pfm/install/handoff.skill.md` |
| `skills/*` | `{clone}/templates/global/skills/` dirs with a `SKILL.md` |
| `skills/{name}` | `~/.local/share/pfm/install/skills/{name}/` source clone |
| `agents/*.md` | clone sources, or rendered declarations under the clone's tracked `templates/generated/agents/` |
| `themes/*` | one `{name}.json` per `templates/themes/{name}/` profile directory; `theme-ownership.json` records ownership |

Source-fetched skills also link under `~/.agents/skills/{name}`. `templates/global/skills/sources.json` registers their repos; `templates/global/agents/` supplies agents; `templates/themes/` supplies themes.

A regular file in the way is backed up before replacement; an existing link can be replaced. Global registry inspection reports foreign targets as conflicts. The registry-ownership scan (`InspectRegistryOwnership`) walks store `agents`, `commands`, `skills` and `~/.agents/skills` without following directory links and classes each link by its target against the install plan (`PlanRegistryLinks`), never by name: `STORE` a link into a retired generated store, `ORPHAN` a live link into a recorded clone or the managed install root that the plan no longer writes, `DEAD` such a link whose target is gone, `RETIRED` an unmarked entry named for a retired agent, command or skill. Foreign links and any other unmarked entry are never listed. Unreadable paths return errors. Install retires `STORE`, `ORPHAN` and `DEAD`, uninstall every owned link; `RETIRED` stays in place. Doctor prints each as a `doctor: registry {CLASS} …` row, else `doctor: registry-ownership ok`. A retired path already absent prints nothing.

## Runtime writes

`pfm archive` prunes archived sessions from `~/.claude/history.jsonl` after a backup to the archive's `_sidecar-backups`. Kill's finisher removes `~/.claude/.cc-new-children/{id}` and `~/.claude/.cc-pane-children/{id}`.

## Reads pfm depends on

Account discovery and the usage hook read `{config dir}/.credentials.json`. Live-session lookup reads `{config dir}/sessions/{pid}.json`. Duplicate-login checks read `.claude.json` `oauthAccount.emailAddress`. Plugin checks read the store's `plugins/installed_plugins.json` and `settings.json` `enabledPlugins` once. Picker, find and archive read the shared `projects` root.

## pfm doctor checks

The authoritative detector list, severities, problems and operator fixes are in [host-checks.md](host-checks.md). Doctor prints `host-check: {severity} {check} {path} — {problem}` and a separate `host-check:   fix: {fix}` line. A `BLOCK` counts a failure; a `WARN` counts a warning. It separately checks the targets built by install:

| State | Output | Tally |
| --- | --- | --- |
| store entry missing | `store: {store}/{entry} missing — run pfm install` | failure |
| store entry unreadable | `store: {store}/{entry} UNREADABLE error={cause}` | failure |
| store entry broken | `store: {store}/{entry} broken: {why} — remove {store}/{entry}, then run pfm install --yes` | failure |
| account directory missing | `account: {id} {config dir} missing — run pfm install` | failure |
| account directory unreadable | `account: {id} {config dir} UNREADABLE error={cause}` | failure |
| account directory is a file | `account: {id} {config dir} is a file, not a directory — mv {config dir} {config dir}.bak, then run pfm install` | failure |
| shared link missing | `account-link: {config dir}/{entry} missing — run pfm install` | failure |
| shared link elsewhere (dangling or wrong store entry) | `account-link: {config dir}/{entry} points at {target}, want {store}/{entry} — run pfm install` | failure |
| shared link to outside data | `account-link: {config dir}/{entry} points at {target} outside the store — run pfm install --yes; its host check names the merge` | failure via host check |
| shared link unreadable | `account-link: {config dir}/{entry} UNREADABLE error={cause}` | failure |
| real shared entry | host-check `account-entry-real`; no duplicate target row | failure via host check |
| all targets clean | `account-links: ok ({a} accounts × {e} entries)` | none |

Managed retention reports `managed-cleanup: {path} missing` with the transcript-deletion warning, `cleanupPeriodDays={v}, want {config value}`, or `has no cleanupPeriodDays, want {config value}` for a null or keyless drop-in. A drop-in with a correct `cleanupPeriodDays` and no `prependPlugins` anywhere reports `{path} has no prependPlugins — Claude Code 2.1.299+ seats cc-plugin-sec-default and skips your plugin hooks`; a missing or wrong row with the key also absent adds `; prependPlugins is unset too — {the same consequence}` before the repair line. When pfm's drop-in lacks it and another managed source sets it, a `managed-cleanup: prependPlugins is set by {file} — pfm leaves it` row follows the drop-in's own row; once pfm's drop-in holds a list, other sources are not read (Claude Code concatenates managed lists, so pfm's `[]` never displaces an organization's order). A non-list value in pfm's drop-in adds a `{path} prependPlugins is not a list of plugin ids, which Claude Code ignores — {the same consequence}; set it to [] or a list of plugin ids` warning. Missing, wrong and no-prependPlugins rows are warnings and append `; run: {sudo line}`, the same repair line install prints, which writes the merged document. `UNREADABLE error={cause}` counts a failure, for pfm's drop-in and for any other managed source. `claude.requireManagedCleanup: false` prints `managed-cleanup: check off by config`.

Registry checks cover `agents`, `commands` and `skills` with `state=missing|conflict|unreadable` and `hint="run pfm install"`, plus dead pfm links. Plugin checks run once on the store: `doctor: claude_plugins ok`, or `doctor: claude_plugins plugin {id} not enabled in {store}/settings.json — run pfm install --yes` / `doctor: claude_plugins plugin {id} not installed in {store} — run pfm install --yes` / `doctor: claude_plugins plugin {id} cannot be installed: marketplace {marketplace} is not known to Claude Code and its claude.plugins entry has no source — {repair}` (one warning, in place of the first two for that id, printed beside the skipped row too) / `doctor: claude_plugins plugin {name} enabled twice ({id} and {id}) in {store}/settings.json — keep one copy: claude plugin disable each other key` / `doctor: claude_plugins plugin {id} marketplace {marketplace} in {store}/plugins/known_marketplaces.json points at {source}, want {source} — claude plugin marketplace remove {marketplace}, then run pfm install --yes` / `doctor: claude_plugins plugin {id} cache in {store}/plugins/installed_plugins.json records version {version} (scope {scope}), checkout {checkout} is {version} — run pfm install --yes` / `doctor: claude_plugins plugin {id} cache {installPath} differs from {checkout} at version {version} — bump the version in {checkout}/.claude-plugin/plugin.json: Claude caches by version; then run pfm install --yes` / `doctor: claude_plugins plugin {id} cache in {store}/plugins/installed_plugins.json cannot be checked: {checkout}/.claude-plugin/plugin.json names no version, and Claude caches by version — add a version to {checkout}/.claude-plugin/plugin.json, then run pfm install --yes`; a behind entry pfm cannot move names its own repair in place of `run pfm install --yes`, and a plugin not installed is only named not installed. Missing store settings print a skipped row; read errors count failures, an unreadable `plugins/known_marketplaces.json` is one failure that leaves every listed plugin that does not need it checked, and a snapshot or checkout the cache check cannot read prints `doctor: claude_plugins could not read the plugin cache: {error}` and counts one failure.

Plugin-logs checks run on an `-alpha` build only (`obs.AlphaBuild`, the predicate the `-dev` plugin install uses); a release build prints `doctor: plugin_logs does not apply: pfm {version} is not an -alpha build`, untallied. Every config dir pfm manages, the store and each account's, must set `PLUGIN_LOG_DIR` in its `settings.json` `env`, the folder plugins write `{folder}/{plugin}/{errors,warnings,info}.jsonl` under (unset, each falls back to its own folder: `~/.local/state/{plugin}/logs/`, callmeter's under its home, which `CALLMETER_HOME` or an absolute `XDG_STATE_HOME` moves — `installer.PluginLogFallbackDir`); a `settings.json` linked from several dirs is read once and its line names every dir on it, and two spellings of one absolute path are one value. Every line prints file-derived text control-escaped. Warnings: `doctor: plugin_logs PLUGIN_LOG_DIR is missing for config dir {dirs}: no {settings}` or `: {settings} sets no env.PLUGIN_LOG_DIR`, `PLUGIN_LOG_DIR differs across config dirs: {dir}={value} …`, `PLUGIN_LOG_DIR "{value}" for config dir {dirs} is not an absolute path`, `no log folder at {folder}`, `plugin {plugin}: {n} rows stranded in its fallback {dir} while PLUGIN_LOG_DIR is set` (every plugin the source clone's `.claude-plugin/marketplace.json` lists, its `*.jsonl` files and their `.1` rotations, judged only while a value is set), `fallback logs not checked: no source clone …`. Failures: `could not read PLUGIN_LOG_DIR for config dir {dirs}: {cause}` (an unreadable, unparsable or non-regular file, `env` not an object, the value not a string — never read as missing), `the log folder {folder} is not a directory`, `the log folder {folder} is a link to a missing target`, `the log folder {folder} is unreadable or unwritable: {cause}` (the kernel's access answer for read, write and search), `could not inspect the log folder`, `fallback logs not checked: {cause}` (the source clone unresolved or its marketplace list unread), `plugin {plugin}: could not count the rows in its fallback {dir}: {cause}` (a matching name that is not a regular file included). A `-dev` copy's installed version against its checkout is the `claude_plugins` cache check's alone. `doctor: plugin_logs ok: PLUGIN_LOG_DIR={folder} in every config dir` prints only when every check held.

VS Code prints `doctor: vscode not managed (pfm install --vscode never ran)` when unmanaged. A `profile=PFM(missing)` row counts one warning with `run pfm install --yes --vscode`; it is the only settings row when the owned settings file is gone. Owned settings with no account environment report `doctor: vscode settings={path} CLAUDE_CONFIG_DIR missing — run pfm install --yes --vscode`; a wrong value reports `CLAUDE_CONFIG_DIR={value}, want {primary dir}` with the same fix. A relinquished entry adds ` (pfm relinquished it after an operator edit)` before the fix. A malformed environment array reports one warning, `doctor: vscode settings={path} claudeCode.environmentVariables unreadable error={cause}`, with no fix or `CLAUDE_CONFIG_DIR` row; profile and default state still report. When an operator's own `PFM` terminal profile would make `--vscode` refuse, its `profile=PFM(relinquished)` row counts one warning with `rename or remove the "PFM" terminal profile in {path}, then run pfm install --yes --vscode`; both account-environment rows use the same fix. A profile matching a shape pfm itself once wrote is reclaimed by `--vscode`. Launcher checks report `doctor: launcher: missing`, `DISPLACED by {target}` or `unreadable error={cause}`, each with `run pfm install`.
