# RR — Implementations of LLM code-reviewer agents, as evidence for a HEAVY/LIGHT two-tier reviewer design

Question: implementations of LLM code-REVIEWER agents — an agent that reviews a code diff (PR, branch range, working tree) and reports defects. Collect the different implementations and techniques people have built and reported working, with one precise end use: we will design TWO reviewers — a HEAVY reviewer for large/risky diffs and a LIGHT reviewer for small diffs. The map must give evidence for both designs and for the routing rule between them.

---

## Answer

The field has converged on one architecture — **generate candidates, then verify/filter them before posting** — and the only techniques with controlled measurement behind them are the verifier pass (BitsAI-CR +8.5pp precision; LLM4PFA 72–96% FP elimination), execution-based evidence (AnyPoC rejects 9.7x more false positives), and risk-based routing (Meta RADAR, Qodo's adaptive router: −21% cost, −27% runtime at all-Deep F1). For the two-tier design the decisive and counterintuitive finding is that **diff size, not model size, is the dominant quality variable**: F1 collapses from 0.657 on sub-10-line diffs to 0.043 over 150 lines, while a small model (Haiku 4.5, $0.003/review) beat a large one (Sonnet 4.6, $0.010) on F1 and recall — so the HEAVY tier's job is decomposition, context and verification, not merely a bigger model, and the routing rule should key on hunk count / blast radius / path sensitivity rather than on a raw line threshold alone.

## Map

### 1. The dominant pipeline shape: find-then-verify

Every system with published precision numbers uses two stages — a generator that over-produces candidates and a filter that kills most of them.

- **ByteDance BitsAI-CR** — RuleChecker (LoRA-finetuned Doubao-Pro-32K over a review-rule taxonomy) + a binary **ReviewFilter**. Published ablation: RuleChecker alone **57.03% precision → 65.59% with ReviewFilter** (~+8.5pp); production precision **75.0%**, Go "Outdated Rate" (adoption proxy) 26.7%, **12,000+ weekly active engineers** ([arXiv 2501.15134](https://arxiv.org/abs/2501.15134), [HTML](https://arxiv.org/html/2501.15134v1)).
- **Refute-or-Promote** — candidate hunters, then Stage A (1 creative + 2 adversarial agents, adversaries see only the claim to prevent anchoring), Stage B (2 creative + 3 adversarial, context-asymmetric), Stage C mandatory **empirical validation**, Stage D **cross-model critic** from a different model family. Stage A kills ~63%, Stage B kills ~42% of survivors; aggregate **~79% of ~171 candidates killed**, prospective **83% (25/30)**. Cross-model critic caught ~3% of kills and found correctness errors in **3/19 (16%) of same-family-approved fixes**. Outcome: 4 CVEs + 36 total findings for **~$250 (~$62/CVE)** over a 31-day campaign. Explicitly **optimises precision and does not measure recall** ([arXiv 2604.19049](https://arxiv.org/html/2604.19049)).
- **Anthropic `claude-code-security-review`** — diff analysis → semantic detection over 10+ vulnerability classes → **a dedicated false-positive filter pass** spawning parallel sub-tasks per finding → PR comments with severity. Excludes DoS, rate-limiting, memory exhaustion, generic input validation, open redirects as noise categories ([README](https://github.com/anthropics/claude-code-security-review/blob/main/README.md)). The filter is **pure LLM self-scoring** — `confidence_score` comes straight from Claude in `claudecode/findings_filter.py`, not a trained classifier, and **defaults to 10.0 (max confidence) when the API call fails** ([findings_filter.py](https://github.com/anthropics/claude-code-security-review/blob/main/claudecode/findings_filter.py), [Issue #69](https://github.com/anthropics/claude-code-security-review/issues/69)). A separate live issue reports the filter **silently broken since 19 Feb 2026** because it hardcodes a retired model ([Issue #139](https://github.com/anthropics/claude-code-security-review/issues/139)). Anthropic publishes **no precision/FPR number**.
- **Ellipsis** — webhook → queue → repo clone → parallel comment generators → a four-stage filter: dedupe → confidence threshold → **hallucination filter using attached Evidence** → comment editing (line-number fixup). Context via tree-sitter AST chunk index, per-file LLM summaries, and **Lsproxy language-server** go-to-definition/find-references. Claude 3.5 Sonnet + GPT-4o with cross-vendor fallback. **No quantitative results published** — the source itself concedes this ([ZenML LLMOps entry](https://www.zenml.io/llmops-database/building-and-deploying-production-llm-code-review-agents-architecture-and-best-practices)).
- **DeepMind CodeMender** and **Big Sleep** are the same pattern with execution as the gate: PoC exploits, functional-equivalence and differential testing before a patch is accepted ([CodeMender](https://deepmind.google/blog/introducing-codemender-an-ai-agent-for-code-security/), [Big Sleep/SQLite](https://www.scworld.com/news/googles-big-sleep-llm-agent-discovers-exploitable-bug-in-sqlite)).

### 2. Industrial deployments with real numbers

- **Meta RADAR (Risk Aware Diff Auto Review)** — the most complete production funnel: authorship classification (human vs bot) → source-type gating (deterministic codemods, AI codemods, RACER runbooks, human diffs) → static heuristics (open-source/SOX metadata) → **60-day bot risk-history lookback** (PI/revert/rejection rates) → daily volume caps (10–2,000 diffs/day per runbook) → **ML Diff Risk Score percentile threshold** → LLM automated code review requiring **≥8/10 confidence** → deterministic validation before landing. **535K+ diffs reviewed, 331K+ landed, peak 25,000/day**; relaxing the gate from the 25th to the 50th percentile raised approve rate to **60.31%** (verification pass rate 26.31%) without degrading safety; RADAR-reviewed diffs show **1/3 the revert rate and 1/50 the production-incident rate** (p<1e-16, p<1e-6), median time-to-close down >330%, median review wall time down 35% ([arXiv 2605.30208](https://arxiv.org/abs/2605.30208), [HTML](https://arxiv.org/html/2605.30208v2)).
- **Google ML-suggested edits / AutoCommenter (Critique)** — calibrated to a **target precision of 50%** for shown suggestions; addresses **52% of comments** offline at that target; **40–50% of previewed suggestions are applied**; preview rate rose ~20% → ~40% after UX changes; fraction of comments resolved via ML doubled from beta to launch; serving-time heuristics suppress known failure patterns identified from "not helpful" feedback ([Google Research](https://research.google/blog/resolving-code-review-comments-with-ml/)).
- **Meta CodeCompose** is authoring/completion (22% acceptance), distinct from RADAR — do not conflate the two.

### 4. Open-source implementations worth copying

- **Qodo Merge / PR-Agent** — the reference LIGHT design: **one LLM call per tool** (`/review`, `/improve`, `/describe`, `/ask`), ~30s, low cost. Its **PR compression** algorithm, in order: exclude binaries; sort files by language prevalence, then by patch token count descending; **deprioritize deletions** (batched into one list, deletion-only hunks stripped); iteratively pack patches with tiktoken until a buffer below the model max; overflow files fall to a soft-truncated "other modified files" list, then a hard-truncated deleted-files list. **Small PRs get 3 lines of context expansion above/below each hunk; large PRs skip this** ([compression_strategy.md](https://github.com/Codium-ai/pr-agent/blob/main/docs/docs/core-abilities/compression_strategy.md), [repo](https://github.com/The-PR-Agent/pr-agent)).
- **Anthropic Claude Code `/code-review` plugin** — the reference HEAVY fan-out: **Haiku gate-check** (skip closed/draft/duplicate PRs, fetch CLAUDE.md) → Sonnet PR summary → **4 parallel review agents (2 Sonnet for CLAUDE.md compliance, 2 independent Opus for bug/logic)** → **re-validation pass** (Opus for bugs, Sonnet for compliance) before posting. FP suppression is prompt-based, not scored: an explicit allowlist skips pre-existing issues, linter-catchable style nitpicks, and lint-ignored code. Output is inline comments with SHA/line links and optional ≤5-line committable suggestions; **no numeric severity** ([code-review.md](https://github.com/anthropics/claude-code/blob/main/plugins/code-review/commands/code-review.md)).
- **calimero-network/ai-code-reviewer** — 4 Sonnet agents on distinct lenses (security, performance, patterns, logic) + 1 tool-disabled Haiku for style; findings clustered and **weighted by agent agreement ("3/3 agents")**, ranked severity × agreement into CRITICAL/WARNING/SUGGESTION; incremental delta review with a **convergence halt** once findings stabilize ([repo](https://github.com/calimero-network/ai-code-reviewer)).
- **claude-code-action** — full Claude Code inside a GitHub Actions runner, interactive (`@claude`) or automation mode, with repo/git-history/diff access. Diff-size limits and cost/latency are **not in the top-level README — UNVERIFIED** ([repo](https://github.com/anthropics/claude-code-action)).
- **OpenAI Codex PR review** — clones into its own cloud sandbox and can run commands; docs say only that it "reviews the pull request diff" and follows `AGENTS.md`. Surfaces **P0/P1 only** (thresholds undefined). Whether tests actually execute during the *review* step is **UNVERIFIED** ([GitHub integration docs](https://learn.chatgpt.com/docs/third-party/github)).

### 5. Benchmarks — and what they do and do not measure

- **"Bigger Isn't Always Better" ([arXiv 2606.15689](https://arxiv.org/html/2606.15689v1))** — 5 models, 150 samples (100 synthetic mutations + 50 real bug-fix PRs from next.js, react, fastapi, flask, pydantic, prisma, terraform, docker/compose; merged, bug-labelled, 1–10 files, 20–500 lines).
  - Per-model F1 on the full n=150 set: **Haiku 4.5 0.365 · Sonnet 4.6 0.343 · GPT-5.4 mini 0.326 · Minimax M2.7 0.322 · GLM-5 Turbo 0.310**.
  - Haiku vs Sonnet head-to-head: recall **0.293 vs 0.248** (+18.1%), precision **0.486 vs 0.558** (Sonnet better), cost/review **$0.003 vs $0.010 (3.2x)**.
  - **Diff size dominates**: F1 **0.657 (<10 lines) → 0.043 (>150 lines)**; the 10–50 line bucket is "the sweet spot".
  - Per-category recall (%): Security 69.6–71.1 across all models · Logic 12.7–24.5 · Architecture 13.6–33.3 · Best Practice 0.0–6.7 · **Performance 0.0 for four of five models** (GLM 4.5).
  - Synthetic vs real: **0.847 → 0.066** (Haiku, 92% drop); others 94–99% drops.
  - **Ensembling multiple models measurably HURT F1** (best single 0.365 vs pairings 0.30–0.33).
  - Authors' own top recommendation: **"preprocess large diffs" is "the most actionable finding"** and diff size is "the highest-leverage intervention"; use smaller models; pair with deterministic/AST rules for performance and architecture bugs.
  - Cross-validated on the third-party Martian benchmark: Haiku F1 36.4% vs Sonnet 27.1%, Haiku ranking #9 between Copilot and CodeRabbit.
- **c-CRAB / Code Review Agent Benchmark ([arXiv 2603.23448](https://arxiv.org/html/2603.23448v1))** — converts human PR comments into **executable tests** (LLM comment-classifier tuned to ~86% precision on a 100-comment gold set → per-PR Docker envs → generated tests that must fail pre-fix and pass post-fix → validated by an independent agent fixing from the comment text alone). 184 PRs, 67 repos, 234 tests, median 123 modified lines. Per-agent pass rates: **Claude Code 32.1% · Devin 24.8% · PR-Agent 23.1% · Codex 20.1%**, union ≈40% (97/234). Agents do well on functional correctness and robustness (verifiable from the diff) and badly on Documentation/Design/Maintainability (**7.9–27.0%**, needing repo-level convention knowledge); they **over-review robustness and testing, under-review design and maintainability** relative to humans. *(Per-agent figures are WebFetch-summarized from the HTML, not read off the raw table — treat decimals as indicative.)*
- **CodeFuse-CR-Bench ([arXiv 2509.14856](https://arxiv.org/abs/2509.14856))** — Ant Group/UNSW; 601 instances, 70 Python projects, 9 PR problem domains, full repo state; rule-based location/syntax checks + model-based quality judgment. No single LLM dominates all dimensions; Gemini-2.5-Pro best comprehensive; models differ in robustness to redundant context.
- **AACR-Bench ([arXiv 2601.19494](https://arxiv.org/abs/2601.19494), [GitHub](https://github.com/alibaba/aacr-bench))** — Alibaba; 200 real PRs, 50 projects, 10 languages, repository-level context; AI-assisted expert-verified annotation raises defect coverage **285%** over mining raw PR comments. Per-model leaderboard not retrieved.
- **CR-Bench** — pairs with a "CR-Evaluator" scoring precision/recall/F1 **plus a usefulness rate and signal-to-noise ratio** — the one benchmark explicitly measuring noise. **FAILED LOOKUP:** OpenReview PDF and ResearchGate both returned 403; details are search-snippet-level only.
- **CodeReviewer (Li et al., FSE 2022, [arXiv 2203.09095](https://arxiv.org/abs/2203.09095))** — the pre-LLM baseline; four review-tailored pretraining tasks over 9 languages; absolute precision/recall not in the abstract (UNVERIFIED without the full body).

### 6. The measurement problem — vendor benchmarks do not survive replication

- Greptile's own July-2025 benchmark (50 seeded bugs, 5 repos) reported **Greptile 82% · Bugbot 58% · Copilot 54% · CodeRabbit 44% · Graphite 6%** ([greptile.com/benchmarks](https://www.greptile.com/benchmarks)) — but **Augment Code's independent re-run on the identical repos produced 45%, not 82%**; DeepSource also flags the 50-PR sample as too small, criticises Qodo's use of LLM-injected rather than real bugs as ground truth, and notes most vendor benchmarks publish neither ground truth nor scoring logic ([DeepSource critique](https://deepsource.com/blog/ai-code-review-benchmarks)). **The Greptile benchmark excludes false positives from scoring entirely** — its 82% is recall-only, alongside ~11 FPs/run vs CodeRabbit's ~2.
- **Independent noise audits:** a Lychee-project audit across 28 PRs (32,784 lines added, 693 files) classified CodeRabbit's comments as **35% genuine improvements, 21% nitpicks, 15% useless/noise, 13% wrong assumptions, 13% thoughtful, 3% security/critical** — i.e. 15–28% noise depending on how nitpicks are counted (**no primary Lychee document found — secondary write-ups only, UNVERIFIED**, [Substack](https://theaiengineer.substack.com/p/how-coderabbit-actually-works)).
- **The cost of unfiltered volume:** curl's HackerOne confirmed-vulnerability rate fell from "north of 15%" to **below 5%** as AI-generated "slop" submissions surged, contributing to the bounty shutting down 31 Jan 2026 ([Daniel Stenberg](https://daniel.haxx.se/blog/2026/01/26/the-end-of-the-curl-bug-bounty/)). This is the clearest real-world demonstration that a high-recall, low-precision reviewer destroys the channel it reports into.
- **Comment-resolution study:** ["Go Home Copilot, You're Drunk"](https://arxiv.org/html/2607.21997v1) — 54,791 AI review comments across 342 Python repos: **Copilot 72.9% resolved, Cursor 67.2%, Codex 54.8%**. The strongest predictor of resolution was **the presence of an inline code suggestion**; long/complex comments were resolved less often.

## HEAVY reviewer — techniques that raise recall and catch deep bugs on big diffs

1. **Fan-out to independent lenses, then re-validate.** Claude Code's `/code-review` runs 2 Sonnet compliance agents + **2 independent Opus bug agents in parallel**, then a separate re-validation pass before posting ([source](https://github.com/anthropics/claude-code/blob/main/plugins/code-review/commands/code-review.md)). calimero uses 4 lens agents + agreement-weighted ranking. Qodo 2.0 adds a **judge agent** to resolve conflicts and dedupe.
   - **Caveat with a measurement behind it:** naive **model ensembling reduced F1** (0.365 best-single vs 0.30–0.33 paired) in [arXiv 2606.15689](https://arxiv.org/html/2606.15689v1). Fan-out helps when lenses are *different questions*, not when they are *the same question to different models* and answers get unioned.
2. **Adversarial verification, with context asymmetry.** Refute-or-Promote's adversaries see only the claim (preventing anchoring) and are split into informed/naive/senior tiers; kills ~63% at Stage A and ~42% of survivors at Stage B; **cross-model-family critic** caught errors in 16% of same-family-approved fixes. Note its own cautionary finding: **ten reviewers unanimously endorsed a nonexistent OpenSSL Bleichenbacher oracle that only an empirical test caught** — "unanimity is a low-signal event" ([arXiv 2604.19049](https://arxiv.org/html/2604.19049)).
3. **Execution as the gate, not reasoning.** AnyPoC is the controlled number: requiring proof-of-concept execution evidence yielded **37% more valid PoCs and rejected 9.7x more false-positive reports** ([arXiv 2604.11950](https://arxiv.org/pdf/2604.11950)). CodeRabbit generates and runs verification scripts in a per-PR sandbox; CodeMender runs PoC exploits and differential tests. Counter-caution: **46% of "passing" validation events carried no bug-discriminating information** ([arXiv 2607.28871](https://arxiv.org/abs/2607.28871)) — the test must discriminate, not merely pass.
4. **A verifier stage, measured.** BitsAI-CR **+8.5pp precision** (57.03 → 65.59) from ReviewFilter alone; LLM4PFA eliminates **72–96% of false positives while missing 3 of 45 true bugs** (recall 0.93 on NPD), and its ablations show the **agentic multi-step decomposition — not raw compute — drives the gain** (dropping iterative context analysis or batching all constraints cuts FP-reduction by 137–173%) ([arXiv 2506.10322](https://arxiv.org/pdf/2506.10322)).
5. **Codebase tracing beyond the diff.** Ellipsis (tree-sitter AST chunks + per-file LLM summaries + **Lsproxy** go-to-definition/find-references), CodeRabbit (Codegraph + co-change history), Greptile (repo knowledge graph). c-CRAB's evidence supports this directly: agents fail precisely on the categories requiring **repo-level convention knowledge** (design, maintainability, documentation: 7.9–27.0%).
6. **Multi-pass voting, measured in production.** Cursor Bugbot's **8 parallel passes + majority vote + validator model** took resolution rate from **52% to >70%** and bugs/run 0.4 → 0.7 ([Cursor](https://cursor.com/blog/building-bugbot)). General self-consistency literature shows **confidence-weighted voting reaches the same accuracy with ~10 samples vs ~18.6 for plain majority** — diminishing returns arrive early ([arXiv 2502.06233](https://arxiv.org/pdf/2502.06233), [Adaptive-Consistency](https://arxiv.org/pdf/2305.11860)).
7. **Measured cost of heavy.** Refute-or-Promote: **~$250 / 31 days / 36 outcomes ≈ $62 per CVE**. Bugbot: **~$1.00–1.50 per PR** usage-based; Greptile deep review = **3 credits vs 1** ($1/extra review). A Kilo Code benchmark put a 338-line PR reviewed with Claude Opus at **$0.73 on 618,853 input tokens** (search-snippet, UNVERIFIED). Against a LIGHT tier at $0.003–0.10 that is a **10x–200x** multiple.
8. **Per-hunk ledgers / completeness forcing — NOTHING FOUND.** No published technique forcing a reviewer to account for every hunk or file with a measured recall gain. Searches tried: "LLM code review large diff checklist ledger every hunk coverage completeness recall". The indirect support is the F1-vs-size collapse plus the paper's own call for per-function/per-hunk splitting as the highest-leverage unimplemented intervention. **This is genuinely open ground, not a solved technique.**

## LIGHT reviewer — the cheap/fast tier for small diffs

1. **Shape: one LLM call, diff-scoped.** PR-Agent's design — a single LLM call per tool, ~30 seconds, JSON-structured output, roughly **$0.02–$0.10 per review** (search-snippet cost figure, UNVERIFIED; the one-call/~30s design is documented) ([repo](https://github.com/The-PR-Agent/pr-agent)).
2. **Small models are not the compromise they look like.** Haiku 4.5 beat Sonnet 4.6 on F1 (0.365 vs 0.343) and recall (+18.1%) at **3.2x lower cost ($0.003 vs $0.010/review)**, replicated on the third-party Martian benchmark (36.4% vs 27.1% F1). Sonnet won on **precision** (0.558 vs 0.486) — so the large model is the better *filter*, the small model the better *finder* ([arXiv 2606.15689](https://arxiv.org/html/2606.15689v1)).
3. **Keep:** security (recall 69.6–71.1% and essentially **commoditized — every model scores the same**), logic bugs (12.7–24.5%), functional correctness and robustness (c-CRAB's strongest categories, verifiable from the diff alone).
   **Drop:** performance bugs (**0.0% recall for 4 of 5 models** — N+1 and unbounded queries; route to deterministic/AST tooling instead), best-practice (0.0–6.7%), and design/maintainability/documentation (c-CRAB 7.9–27.0%, needs repo context the light tier will not have).
4. **Prompt techniques that hold signal** (widely reported, **effect sizes unquantified — treat as practitioner consensus, not measurement**): severity floors ("critical/high only", "a missing JSDoc is never P0/P1"); requiring a **concrete triggering input/failure scenario** before a finding is allowed; requiring file:line citation; explicitly permitting **zero findings** as a correct outcome; repo rule files (`.cursor/BUGBOT.md`, `copilot-instructions.md`, `CLAUDE.md`, `.coderabbit.yaml`); Claude Code's explicit skip-list (pre-existing issues, linter-catchable style, lint-ignored code) ([Ionix](https://www.ionix.io/blog/we-built-an-ai-pr-reviewer/), [Graphite prompt guide](https://graphite.com/guides/effective-prompt-engineering-ai-code-reviews)).
5. **Output format has a measured effect.** Inline code suggestions were **the strongest predictor of comment resolution** across 54,791 AI comments; long/complex comments resolved less often ([arXiv 2607.21997](https://arxiv.org/html/2607.21997v1)). Claude Code caps committable suggestions at ≤5 lines.
6. **Latency:** PR-Agent ~30s; Copilot ~30s; Bugbot median ~90s (>90% under 3 min) after its June 2026 rework. **No source links latency to whether developers act on comments** — the resolution study ties resolution to content/format, not speed.
7. **Where light demonstrably misses:** anything cross-file or repo-convention-dependent (c-CRAB's weak categories), performance bugs (universal blind spot at every tier), and **anything on a large diff** — the F1 collapse is not a model-tier problem, it hits cheap and expensive models alike.

### Published SIZE/RISK routing rules

- **Qodo's adaptive router** ([blog](https://www.qodo.ai/blog/building-an-adaptive-router-for-code-review-depth/)) — four tiers: **Fast** (single lightweight pass), **Balanced** (one pass on the benchmark-leading model, default), **Deep** (multiple passes across different models), **Auto**. The objective is explicitly **max(F1 − λ·cost)**. The primary routing signal is **hunk count (contiguous change blocks), not raw line count**, refined by an LLM semantic classifier scoring **logic complexity, change dispersion, uncertainty, and blast radius** — with the asymmetry that **uncertainty pushes toward deeper review, never away**. Deep fires only when a diff clears two minimum gates (changed lines AND hunk count). Measured: **−21% model cost, −30% tokens, −27% average runtime, −12% p90 runtime, matching all-Deep F1.** Exact numeric thresholds are **not published**.
- **Meta RADAR's Diff Risk Score** — an ML percentile gate; relaxing 25th → 50th percentile raised approve rate to 60.31% without safety degradation, i.e. **the threshold is a tunable dial with a measured safety curve**. **The DRS's actual features and training procedure are not disclosed — UNVERIFIED** beyond "optimized for high recall at a given flagged percentage" ([arXiv 2605.30208](https://arxiv.org/abs/2605.30208)).
- **A community two-tier gate with explicit weights** — path-risk hit = **5 pts** each, content-signal hit (e.g. a `subprocess` call) = **3 pts** each, size penalty = **1 pt per 100 changed lines**, escalate to the strong model at **≥5 points**; the author stresses these are tunable starting weights, not constants ([DEV: route AI code reviews by risk](https://dev.to/techpy_768/route-your-ai-code-reviews-by-risk-a-two-tier-gate-that-spends-strong-models-only-on-scary-diffs-228o)).
- **Product effort tiers, all qualitative:** Bugbot Low/Default/High/Smart (one unconfirmed snippet: Default 0.7 vs High 0.95 bugs/run); Copilot Lite vs Balanced ("higher-reasoning model" for complex/security-sensitive/cross-service changes — model and cost undisclosed); Greptile standard (1 credit) vs deep "T-Rex" (3 credits, tied to an unexplained **"Runtime Validation"** beta that may be execution-based).
- **File-count heuristics:** Propel Code's buckets (1–4 files high usefulness, 5–8 moderate, 9–15 usefulness drops, 16+ high risk of shallow review) — but the page contains **no actual numeric data despite its title; qualitative only, UNVERIFIED**.
- **Academic alternatives:** just-in-time defect prediction (DeepJIT, CC2Vec) over diff/commit representations; Nagappan & Ball's relative code churn; hotspot files, historical defect density, dependency sensitivity, import-graph blast radius. No canonical published routing model beyond RADAR was found.

**What the evidence actually supports as a routing rule:** route on **hunk count and dispersion first** (Qodo), with **path sensitivity and blast radius as forcing overrides** (Qodo's classifier, the community gate's 5-pt path weight, RADAR's SOX/open-source metadata gating), and treat **uncertainty as a one-way escalation**. Route on raw line count only as a coarse size penalty — and note that above ~150 lines, *no* tier performs well, so the correct response to a very large diff is **decomposition before review**, not merely a heavier model.

## Recurring, failing, and novel techniques

**Recurring across the systems that report working:**
- Two-stage find-then-verify (BitsAI-CR, Refute-or-Promote, Ellipsis, Qodo's judge, Anthropic's filter pass, CodeMender).
- A hard severity floor and an explicit *exclusion* list of noise categories (Claude Code's skip-list, Anthropic security-review's excluded classes, Codex's P0/P1-only, Copilot's High/Medium/Low).
- Repo rule files as the cheapest context lever, supported at every vendor.
- Incremental/delta review — only what changed since the last pass (Bugbot, calimero).
- Dedupe against existing and prior comments before posting.
- Structured output with file:line and an evidence field; inline suggestions where possible (the one format choice with measured resolution impact).

**Reported to FAIL:**
- **Recall-first, precision-last.** curl's bounty confirmed-rate fell below 5% and the programme closed. Vendor benchmarks that score recall while excluding false positives (Greptile's 82%) reproduce at 45% under independent re-run.
- **Nitpick floods and "confidently wrong" comments** — 21% nitpicks + 15% noise + 13% wrong assumptions in the Lychee audit; practitioners describe tuning out once noise accumulates.
- **Naive model ensembling** — measurably *lowered* F1 (0.365 → 0.30–0.33).
- **Unanimity as a confidence signal** — Refute-or-Promote found ten agents unanimously endorsing a nonexistent vulnerability; unanimity is "a low-signal event" because models share priors.
- **Self-reported confidence as a threshold.** Research finds LLM self-assessment poorly calibrated (49–54% accuracy, worse than perplexity thresholding; systematic under-confidence that hedges equally on correct and hallucinated answers) ([arXiv 2608.10008](https://arxiv.org/html/2608.10008), [arXiv 2606.31159](https://arxiv.org/html/2606.31159v1)) — yet Anthropic's security filter thresholds on exactly this, **and defaults to maximum confidence on API failure**.
- **Filters that silently die.** `claude-code-security-review`'s FP filter has been broken since Feb 2026 on a hardcoded retired model — a live demonstration that a verification stage must report its own failure, never fail open.
- **Synthetic-bug evaluation.** Injected-mutation benchmarks overstate capability by **92–99%** versus real PRs; DeepSource criticises Qodo's benchmark on exactly this ground.
- **Coverage-maximizing without precision** — raising % of PRs reviewed without precision increased dismissed comments and code instability ([TianPan.co](https://tianpan.co/blog/2026-05-05-llm-code-review-production-diff-pipeline)).

**Genuinely novel:**
- **Context-asymmetric adversaries** — refuters who see only the claim, never the reasoning, to block anchoring (Refute-or-Promote).
- **Cross-model-family critics** — a different vendor's model as the last gate, catching errors in 16% of same-family-approved fixes.
- **Executable tests derived from human review comments** as an objective oracle, validated by an independent agent fixing from the comment alone (c-CRAB).
- **Generated verification scripts run in a per-PR sandbox** to falsify the reviewer's own comments (CodeRabbit).
- **Risk-history lookback on the *author*** — RADAR's 60-day per-bot PI/revert/rejection rates plus daily volume caps: routing on who/what produced the diff, not only on the diff.
- **An explicit F1 − λ·cost routing objective** with hunk count as the primary signal and uncertainty as a one-way escalation (Qodo).
- **Symbolic verification of LLM findings** — LLM4PFA's Z3 SMT path-feasibility check as the filter.
- **"Outdated Rate"** — ByteDance measuring whether a comment's target code was subsequently changed, as a continuous acceptance proxy driving a data flywheel.
