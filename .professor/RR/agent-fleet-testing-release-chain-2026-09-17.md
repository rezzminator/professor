# RR — How do Professor/pfm's nearest neighbours test and gate releases?

Question: Projects close to Professor/pfm — a Go CLI + daemon that spawns and manages fleets of AI coding-agent sessions (Claude Code, OpenAI Codex CLI, OpenCode) inside tmux, installs hooks/commands/skills into those tools' config dirs across multiple accounts, serves MCP tools, and scaffolds a framework into adopter repos — how do they and their nearest neighbours test and keep reliability across their release chain? Look at: Claude Code, Codex CLI, OpenCode, aider, Cline/Roo, Goose, agent orchestrators and multi-agent runners (e.g. claude-squad, tmux-based agent managers, 'agent fleet' tools), MCP server frameworks, dotfile/install managers that write into user config dirs (chezmoi, Homebrew, mise), and tmux-driving tools (tmuxinator, zellij) — for each: unit vs integration split, how they fake the terminal/tmux/process/network, hermetic e2e (testscript, expect/pty harnesses, container-based), what gates a release (CI matrix on darwin+linux, nightly live runs against real APIs, canary channels), how they handle flaky tests and known gaps, and any public post-mortems on releases that broke users' configs or sessions. Return per project: what they do, with source links (repos' CI configs, CONTRIBUTING/testing docs, blog posts, issues, post-mortems), then the patterns worth adopting and the ones to avoid, and open questions.

---

## Answer

Nobody in this neighbourhood has solved pfm's exact problem, but the shape of the answer is consistent: **the merge gate is hermetic and fixture-driven — not one of the six CI configs read hits a real LLM API — and the only project that seriously tests the "writes into a user's HOME" problem is chezmoi**, whose four-tier ladder (unit → `go-vfs` filesystem mocking → `testscript`/txtar e2e with a fake HOME → Docker/Vagrant/GHA-Windows OS sweep) is the single closest template for pfm. The terminal layer is where everyone is weakest: zellij is the lone project that drives a real terminal end-to-end (binary in Docker, driven over SSH, output diffed against snapshots), while claude-squad — the closest structural analogue to pfm — ships no tests for its tmux layer at all.

## Per project

### OpenAI Codex CLI (openai/codex, Rust) — integration-first, mocked SSE, snapshot-gated TUI

`AGENTS.md` states the doctrine outright: "prefer integration tests over unit tests. Integration tests are under `core/suite` and use `test_codex`"; unit tests, when needed, live in dedicated `*_tests.rs` files, and everything runs through `just test`, never bare `cargo test`. The model layer is faked with a mounted SSE mock server (`responses::mount_sse_once(&server, responses::sse(vec![...]))`), and the TUI is locked down with `insta` snapshots in `codex-rs/tui` — "any change that affects user-visible UI... must include corresponding insta snapshot coverage." Cross-OS hermeticity is implied by `TestCodexBuilder::build_with_auto_env()` for "foreign app/exec OSes." No PTY harness is mentioned. The CI matrix, release/canary channel, and flaky-test policy are **not documented on that page** — unverified. ([openai/codex AGENTS.md](https://github.com/openai/codex/blob/main/AGENTS.md))

### OpenCode (sst/opencode, TypeScript) — two-OS CI, Playwright e2e, zero provider secrets

`test.yml` triggers on push to `dev`, PRs, and `workflow_dispatch`, running on Blacksmith-hosted `blacksmith-4vcpu-ubuntu-2404` and `blacksmith-4vcpu-windows-2025` — **no macOS leg**. Two jobs: a unit job (`bun turbo test`, plus Linux-only `bun run check:generated` and `bun run test:httpapi`) and an e2e job (`bunx playwright install chromium`, then `bun --cwd packages/app test:e2e:local`). The only secret referenced is `GITHUB_TOKEN` — no provider API keys, so the suite runs on fixtures/mocks. `fail-fast: false` keeps both OS legs independent; there is no retry, no `continue-on-error`, and no publish logic in this file. ([raw test.yml](https://raw.githubusercontent.com/sst/opencode/dev/.github/workflows/test.yml)) The repo carries ~27 workflows including `publish.yml`, `publish-vscode.yml`, `containers.yml`, `nix-eval.yml` ([workflows listing](https://github.com/sst/opencode/tree/dev/.github/workflows)) — their channel semantics (stable vs canary/nightly) were **not read** and remain unverified.

### Goose (block/goose, Rust + Electron) — strict lint/test gate, prose-only contributor doc

`ci.yml` gates `push`, `pull_request`, `merge_group`, and `workflow_dispatch` on `main`: mostly `ubuntu-latest`, with `windows-latest` for `rust-build-windows`/`desktop-updater-install` and `macos-latest` **only for `desktop-lint`**. Jobs run `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test --locked` (with a scenario-test suite forced to `--jobs 1`), `pnpm run lint:check` / `test:run` for the Electron app, and schema/docs consistency checks. No secrets or provider keys appear (only a hardcoded `gnome-keyring-daemon` dummy password); a `paths-filter` step skips the Rust/desktop jobs entirely on docs-only PRs; `fail-fast: false` on the TLS/roaming build matrix. No release, canary, or tag trigger lives in this file. ([raw ci.yml](https://raw.githubusercontent.com/block/goose/main/.github/workflows/ci.yml)) Its `CONTRIBUTING.md` is a workflow/triage doc, not a testing-architecture doc — it only asks PRs to state how a "verification plan was carried out" and, for agent-loop changes, "how parity between the two paths was verified"; **no public testing docs found** there for the unit/integration split, mocking, PTY strategy, or release channels. ([block/goose CONTRIBUTING.md](https://github.com/block/goose/blob/main/CONTRIBUTING.md)) A `canary.yml` is referenced as existing but was **not fetched** — goose's canary channel is unverified.

### claude-squad (smtg-ai/claude-squad, Go + tmux + git worktrees) — the closest analogue, and the thinnest testing

tmux is driven for real, with no visible abstraction or mock seam; the public repo listing shows **no `*_test.go` files and no `tests/`/`testdata/` directory** — i.e. **no terminal-layer tests found**. ([smtg-ai/claude-squad](https://github.com/smtg-ai/claude-squad)) Its `build.yml` runs entirely on `ubuntu-latest`, cross-compiling Go 1.25.8 across `GOOS: [linux, darwin, windows] × GOARCH: [amd64, arm64]` (excluding windows/arm64), running `go test -v ./...` then `go build`, uploading artifacts with 7-day retention; triggers are push/PR to `main` filtered to Go files. No secrets, no LLM calls, no retry/`continue-on-error`, and no release trigger in this file. ([raw build.yml](https://raw.githubusercontent.com/smtg-ai/claude-squad/main/.github/workflows/build.yml)) Its release/distribution mechanism was not located — unverified.

### zellij — the only real terminal e2e in the set

`CONTRIBUTING.md` documents `cargo xtask test` for unit/integration plus a dedicated e2e suite that runs the **actual zellij binary inside a Docker container**, connects over SSH, sends commands, and diffs output against predefined snapshots — `docker compose up -d`, then `cargo xtask ci e2e --build` / `cargo xtask ci e2e --test`. A `--debug` flag logs the raw bytes received over the pty. The CI trigger/schedule for those e2e jobs was not read — unverified. ([zellij CONTRIBUTING.md](https://github.com/zellij-org/zellij/blob/main/CONTRIBUTING.md))

### tmuxinator — **no public testing docs found** (not retrieved within budget; any claim about its suite is unverified)

### Charm bubbletea / teatest — **not fetched**; the golden-file-with-`-update` model is general knowledge only and is marked **unverified** pending [charmbracelet/x/exp/teatest](https://github.com/charmbracelet/x/tree/main/exp/teatest)

### testscript (rogpeppe/go-internal) — the hermeticity mechanics, confirmed

Tests isolate the environment by pointing `HOME`/`XDG_DATA_HOME` at the per-test `$WORK` dir in a `Setup` callback, and `testscript.Main` puts a temp bin dir (holding the binary under test) first on `PATH` so no system binary leaks in. Fixtures are txtar: script commands (`exec`, `stdout '^pattern$'`, `cmp stdout want`, `stderr`, `!` negation) followed by `-- filename --` sections extracted into `$WORK`; commands are registered in `TestMain` via `testscript.Main(m, map[string]func(){...})` and dispatched by matching `os.Args[0]`. The source is silent on `UPDATE_SCRIPTS` golden regeneration and on how `rsc.io/script` differs — both gaps. ([rednafi.com/go/testscript-cli](https://rednafi.com/go/testscript-cli/))

### chezmoi (twpayne/chezmoi, Go) — the template for writing into a user's HOME

Four tiers: plain Go `testing` + `alecthomas/assert/v2` unit tests in `internal/chezmoi/*_test.go`; filesystem-integration tests on `twpayne/go-vfs/v5` that exercise FS logic without touching a real HOME; high-level e2e via `rogpeppe/go-internal/testscript` against `.txtar` scripts in `internal/cmd/testdata/scripts/*.txtar`, driven by `internal/cmd/main_test.go`; and an OS layer — **Docker for Linux distros, Vagrant for other OSes, GitHub Actions for Windows**. ([chezmoi testing guide](https://www.chezmoi.io/developer-guide/testing/)) That page documents **no canary/beta channel and no flaky-test quarantine** — gaps, not confirmed absences. Concrete regression: chezmoi ≥2.72 began rejecting every leading-slash pattern in `.chezmoiignore` as an invalid path, breaking existing dotfile setups ([laurigates/dotfiles #377](https://github.com/laurigates/dotfiles/issues/377), [twpayne/chezmoi #4916](https://github.com/twpayne/chezmoi/issues/4916)) — those threads were **not fetched**, so the maintainer resolution is unverified.

### Homebrew — merge-gating documented, everything else deferred

`brew test-bot` is "Homebrew's continuous-integration orchestration command, originally funded by our Kickstarter in 2013," running on GitHub Actions macOS/Linux runners to build bottles and gate PR merges through queued/failed/passed-and-approved status checks. The page explicitly defers the CI matrix, formula-audit specifics, and bottle-build details to the workflow YAML ("the workflow definitions are the authoritative description"), and says nothing about a canary channel, flaky handling, or bottle rollback — for those, effectively **no public testing docs found**. ([docs.brew.sh/BrewTestBot](https://docs.brew.sh/BrewTestBot)) No concrete public incident of a Homebrew release clobbering user state was found in this pass — unverified, not disproven.

### mise (jdx/mise, Rust) — the best-structured e2e of the config-writers

`mise run test:unit` (Cargo, "local parsing and resolution") is split from `mise run test:e2e`, shell tests that spin up **isolated mise config/data/state/working directories per test**, asserted through `e2e/assert.sh` helpers, plus snapshot tests for stable-contract output. CI covers Ubuntu, macOS, and Windows (Windows via a separate PowerShell/Pester runner, `e2e-win/run.ps1`), with `TEST_TRANCHE`/`TEST_TRANCHE_COUNT` partitioning e2e across distributed jobs and a `test:shuffle` order-sensitivity check. Releases are cut automatically by `release-plz` off conventional commits, with **no documented canary/nightly/beta channel** and no explicit flaky quarantine. ([mise contributing guide](https://mise.jdx.dev/contributing.html)) No rolled-back mise release was found — unverified.

### aider (Aider-AI/aider, Python) — one pytest suite, benchmark not shown to gate

Everything runs through pytest (`pytest`, or `pytest tests/basic/test_coder.py`); `CONTRIBUTING.md` draws **no unit/integration distinction** and only asks contributors to "write appropriate tests to maintain code coverage." The benchmark harness is invited as a community contribution ("Contributions of LLM benchmark results are welcome!") — no language ties leaderboard scores to a release go/no-go. ([Aider CONTRIBUTING.md](https://github.com/Aider-AI/aider/blob/main/CONTRIBUTING.md))

### Cline (TypeScript, VS Code) — real e2e, and a repeat config-corruption incident

`CONTRIBUTING.md` documents Playwright-driven e2e simulating user interaction inside VS Code (`bun run test:e2e`, `--debug` for interactive runs), `bun test` for unit/integration, and a mentioned-but-underspecified "mock API server for backend testing"; CI runs tests, lint, and format checks before merge, though the workflow files themselves are not linked, and versioning/changelog curation is explicitly maintainer-owned. ([cline CONTRIBUTING.md](https://github.com/cline/cline/blob/main/CONTRIBUTING.md)) Its Checkpoints feature has repeatedly corrupted users' git repos by renaming `.git` to `.git_disabled` (sometimes creating infinite nested `.git` dirs inside `node_modules`), requiring manual deletion from VS Code's AppData — a long-running string of issues: [#1313](https://github.com/cline/cline/issues/1313), [#4385](https://github.com/cline/cline/issues/4385), [#4388](https://github.com/cline/cline/issues/4388), [#5598](https://github.com/cline/cline/issues/5598), [#9286](https://github.com/cline/cline/issues/9286), [#9590](https://github.com/cline/cline/issues/9590), [#9631](https://github.com/cline/cline/issues/9631). These were surfaced via search, not fetched — the current fix status is **unverified**.

### Roo Code — **no public testing docs found** in this pass; it is widely described as a Cline fork, but shared Playwright/e2e setup is **unverified**

### Claude Code — closed internals, an eval surface for extensions, and a real post-mortem

The public testing surface for extensions is `claude plugin eval`, an ablation-style runner that scores a plugin/skill's contribution by running the same cases with and without it enabled, emitting JSON/HTML reports ([plugin evals docs](https://code.claude.com/docs/en/plugin-evals)) — reported via search summary, **not independently fetched**. A public changelog exists ([changelog](https://code.claude.com/docs/en/changelog)) but was not fetched, so documented rollback/versioning guidance is unverified. The high-signal artifact is Anthropic's published post-mortem, ["An update on recent Claude Code quality reports"](https://www.anthropic.com/engineering/april-23-postmortem), covering three stacked regressions between March 4 and April 20, 2026: reasoning effort silently defaulting from high to medium; a prompt-caching bug that erased reasoning "on every turn" after idle sessions, making Claude "seem forgetful and repetitive"; and a verbosity-limiting system prompt that hurt coding quality despite weeks of internal testing. All three shipped past internal evals because user reports were "challenging to distinguish from normal variation." Fixes landed incrementally (v2.1.101 on April 10, v2.1.116 on April 20), usage limits were reset for all subscribers on April 23 as compensation, and the committed remediations were **soak periods, gradual rollouts, and per-model eval suites**.

### MCP server frameworks — an external conformance judge exists

[modelcontextprotocol/conformance](https://github.com/modelcontextprotocol/conformance) tests client and server implementations against the spec: for servers it connects as an MCP client and runs checks; for clients it starts a test server per scenario. Scenarios live in `src/scenarios/<name>/`, implement a `Scenario` interface (`start()`, `stop()`, `getChecks()`), and register in `src/scenarios/index.ts`, covering client scenarios (initialize, tools-call, auth/basic-dcr) and server scenarios (server-initialize, tools-list, tools-call, resources, prompts); each scenario also emits synthetic **wire-schema checks** validating JSON-RPC messages against the spec's JSON schema, with results written to `results/` as `checks.json`/`stdout.txt`/`stderr.txt`, across multiple spec versions. Its `sdk` subcommand is the cross-SDK CI mechanism — it clones an SDK repo at a ref, builds it, and runs the local conformance build against it (`npm start -- sdk typescript-sdk@abc123f --mode server`), with per-SDK build config in `src/sdk-runner/known-sdks.ts`; a `tier-check` command exits nonzero when any scored scenario fails. For the **Go SDK**, `no public testing docs found` for the specifics: [modelcontextprotocol/go-sdk](https://github.com/modelcontextprotocol/go-sdk) shows a `conformance/` directory and a `copyright_test.go`, but in-memory transport round-trips, table tests, and how `.github/workflows` wires conformance into CI are all **unverified**. [MCP Inspector](https://github.com/modelcontextprotocol/inspector) documents `npx @modelcontextprotocol/inspector --cli` as "a scriptable command-line client for automation, CI, and fast agent feedback loops," with a connect → list → call → assert smoke workflow using `--format json` + `jq` and an "exit-code map" for CI — the actual exit codes live in `docs/cli-smoke-testing.md`, unfetched and unverified.

## Patterns worth adopting

1. **Integration-first with a named harness builder.** Codex's "prefer integration tests, use `test_codex`" plus a single entrypoint (`just test`, never bare `cargo test`) is the posture pfm wants: one builder that stands up a whole fake install so tests read as scenarios, not as unit plumbing. ([codex AGENTS.md](https://github.com/openai/codex/blob/main/AGENTS.md))
2. **chezmoi's four-tier ladder is pfm's blueprint**, because it is the same problem — unit → virtual-filesystem integration (`go-vfs`) → `testscript`/txtar e2e under a fake HOME → Docker/Vagrant/Windows-GHA OS sweep. pfm writes into `~/.claude/{agents,commands,skills}`, `~/.codex/agents/`, and adopter repos; that entire surface belongs in txtar scripts with `HOME`/`XDG_*` redirected per test. ([chezmoi testing](https://www.chezmoi.io/developer-guide/testing/), [testscript mechanics](https://rednafi.com/go/testscript-cli/))
3. **Zero provider secrets in the merge gate.** All three agent-runner CI configs actually read (opencode, goose, claude-squad) gate purely on fixtures and local builds; none reference an LLM key. Live-API runs, if wanted, belong in a separate scheduled lane whose failure never blocks a merge.
4. **Per-test isolated config/data/state/working dirs plus an order-shuffle check.** mise's `test:e2e` gives every test its own four directories and runs a `test:shuffle` job to catch inter-test state leakage — exactly the failure mode of a daemon that writes global config across multiple accounts. ([mise contributing](https://mise.jdx.dev/contributing.html))
5. **Shard slow e2e explicitly.** `TEST_TRANCHE`/`TEST_TRANCHE_COUNT` partitioning keeps a growing e2e suite inside CI time without deleting coverage. ([mise](https://mise.jdx.dev/contributing.html))
6. **Serialize the suites that contend on a shared resource.** goose forces its scenario tests to `--jobs 1`; pfm's tmux-server and daemon-socket tests need the same explicit serialization rather than hoping for the best. ([goose ci.yml](https://raw.githubusercontent.com/block/goose/main/.github/workflows/ci.yml))
7. **Snapshot the user-visible surface, with a mandate.** Codex requires insta coverage for any UI-affecting change; zellij diffs real terminal output against snapshots. For pfm the analogue is golden-file coverage of every rendered status/TUI frame and every generated config file.
8. **Drive the real terminal in a container for e2e, keep a seam for unit tests.** zellij's binary-in-Docker-over-SSH-with-snapshot-diff is the proven shape for a tmux-driving tool, and its `--debug` raw-pty-byte log is the debugging affordance that makes such tests maintainable. ([zellij CONTRIBUTING](https://github.com/zellij-org/zellij/blob/main/CONTRIBUTING.md))
9. **Let an external judge score the MCP surface.** Wire `modelcontextprotocol/conformance` (and Inspector `--cli` as a smoke gate with exit codes) against pfm's MCP server — an independent implementation of the spec is a far better judge than self-written assertions.
10. **Soak + gradual rollout + per-surface eval suites**, Anthropic's own stated remediations after three regressions shipped past internal evals. The deeper lesson is the diagnostic one: degradation reports were "challenging to distinguish from normal variation," so a release chain needs a *deterministic* signal, not user sentiment. ([Anthropic post-mortem](https://www.anthropic.com/engineering/april-23-postmortem))
11. **Destructive operations on user state need their own test class.** Cline's Checkpoints renamed users' `.git` to `.git_disabled` across a multi-year issue trail; any pfm code that moves, renames, or rewrites an adopter's config needs explicit refusal-path tests, not just happy-path ones. (issue trail above; current status unverified)

## Patterns to avoid

- **Cross-compile as a stand-in for coverage.** claude-squad cross-builds six OS/arch targets but runs `go test` only on `ubuntu-latest` — the darwin and windows binaries are built, never exercised. ([build.yml](https://raw.githubusercontent.com/smtg-ai/claude-squad/main/.github/workflows/build.yml))
- **Build-only CI for a tool whose whole value is session management.** claude-squad drives tmux for real with no test seam and no terminal-layer tests; the git-worktree isolation that is its core promise has no visible regression coverage.
- **A prose "verification plan" in CONTRIBUTING instead of an enforced suite.** goose asks PRs to describe how parity "was verified" — a gate that reports fine whether or not the verification happened.
- **Benchmarks as decoration.** aider's leaderboard is a community contribution with no documented link to a release decision; a number that never blocks is not a gate. ([aider CONTRIBUTING](https://github.com/Aider-AI/aider/blob/main/CONTRIBUTING.md))
- **Docs-only path filters that also skip consistency gates.** goose's `paths-filter` skipping Rust/desktop jobs on docs-only PRs is fine *until* the skipped job is the schema↔docs consistency check — then the filter hides exactly the failure the PR can cause.
- **Fully automated release with no canary, for a tool that writes user config.** mise cuts releases from conventional commits via `release-plz` with no documented beta channel; chezmoi ≥2.72 silently broke every leading-slash `.chezmoiignore` pattern. A staged channel is the difference between one reporter and every user.
- **Documentation that defers to YAML as "authoritative."** Homebrew's own CI doc points at workflow files for the real behaviour — meaning the doc cannot be trusted as the specification of the gate.
- **A single undifferentiated pytest/go-test pile.** aider's `tests/basic/` conflates layers; without a unit/integration split there is no fast lane and no way to say which tier a regression escaped.
