# The laws — honesty over time, and what a test may not be

This file covers Laws 19–31 of [`/quality:integration-suite`](../../../templates/global/commands/quality/integration-suite.md), one section each: how the ledgers, the budgets and the gates stay true after the designers have left, and the shapes that look like tests and test nothing. [laws.md](laws.md) covers Laws 1–18 and holds the [Sources](laws.md#sources) table both files cite. Every section gives the rule, the failure it prevents, why it takes this shape and not a nearby one, and how it is checked. The laws hold for any project in any language.

## Law 19 — a known issue is fixed

**Rule:** The known-gap ledger, `gaps.tsv` (`row⇥landscape_id⇥why⇥owner⇥expires`), an owner-owned path, holds only what cannot be fixed in this repository: an upstream defect or absent hardware. Every entry's `why` carries an external reference — an upstream issue link or `hardware:<identifier>` — and a `why` that names a file in this repository, or any of the project's own identifiers (its repository names, its issue-tracker hosts, its internal domains, listed as a design input), fails the check. Every entry carries an owner from `roster.txt` and an expiry. Each of three states is red: an expired entry, an entry without an expiry, and a listed row that passes. The ledger's healthy state is empty. A fix flips its row to a real assertion and deletes the entry in the same commit. Every arm of a beat is its own beat, so a `known` mark never excuses more than one verdict. An exemption or allow list anywhere in the suite anchors on a signature (§ Terms), never on a line number.

**Prevents.** The ledger becoming a graveyard, and a red gate parked as furniture. A list of known issues records a decision not to fix, made invisibly. It grows because adding a row is always cheaper than fixing the defect, and under pressure it takes an in-repository production defect with a placeholder owner, or a link to the project's own tracker, so the suite can report green. A listed row that passes means the ledger lies: the row is excused while it is fine, and it will stay excused when it breaks again. A `known` mark that covers a whole beat forces beat splits to excuse one arm. A line-anchored exemption breaks on every unrelated edit nearby and is re-anchored without being re-verified.

**Why this shape.** Each clause closes one way the list rots:

- **Unfixable-here only, proven by the reference.** Deferring is not an option: anything the repository can fix, it fixes. The external reference is the mechanical test of "cannot be fixed here"; a placeholder owner, a file path and the project's own tracker are the three shapes an in-repository defect takes when it is parked, and the own-identifier list is what lets a check tell the last one from a real upstream link. Reading the ledger at the merge base is what stops a fourth shape, an entry written in the commit that needs it (integration-suite.md § The threat model).
- **An expiry even for upstream defects.** Upstream moves, and a date forces the entry to be looked at again.
- **Listed-and-passing is red.** This is the strict expected-failure rule: the ledger reports its own staleness.
- **Healthy state empty.** Every entry shows as debt, never as furniture.
- **Same-commit flip.** Without it, the window between the fix and the ledger edit is a window where a listed row passes, which the previous clause makes red.
- **Signature anchors.** A signature survives the edits around it and the file's rename; a line number does not.

**Checked by.** `gaps`: expired, no expiry, `why` without an external reference or naming an own identifier or a repository file, owner off the roster; the runner's red on a listed row that passes; `refused-shapes`, the Line-anchored exemption row.

**Evidence.** A strict expected-failure marker is the one mechanism the research found that fails the build when a listed gap passes. Chromium's `TestExpectations` requires a bug link but has no expiry, and its stale rows are moved by hand into a separate file.

## Law 20 — speed is designed, and budgets ratchet from a soak

**Rule:** The design states, before the build, the target wall for the full sequence, for each lane and for each tier, and every beat and hermetic row carries `cost_ms:`, its paper estimate — actor provisioning, process boots, waits, third-party round trips; the `budgets` check sums the estimates per lane and along the critical path against the target on every commit. The design also states the scheduling and the per-change run policy: the lanes touching the changed files, from their checkpoints, then the touched lane alone; the full sequence at each close and at release. The runner prints a wall breakdown per row and per lane with the idle gaps between rows. Speed is measured against the target after the first two lanes, before more are written. Budgets are enforced at close per lane, per sequence and per tier, pinned in `budgets.tsv` (`key⇥budget_ms⇥run_ids⇥load`, the key a lane, `tier-unit` or `tier-hermetic`) as the maximum of at least three green canonical runs on one root hash (a tier key's on one subject) plus the fixed headroom the Speed section declares, named by their run ids so the check recomputes the pin from the ledgers; the pinned sequence budget may not exceed the Speed target. A budget ratchets down only, except that a commit adding rows to a key may raise that key's budget by at most the added rows' own maximum `wall_ms` in the named runs. The check refuses a pin from fewer than three runs and a key whose slowest run exceeds twice its median, which is a bimodal key and a defect to diagnose first. A per-row number is a hang guard and never fails a passing run. At close an unpinned key is `BUDGET-UNPINNED`; on every other commit the check lists unpinned keys and does not fail on them. With no live tier, close is one green run of the blocking commands on the merge subject, and three only in the landing that pins a tier budget.

**Prevents.** Three failures:

- **Speed discovered after the build.** Wall time, the critical path and the per-change policy are not designed, so the build runs full suites around small edits, waits in fixed batches, starts the late lanes only after every early one, and nobody measures where the minutes go until the suite is the bottleneck. A Speed section with a target and no costs is the same discovery deferred, and a sequence pinned at three times its target closes green unless the pin is held to the target.
- **Suite creep.** Nobody decides to make a suite slow. It gains a few seconds per change until people stop running it. A ratchet turns creep into a red at the change that caused it, while that change is still small enough to fix — unless a trivial added row is allowed to absorb the whole lane's creep in one re-pin.
- **The moving target, and the self-declared soak.** A budget pinned from one run at beat granularity, with a multiplier, breaches on the next noisy run, is re-pinned, and breaches again; a functionally green suite is blocked by its own timing rows, and a bimodal beat is pinned instead of diagnosed. A budgets file that says "three runs" without naming them was pinned from whatever the author had.

**Why this shape.** Each clause answers one way speed fails:

- **Designed before the build, summed by a check, and held at close.** The cost of Law 6's sequence is the sum of its lanes; the design pays that cost on paper first, so the build knows its target and the lanes are cut to meet it; `cost_ms:` is what turns the paper into a number a check can compare, and the target bound on the pin is what keeps the paper honest once the walls are measured.
- **The maximum of three, plus headroom, not the median.** A budget is a ceiling. A ceiling at the median breaches on every slower-than-typical run; the maximum of a soak is the observed worst case, and a fixed headroom absorbs load noise without inviting drift. One run is noise (a busy machine, a cold cache); three green runs make a soak, and a number is trusted only once it repeats — and only once the check can find the runs.
- **Down only, with one bounded way up.** A budget that the change exceeding it may raise is not a budget; a budget that cannot rise when a lane gains rows is a lane that cannot grow, which contradicts the one-commit rule for a new capability. The added rows' own measured wall is the one legitimate increment, and bounding the raise by it is what stops the increment from carrying the rest of the lane's creep.
- **Per key, never per row.** A row's time is dominated by the state it ran on and the load beside it; a lane's or a tier's time averages that out, and keying the tiers gives a project without lanes a budget at all. The per-row guard catches a hang, which is the one per-row timing that is a defect.
- **Bimodal refused.** A key whose slowest run is twice its median is waiting on something — a real interval, a visibility window, a consuming probe (Law 16) — and pinning it hides the wait.
- **Unpinned fails at close, not on every commit; one green run without lanes.** A lane that has just been written cannot have three green sequences; failing every commit until it does would make the rule the first one switched off, and tripling a unit suite at every landing, with nothing to pin, is the same cost with no soak to buy.
- **The load recorded with the number.** A time measured beside another build cannot be compared with one measured on an idle machine.

**Checked by.** `budgets`: plain mode, the paper cost above the target and the unpinned keys listed; `--close`, `BUDGET-UNPINNED`, fewer than three named green canonical runs on one root hash or subject, the recomputed maximum plus headroom above the pin, the slowest run over twice the median, the pinned sequence budget above the Speed target, a pin raised by more than the added rows' own maximum `wall_ms`; the runner's ledger carries the wall breakdown.

**Evidence.** In the literature, the ten-minute build is a guideline, not a mechanism. No source the research found documents an automated suite-time ratchet, so the numbers are measured on the project's own machine. The soak clause follows a published post-mortem's remediation of soak periods before trusting a change.

## Law 21 — a flaky test is a defect

**Rule:** A flaky test is a defect with an owner, never a quarantine. A flake is a row that failed and passed on the same merge subject, dirty hash and root hash; the runner records every such row into `flakes.tsv` (`row⇥tree⇥dirty⇥root⇥first_seen⇥owner⇥expires`) with its owner, and the close gate recomputes the flakes from the run ledgers on the merge subject, never from that file, and fails while one exists. A retry or rerun setting in a runner configuration applies only to tests named in the ledger, every attempt is its own run-ledger row, and flakiness is tracked per configuration. The unit and hermetic tiers run in shuffled order in one scheduled leg, and the shuffled ledger must exist within the schedule window; a failure that appears only under shuffle is a shared-state defect. The live tier is never shuffled — its order is canonical and its beats carry state — and its order probe is Law 7's solo run from a fresh root.

**Prevents.** Quarantine as a way of discarding signal, and "green on rerun" as a verdict. A flaky test is often a real intermittent bug in the product or a real race in the harness, and hiding the test hides the bug. Blanket retries do the same automatically: a retry setting in the runner's configuration makes every flake, and every real race, invisible at once, and never reaches any ledger. A red recorded as "contention", "pre-existing" or "isolated pass" and left in place is the same discard by hand, and every full-run-only red of that kind turns out at close to be a race nobody diagnosed. A shuffle leg that exists on paper and never runs hides order dependence forever.

**Why this shape.** Each clause answers one way flakiness hides:

- **The flakes are recomputed from the run ledgers, never read from a file anyone can clear, by a definition a check can apply.** Two verdicts on one subject, dirty hash and root are the same test on the same world; a red then a fix then a green is two worlds, and recording that as a flake would fill the ledger with every ordinary fix and invite clearing it by hand.
- **Close fails while a flake exists.** The flake stays visible, named and owned while it waits for its fix, and the suite cannot close around it.
- **Retry only what is already ledgered, and only where the configuration says so.** A retry on an unledgered test is a quarantine with no row, and the runner's own retry setting is where that quarantine hides.
- **Per configuration.** A test that flakes under a race detector or on one architecture does not flake everywhere, and a global mark hides it where it is stable.
- **A shuffled order, proven to have run, where order is not the contract.** Order dependence is the one flake class that a deterministic run can hide forever: a run that always uses the same order never trips it, and a scheduled leg is only evidence when its ledger exists. The live tier's order is the contract, so shuffling it would test nothing; the solo run is its probe.
- **One scheduled leg, not every run.** A shuffled commit gate would go red for reasons unrelated to the change, which Law 1 forbids.
- **A shuffle-only failure is a shared-state defect by definition.** The test depends on state another test left behind.

**Checked by.** `flakes` at close: a row the run ledgers show failing and passing on the merge subject with one dirty hash and root; no shuffled-order ledger for the unit or hermetic tier within the schedule window; a retry or rerun setting in a runner configuration outside tests named in the ledger.

**Evidence.** Luo et al. (FSE 2014) found the top causes of flakiness to be async wait (45 %), concurrency (20 %) and order dependency (12 %). In the same study, 24 % of flaky-test fixes changed the code under test, and 94 % of those were real bugs. Google reruns only tests already marked flaky and tracks flakiness per configuration. A neighbour project runs an order-shuffle job to catch state leaking between tests.

## Law 22 — a verdict is bound to the tree it ran on

**Rule:** Every run ledger records the tree it ran on — the version-control system's staged-tree hash over the hash subject, which is every tracked path minus those `exclusions.txt` tags `hash` (the ledgers, the documentation) — and a dirty hash covering the tracked diff plus every untracked, non-ignored file under the same subject; both are taken at the start of the run and again at its end. A gate and a merge refuse a ledger whose subject hash differs from the merge subject, whose dirty hash is non-empty, or whose start and end hashes differ; they also refuse a ledger the rows disprove — a `sequence` whose rows overlap across lanes, a `boot: process` whose product records carry the header's `runner_pid`. A bite's red run is verified against its own diff hash, not against a clean tree. A report older than the tree's latest change is not evidence.

**Prevents.** A green credited to a different object than the one merged. The evidence offered for a merge came from a run on a tree with uncommitted deltas, from an untracked runner configuration that changed what ran, from a lockfile or a CI file nobody declared as part of the product, from a sibling's edit landing mid-run after the start hash was taken, or from a report older than the tree's latest red. The ledger then names a beat that exists in no source and lacks two that do, and the merge proceeds on a verdict about something else — or on a header that says "sequence" over rows that ran side by side.

**Why this shape.** The root hash of the environment (Law 7) keys what the product ran *on*; the tree hash keys *what* ran. Both are needed, because a stale root and a stale tree lie in different directions. The subject is everything tracked minus an exclusion list rather than a list of included paths, because an inclusion list is only as complete as someone's memory of what shapes the build — a lockfile bump or a compose file falls outside it — while an exclusion list omits only what cannot change a verdict: the ledgers, so writing one never dirties the tree it describes, and the documentation. Untracked files are in the dirty hash because a new file changes what runs as surely as an edited one. Start and end together are what catch the mid-run edit. The header is self-declared, so the two fields the rows can contradict are checked against the rows. Recording the dirty hash rather than refusing to run keeps the working loop free — a dirty run is fine to learn from, and a bite's run is dirty by design — while making it worthless as merge evidence, which is the only place it does harm.

**Checked by.** `tree` at close: the canonical ledger's subject hash equals the merge subject, its dirty hash is empty, its start and end hashes agree, its rows do not contradict `mode` or `boot`; `bite`: the red run's dirty hash equals the row's `diff_hash`; `observed`, Law 7's two-mode requirement and `retired`'s "passed on this subject" all read ledgers through this binding.

## Law 23 — a check counts only when the blocking gate runs it

**Rule:** The design names the exact blocking command per tier, and every ledger header records the `command:` that produced it. A census lists every file matching a test-name pattern anywhere in the repository, outside the `scope`-tagged paths of `exclusions.txt`, and every file the blocking run's own log shows collected; the sets are equal and each file is collected exactly once. The blocking run's log must show every `CHECK` line of the design's table — the plain checks in the commit job, and in plain mode a close-job log within the schedule window must carry every `--close` line — and every CI step that runs a check blocks; a non-blocking flag on a check step is refused, a CI configuration with no job that invokes `--close` is the plain check's `ERROR`, and a CI configuration or run log the check cannot read is its `ERROR`. A lint rule's wiring is proven only by a bite row whose red run's `command:` is the blocking command.

**Prevents.** Coverage that exists on disk and nowhere in the gate. A self-test suite for the gate's own verdict logic sits in a directory outside the tier's globs, so a census over those globs never misses it; a file is collected by two configurations under two harnesses and is red in one; a scan that would catch a plaintext leak of regulated data is moved into a step that cannot fail the build, or into a job the merge does not require; a close job is never defined, so the close-only checks can never fail a deploy and nothing notices; a rule's wiring is "proven" through a shim CI does not use. Each is a rule that is proven and not enforced.

**Why this shape.** The census is a set comparison the gate can run on itself, so the gap between "written" and "run" is a red line rather than a review question — provided the disk side is every test-shaped file in the repository, not the files the designer expected, and the design's own planted corpora are excluded by name rather than by luck. "Exactly once" matters because a double collection is two verdicts for one file, and the green one gets read. Execution is proven from the blocking run's own log rather than from the CI configuration, because a job can be non-blocking in ways a flag grep cannot see — absent from the required checks, triggered by hand — while a log line either exists or does not; the one thing a log cannot show is a job that was never defined, which is why the plain check reads the CI configuration for the close invocation. The planted violation with the blocking command in its header is the only proof that the wiring reaches the command that blocks.

**Checked by.** `collected`: the repository-wide disk set against the blocking run's collected set, a file collected twice, a `CHECK` line absent from the blocking run's log or no close-job log within the schedule window carrying every `--close` line, a fake with no contract suite collected; `ERROR` when no CI job invokes `--close`; `refused-shapes`, the Fail-open row: a non-blocking flag on a check step; `bite`: a lint rule's red run carries the blocking `command:`.

## Law 24 — a test retires only through a verified successor

**Rule:** A test is deleted only in the commit that installs its verified retirement ledger: `retired.tsv`, one row per assertion of the retired test — `file⇥assertion_signature⇥disposition⇥run_id` — derived by the assertion spelling set from the test's text at the merge base, never per file or per name. The check re-derives the deleted files' assertions from the merge base, drops those whose signatures reappear in files the same commit adds (a move, not a retirement), and requires set equality with the rows added since the merge base. A disposition is `successor:<file:line | row id>`, verified to exist, to have passed in the named run on the merge subject, and to carry the retired assertion's signature — the same subject on the actual side and the same expected literal or code; or `dropped:<refused shape>`, verified against that shape's spelling; or `ruling:<ref_id>`, resolved in `references.tsv`. A row without a verified disposition fails the commit. Tests the design keeps get no row. The old suite is a list of claims to verify, never a source of fixtures or expected values.

**Prevents.** Two opposite failures of a suite replacement:

- **Guards lost silently.** A suite deleted on the assumption that the new one covers it, reconciled afterwards by file names and quoted literals, loses the assertions nobody grepped for: a refusal code, a boundary guard, an attribution line, a retention actor. One of them is the regression the old suite would have caught, and the reviewers cannot close the deletion because they can verify a fraction of the rows within budget. A successor that is any passing line containing the same code, a row pruned from the ledger by hand, and a `dropped:` with no shape behind it are the three ways the same loss survives a ledger.
- **Junk ported as debt.** Once every old scenario is treated as owed coverage, the old suite's worthless rows — shipped-migration replays, source-text pins, tombstones — are rebuilt as new beats and cut again later.

**Why this shape.** The assertion is the unit because it is what a test guards; a file name and a scenario title describe intent, not protection. Re-deriving from the merge base is what makes the ledger complete by construction rather than by diligence, and excusing the signatures that reappear is what keeps a rename or the split Law 31 demands from being billed as a retirement. The subject-and-literal clause is what makes a successor a successor: the same guarded value read from the same thing, somewhere that still runs — a literal alone is reconciliation by grep. The `dropped:` exit is what stops junk from being ported: it names the law under which the assertion tests nothing, and the spelling check keeps it honest. Same commit, because a deletion before the ledger is verified is the silent loss, and a ledger frozen with blank dispositions is no ledger. The old suite is not a fixture source because its fakes and expected values are exactly the guessed and tautological oracles Law 12 refuses; reading it for claims to verify keeps its knowledge, reading it for values imports its faults.

**Checked by.** `retired`: deleted test files since the merge base whose re-derived signatures, minus those that reappear in added files, are not set-equal to the rows added since the merge base; a successor that does not exist, did not pass in the named run on this subject, or differs in subject or literal from the retired signature; a `dropped:` whose shape the assertion does not match; a `ruling:` not in `references.tsv`; `ERROR` when the merge base is unreadable, deletions exist with an empty ledger, or the assertion spelling set is empty.

## Law 25 — the landscape holds only product behaviour

**Rule:** The landscape holds only behaviour a user, an operator or an integration invokes on the running or installed product. Excluded by rule, never mapped: package-manager scripts that build, lint, type-check, format, test, generate or export; CI workflow structure and step names; container build ordering; lockfiles, toolchain and dependency versions; the developer's own gates. Developer tooling is verified by running it as its own CI step. A configuration invariant that matters — a secret roster, no public address, a patch applied before an install — lives in one policy lint over the configuration files, each rule citing a `references.tsv` row and asserting a property (a key present or absent, a pattern absent), never a line's full text, with a planted violation per rule; it is never a test. A version pin lives in the lockfile and a dependency policy, never in a test. The map's names leg reads the built product's own registries — its router, its job registry, its tool list, the help tree of a CLI product — never a package manifest's script list, and in both directions.

**Prevents.** The toolchain becoming the product. An enumeration that reads every named thing as a capability turns each package script into a row, the map gate then demands a beat per row, and a lane beat ends up running the build, the type check and the lint inside the live suite, minutes per run, with a permanently red lint gate parked as a known gap. A test that pins a CI step name or a recipe's text breaks on every edit to CI, and a version pinned in a test disagrees with the lockfile the moment either moves. A gate that only builds is green whether or not the feature works. And a thousand-line pin file relabelled "the policy lint" is the same pins with an exemption.

**Why this shape.** The landscape is the denominator of coverage, so what it admits decides what the suite is for. "Invoked on the running or installed product" is the line because it is what a user can experience: a failing type check is a developer's problem, a failing export is a user's. The exclusion is by rule rather than by judgement because the mechanical enumeration of step 1 has no judgement; the rule is the judgement, written once. The policy lint keeps the configuration invariants that matter, in the one shape (Law 27) that can hold a source invariant honestly; the reference per rule is a row of a file read at the merge base, so a rule cannot cite a reference written for it in the same commit (integration-suite.md § The threat model), and whether a rule asserts a property or pins a line is the reviewer's reading.

**Checked by.** `landscape-scope`: a landscape row whose `op:` matches the exclusion spellings; `refused-shapes`, the Toolchain as product row; `map-names` in both directions; `oracle`: a policy-lint rule without a `references.tsv` source.

## Law 26 — a migration is tested as a mechanism

**Rule:** Beats and tests exercise the migration runner — ledger, checksum, ordering, a half-applied step, a rollback, the second run that changes nothing — with fabricated scratch migrations only, in the scratch-migration directory. The resulting schema is asserted by introspecting a freshly migrated store against the code's own definitions (its enums, its models) as a `source:drift:` row (Law 12), never by replaying a shipped migration file or parsing its text. The upgrade row builds its previous state by running the previous release. A data backfill is proven once at authoring against a synthetic, production-shaped fixture and is not kept as a regression test; a backfill proof that would need production data is a data-handling decision for the owner, never a test. No test names a shipped migration directory or file, carries a parser over migration text, migrates to a named version, seeds rows between two migration runs, or restores a store dump or snapshot outside the root build and the scratch-migration directory.

**Prevents.** Shipped migration content becoming a test subject. A lane that replays a specific shipped migration against seeded predecessor rows and asserts that migration's literals costs a minute per run and proves what was proven the day it shipped — and "migrate to version N, seed, migrate", or "restore last release's dump, migrate", is the same replay with no file name in it. A parser over migration text — a regex over SQL, a simulator that knows one statement and not its inverse, a branch hard-coded to one migration's number — breaks on the next migration's shape and blocks the gate for a reason that is not a defect. A per-file checksum freeze pins history, not behaviour.

**Why this shape.** The runner is the behaviour a user meets — an upgrade that applies cleanly, refuses a corrupt ledger, and does nothing the second time — and a scratch migration can reach every one of its branches without touching a shipped file. The previous release, run, is what an upgrading user actually has; a dump is a frozen copy of one moment of it. Introspection asserts the schema that exists, against the definitions the product compiles, so a drift between code and store is caught without anyone maintaining a hand-copied mirror of a constraint; it is the one legitimate product value on an expected side, which is why it carries the `drift:` source and a two-sided bite. The landscape (step 1) carries one row for the migration mechanism, never one per shipped migration. The backfill fixture is synthetic for the same reason lane fixtures are (Laws 17, 31): a test that needs real rows is a test that moves real data into a test tree, a log and a review, and the shape of production data — its cardinalities, its null patterns, its edge rows — can be fabricated without one real row.

**Checked by.** `refused-shapes`, the Shipped migration content row: a shipped migration directory or file-name pattern, a parser over migration text, a migrate-to-version argument, a seed between two migration runs, or a dump or snapshot restore, in any test file outside the scratch-migration directory.

## Law 27 — a source invariant is a lint rule, never a test

**Rule:** A test never opens a product-tree file — source, configuration, prompt, build output, or any text form of product code (a function's source string, a raw import) — as its subject. An invariant over source — a spelling that must not appear, a symbol that must be absent, a pattern every module must follow — is a lint rule with one planted-violation case per rule, run by the blocking command. An absence is asserted only this way, only when the rule is tagged security or privacy with a `references.tsv` row behind the tag; every other absence — a removed field, a retired file, a dropped integration — is not tested. A behaviour test imports and runs the code. A file the product wrote into the run root is output, not source, and a product whose output is configuration or prompt text pins that output under Law 18. A lint rule's own fixtures and the planted-violation corpora are `scope`-tagged in `exclusions.txt`.

**Prevents.** Two failures:

- **Lint-as-test.** A test that asserts a string is present in a file breaks on a harmless refactor and passes when the behaviour is broken; a test that builds its expected job list by scanning the registration source — or the built bundle, or the function's own source string — is the tautological oracle of Law 12 in another form.
- **Tombstones.** A test that asserts something deleted stays deleted pins history, and the hundreds of them a long-lived tree accumulates are reviewed by nobody, until a deletion is contested because one of them was the only guard on a security absence — which is the one case the rule keeps, in the one shape that can hold it, and with a reference that landed before the tag behind it, so the tag is not self-applied.

**Why this shape.** A lint rule states its invariant once, over the whole tree, with a planted violation that proves it bites (Law 13); a test that reads a file states the same invariant at one path with no proof. "Any text form of product code" is the line because the shape of the fault is reading code as text, whatever path or reflection it arrives by. The security-or-privacy tag is the line for absences because those are the absences whose return is a breach; every other absence is a design decision that a returning symbol re-opens legitimately, and a tag anyone can apply is no line at all. The run-root and output clauses keep the rule from firing on the products whose job is to write configuration, and the exclusion list keeps it from firing on its own corpora.

**Checked by.** `refused-shapes`, the Lint-as-test and Tombstone rows: a file read, a source-reflection call or a raw import over a product-tree path as a test's subject; an assertion that a file does not exist, that a schema lacks a property, or a test title claiming an absence, outside a lint rule tagged security or privacy whose tag cites a `references.tsv` row.

## Law 28 — one contract, one test per tier

**Rule:** A landscape id is mapped to at most one row per tier, except where the map row names the reason: `crossing:` for Law 9's two sides, or `twin:<row>` naming a row at a different tier for Law 3's twin, each asserting what the other cannot; at each tier above the unit tier, one operation has at most one success row and one refusal row besides its `crossing:` rows, and the `crossing:` rows of one id span two lanes or more. Every (row, id) pair in `beats.md` is a map row. Tests that differ only in a literal are one table-driven test. A token-based clone detector runs over the test tree as this suite's own `clones` check, under the test tree's own baseline; test files are not exempt from it. `map-dup` prints `DUPLICATE-CANDIDATES` — tests at one tier with equal operation sets and equal expected literals, read from the tier ledgers — as the reviewer's list.

**Prevents.** Duplicate coverage and un-merged siblings. The same contract pinned by several tests at the same tier is maintained several times, runs several times, and when they disagree the weaker one is kept because it is green; leaving the duplicates out of the map hides them from a map check, a `twin:` at the same tier is a duplicate with a label, and five refusal rows of one operation are five process boots for one mechanism. Sibling tests copied with one literal changed are the same maintenance multiplied, and a change to the contract updates some of them.

**Why this shape.** The landscape id is already the contract's name, so the map is where a duplicate shows — provided every row that claims an id is in the map, which the `beats.md`-to-map direction enforces; the two named exceptions are the two planned overlaps the laws require, and naming them, with the twin's tier checked, keeps "planned" and "accidental" apart; the per-operation bound is Law 3's "one row per mechanism" in a form a check can count. The clone detector is the mechanical form of "differ only in a literal"; it is a row of this design's table so that a project without the neighbour reports `ERROR`, not silence. Test files are inside its scope because an exemption for test files is where copied siblings come from: a test is source, and a copied test is a copied maintenance burden. Duplicates the detector cannot see — two differently written tests of one contract — are the reviewer's, and the candidate list read from the ledgers is what gives the reviewer something to read (integration-suite.md § The threat model).

**Checked by.** `map-dup`: an id mapped twice at one tier with no `crossing:`, more than one success or one refusal row per operation at a tier above the unit tier besides `crossing:` rows, an id whose `crossing:` rows all lie in one lane, a `twin:` at the same tier or naming no row, and the `DUPLICATE-CANDIDATES` listing; `map-beats`: a `beats.md` row with no map row; `clones`: a clone in the test tree beyond its baseline, `ERROR` when the detector is absent.

## Law 29 — a test is hermetic to its environment

**Rule:** The suite assembles its own configuration from the run root and yields the same result under any ambient configuration — environment variables, a user configuration directory, flags. In one scheduled leg, and on every commit that touches the settings or test-configuration paths the Tiers section declares, the unit tier runs twice: once under the base configuration and once under a configuration derived from the settings schema — or, where none exists, from the key set the environment-reader seam's call sites name — with every key perturbed to a valid alternative value and every flag toggled; the two results must be identical, and between legs the check prints `PASS not-due` with the last leg's run id. Settings are never resolved at import or collection time in a test file. Every runner builds the product's environment only from the run root and the `need` values, so an ambient value never reaches the product; a run-root key set in the ambient configuration is an error, never a silent take.

**Prevents.** Greens that depend on whose machine ran them. A unit suite passes by default and fails under the test configuration; a collection error appears only under one flag; an integration tier runs against whatever store a stale configuration points to, or never runs because a variable is absent; a beat is green only because it rode an export in the operator's shell that the runner passed through. Each is a verdict about the machine, and a migration's shape test can reach merge without ever having been observed green. Two "different" configurations that differ in a key nothing reads prove nothing, and a service with no settings schema is not thereby exempt: its environment reader knows every key it asks for.

**Why this shape.** The double run is a differential test of the suite itself: two configurations, one result, or the suite reads something it does not own — and deriving the second from the settings schema, or from the seam's call sites where there is none, is what makes the two genuinely different in every key the product knows. Building the product's environment from the run root alone, rather than refusing only the run-root keys, is what stops the pass-through. Import-time resolution is refused because it binds the verdict to whatever was in the environment when the file was loaded, before any fixture could set it. Scheduled rather than per commit, because doubling the unit tier on every commit is a cost teams remove, while a commit that touches settings is exactly when the second leg pays; printing `PASS not-due` in between is what lets the census still see the check (Law 15).

**Checked by.** `env-twice`: the two unit runs' results differ, `ERROR` on a missing leg, a last leg older than the schedule window, or an unreadable key set or trigger path list; `refused-shapes`, the Self-skip row's settings read at module scope; the runner's `ERROR` on an ambient run-root key.

## Law 30 — the product tree holds no double and cites no test

**Rule:** Fakes, stubs and no-op implementations live only in the fakes directory of the test tree. Production code never selects a double from a configuration value — a test flag, a test store name, a mock switch — and never substitutes a no-op for a missing configuration key: it refuses to boot. One hermetic boot with every required key blank asserts a non-zero exit whose refusal names every key; the per-key cases are unit tests over the configuration loader. A test never replaces a product module in place with an inline stand-in (Law 2). Traceability points one way: a test cites production; production source, contracts, schema comments and CI files never name a test file, a beat id or a test tree path, except as an argument of a declared blocking command in a CI file.

**Prevents.** Two failures:

- **A production box behaving like a test.** A blank queue address boots a no-op publisher and every job is dropped silently — whether the no-op has a class named for it or is an anonymous object returned on the blank; a branch on the store name mints a plaintext credential; a test-mode switch nulls the mail client on a machine that was not a test. A misconfiguration then presents as a working system with nothing behind it.
- **Tests rotting production.** A comment in a service citing a deleted test file, a schema comment naming a beat, a workflow comment asserting a test's file name: renaming or deleting the test edits production files, and a comment-only edit to a contract can trip a content-hash drift gate.

**Why this shape.** The seam (step 3) is an interface with a fake behind it; the interface belongs to production and the fake to the test tree, because the fake is a test's tool and a boot-time choice of it is a test's decision taken by production. Refusing to boot is the visible failure; substituting is the silent one, and because the substitute can be anonymous, the boot test is the check that does not depend on how the double is spelled — one boot with every key blank, because a boot per key is Law 3's "a mechanism booted per variation", and the loader's per-key behaviour is a unit case. One-way citation keeps a test's rename inside the test tree; the blocking command's arguments are the one place a CI file must name the test tree, so they are exempt rather than the rule being switched off.

**Checked by.** `self-tests`: the all-keys-blank boot test is a line of `self-tests.txt`; `refused-shapes`, the Double in production and Test cited by production rows: a class or function named as a double in production source; a branch on a test-environment value or a mock flag; the language's module-mocking spelling applied to a product module; a test tree path, a test file name pattern or a beat id pattern in production source, contracts or CI files outside the declared blocking commands' arguments.

## Law 31 — test files obey the tree's ceiling, and fixtures are synthetic

**Rule:** Lane and test files obey the size ceiling the design declares (`size-ceiling`) at authoring, checked as the `size` row of the design's table and not warned; a project with no ceiling configured is that row's `ERROR`; a lane file splits by journey segment. Fixture files carry no absolute host path, no captured process id and no personal or regulated data. A log-record shape (a JSON line with a timestamp, a level and a message) lives only in the synthetic-log fixture directory, `scope`-tagged in `exclusions.txt`, whose records carry the reserved run id `synthetic`; a captured run log is never a fixture.

**Prevents.** Files nobody can review and fixtures that name a machine. A lane file of thousands of lines is read by nobody in one pass, so its review rows stay unreached and the architecture gate that would flag it is kept warn-only to accommodate it. A captured log committed as a fixture carries the developer's home directory into the repository and pins a run rather than a shape — and with the paths scrubbed it still pins a run.

**Why this shape.** A ceiling holds for source; a test file is source, and a ceiling that stops at the test tree is where the unreviewable file comes from. It is a row of this design's table so that a project without the neighbour reports `ERROR`, not silence. Synthetic fixtures are Law 17's clause applied to what the test tree stores. The record-shape spelling is what catches a captured log after its paths are gone, and the one declared directory with a reserved run id is what lets the self-tests that must parse records — `observed`, the beat library's slice scan, the redaction test — keep their fabricated ones.

**Checked by.** `size`: a test or lane file above the ceiling beyond the test tree's baseline, `ERROR` when no ceiling is configured; `refused-shapes`, the Machine in a fixture row.
