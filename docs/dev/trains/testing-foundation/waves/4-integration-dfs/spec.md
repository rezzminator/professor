# Wave 4 — the live DFS suite (Tier B): one root, parallel lanes, planned overlap

**Northstar (the user's):** cover the whole landscape efficiently, without becoming a bottleneck — the answer is lanes that overlap on the seams and the edge cases. **Depends on:** Wave 1 (`infra/fence/`), the landscape digest (`tmp/inventory/landscape.md` → tracked as `docs/dev/testing/landscape.md`), Wave 2's TSV shape. **Home:** `infra/fence/lanes/`.

## Shape

```
root image (built once, hash-keyed)
   └─► ONE container per run — the fleet's state accumulates lane after lane:
       O₁ ops-install → E1 Claude → E2 Codex → E3 OpenCode → F fleet → M MCP → A adopter → O₂ ops-teardown
       (or any single lane alone, from a fresh container: `run.sh --lanes M`)
```

- **Root (R)** — `infra/fence/lanes/root.sh`: fence container from `pfm-dev` → pfm built from the tree, `pfm install --yes` with every configured seat (Claude seats, the Codex home, the OpenCode home; credentials copied in by `lanes/creds.sh`, which reads the macOS Keychain on darwin and each seat's `.credentials.json` / `auth.json` on linux — today's `infra/demo/creds.sh` is darwin-only, a real gap on the devbox) → express cloned, `pfm init`, the install interview run by a real Claude chat (the demo's `adopt.sh`) → `pfm` launched once: an empty fleet. Then `docker commit` → `pfm-lane-root:<hash>` where `<hash>` covers `pfm/**`, `templates/**`, `docs/SETUP.md`, `infra/fence/**`; an unchanged hash reuses the image, so the ~10–15 min interview is paid once per template change, not per run. The image is local only (it carries seat tokens); it is never pushed.
- **One container per run, lanes in sequence.** `run.sh` starts ONE container from the root image and runs the selected lanes in order inside it; every lane inherits the pfm state the lanes before it built — E1's named chat is still alive when F storms, when M restarts the daemon, when A rewrites the adopter's hooks. pfm is one state (one daemon, one `fleet.db`, one tmux server, one hook set), and the effect of each area on that shared state is where the bugs live; isolating lanes in separate containers would test each area in a vacuum and dismiss that class (the user's call, 2026-09-17, replacing the container-per-lane draft). Concurrency is a scripted beat (`storm`, `TwoWriters`, inject-during-busy), never a scheduling strategy: two lanes racing on one fleet would make every red row order-dependent and unreproducible.
- **Any lane runs alone.** `run.sh --lanes M` starts a fresh container from the root and runs M only. Each lane opens with a `need` prelude that creates its own preconditions when absent (M needs a live chat → it opens one on cc:1) and is a no-op when the sequence already built them — so a solo lane is the dev/qa loop while working on that area (minutes, one seat), and the full sequence is the wave-close and `/pfm:release` step 9 gate. The report header names the mode (`solo` / `sequence`) and, in sequence mode, the lanes that ran before; a red row in sequence mode carries the timeline position (`lane · beat · t+s`) so it can be replayed in order.
- **Order is a design decision:** state builders first, readers over the richest state, destroyers last. O is one file with two entry points — O₁ (install idempotence, dropped seat, credentials, symlinked home, doctor, heal — before any chat exists) and O₂ (reap states after F's storm, archive/index over a real history, `uninstall` — the end of the run, since it tears the machine down). F's kill-storm kills its own storm chats by label and leaves E1's named chat alive by design, so M and A still assert against a live fleet.
- **Cross-lane interaction beats** — the effect of one area on the state another built, each a row in the overlap table: after F's storm, E1's chat still answers `status`/`last`/`inject`; M's daemon restart with live chats → every chat's next MCP call succeeds; A's `pfm update` + hook rewrite while the fleet is up → `pfm ls` and every chat's hooks unchanged; O₂'s dropped seat while a chat lives on that seat → the chat keeps working and doctor names the seat.
- **Lane** — `lanes/<id>.sh`, a DFS path: each beat is `beat <id> <landscape-ids…>`; a beat asserts from pfm's own reports and the pane (tmux `capture-pane`), never from a model's word; a beat whose precondition beat failed reports `blocked-by <beat>` (not ✗, not skipped-silently); the lane runs to its end. Beats declare the seat they spend (`spends cc:1`) so a solo run and the sequence both account for quota; the default run uses one Claude seat throughout, `--seats` spreads it.
- **Known gaps** — `lanes/known-gaps.yml`: `<beat> · <landscape id> · <why> · <owner> · <date>`. A listed beat reports `✗ known-gap`, counts separately, and does NOT fail the suite; a listed beat that PASSES is a red row (`known-gap now passes — remove the entry`), so the list can never rot into a coincidence detector. First entries: OpenCode MCP wiring (M lane), OpenCode compile layer for adopters (A lane), harvestpy on linux-arm64 (O lane; passes on x86_64 — the entry is arch-conditional).
- **Map gate** — `lanes/map.tsv`: `landscape-id · lane · beat`. `lanes/check-map.sh` fails when any id in `docs/dev/testing/landscape.md` is unmapped, when a mapped beat does not exist, and — machine-derived, so the doc cannot drift — when `pfm --help`'s command tree or the MCP servers' tool lists contain a name the map does not carry. Coverage = a beat per id, on purpose more than one for the seam ids below.
- **Runner** — `lanes/run.sh [--lanes E1,F,…] [--root reuse|rebuild] [--seats cc:1,2,3 cx oc]`: builds/reuses the root, starts one container, runs the lanes in canonical order (or the one named), streams `✓/✗/known/blocked` lines with the lane prefix and the timeline stamp, writes `tmp/lanes/<stamp>/<lane>.log` (a failed beat dumps `capture-pane -e -p -S -` raw bytes beside the assertion), `timeline.tsv`, `summary.md`, and the Wave 2 TSV (`lane · wall_s · beats · failed · known · blocked`), checks `lanes/budgets.yml` (per-lane and full-sequence wall budgets, ratchet-down like `.testtiming.yml`), and exits 1 on any ✗ that is not a known gap, on an unmapped id, or on a budget breach — each named. There is no `--parallel`.
- **Demo** — `infra/demo/verify.sh` keeps the deck's beats for the live demo but sources the same beat library (`lanes/lib.sh`: `pass/fail/known/blocked/spends/timing`) — one implementation, the demo is a subset view, never a second copy.

## The lanes (DFS order inside each; landscape ids filled by the mapping step)

**E1 — Claude.** Open one cc chat on seat 1 → label, tmux title, statusline (seat glyph, model, effort, context %), theme `custom:professor-*`, fullscreen TUI → `/reload` matrix, one beat per flag and the meaningful pairs: `--account 2`, `--model`, `--effort`, `--1h on`, `--1h off`, `--new`, `--new --hide`, `--then "<steer>"`, `--sock <own>`, and `/reload` typed WHILE the chat is busy (asserts Wave 0's on-pane hold notice, then the reboot) → every outside-in verb on that chat: `status` (working/idle with a background sub-agent → still `working`), `last`, `read`, `stream`, `capture`, `keys`, `ask`, `inject` (busy → queued; menu open → refused by name), `watch --idle-after`, `name` (label converges in tmux + statusline), `kill`/`unkill`, `self-compact` (receipt on the pane), `/handoff` (new chat carries the file, old one hidden), `end` → lane end.
**E2 — Codex.** Same DFS shape on the Codex home: label/title/statusline; `/reload` matrix as far as Codex supports it (no UserPromptSubmit hook: `/reload` travels through the model — the beat asserts that path); `recover` from a rollout; the appendix hook (`codex-appendix`) present in the first turn; MCP over HTTP (`chat_*` tools listed in the Codex session); inject/ask/watch; `pfm doctor`'s `codex_pane` rows clean while the chat lives.
**E3 — OpenCode.** Same shape on the OpenCode home; the MCP beat is the known gap (M4); everything else asserted for real.
**F — fleet.** From the root: `chat new` for every kind dimension the landscape lists (cc/cx/oc × named × `{name}:{group}` × hidden × role/prompt-file × account × 1h × model/effort), a headless chat, a storm (`storm.sh`) → `pfm ls` rows and kinds → the TUI: picker rows per kind, fuzzy-find, every keybinding, Stats (every chat where expected), Limits (per seat), cosmos (rails, live shine) — asserted by `capture-pane` against the golden shapes the unit tier already pins → `name-sync` convergence → idle down/up (a chat with a running background agent must NOT go down) → kill-storm → reap states (the 13, each provoked where it can be) → lane end.
**M — MCP.** Registration per engine from the files the installer wrote (Claude stdio + HTTP, Codex HTTP-only, OpenCode = known gap) → daemon: port, health, restart on replaced binary (rebuild pfm in-container, observe the exit-75 restart) → every tool of both servers driven by a direct MCP client against the live daemon with real targets (a live chat from this lane; the harvester on a small public document): `chat_ls status last read inject ask watch … whoami self_compact save find resolve name kill unkill new open …` and `searchCache findWorks fetch fetchImage search archive` — each asserting the documented result shape AND the error-vs-absence contract (a missing chat → `not_found`; a dead daemon → an error, never an empty list) → one chat-driven call per server (a Claude chat asked to call `chat_status` on itself and to `fetch` one URL; a Codex chat the same over HTTP) proves the engine wiring end to end → lane end.
**A — adopter.** The express install: `pfm update check` clean; `pfm codex check` PASS; hooks rooted at `$CLAUDE_PROJECT_DIR` and present; the guard hook DENIES a real chat's Edit of `.claude/**` without the `/pcm` stamp and ALLOWS it with the stamp; the Stop hook recompiles `AGENTS.md`; `/dev status|test` runs express's own suite; then the update flow against a second blueprint copy inside the container with one template edited / one added / one removed / one local file deleted → `UPDATED / NEW / GONE-UPSTREAM / LOCAL-DELETED` each reported with the right diff command → `pin` / `ignore` / `drop` → `clean`; `pfm update adopt` on a copy that predates init; OpenCode compile layer = known gap → lane end.
**O — ops & host.** Second `pfm install --yes` is idempotent (`changed=0`); two seats logged into one account → doctor names the duplicate (O₁, with Wave 3 B5a's advisory; a known gap until B5a lands); a dropped seat loses exactly its owned hooks and ledger rows (P10.2); a seat with an expired/absent credential → doctor says NOT-LOGGED-IN by name, `chat new --account` on it refuses by name, `/reload --account` onto it refuses on the pane; `~/.claude` as a SYMLINK and a blueprint reached through a symlink (P10.1 class); two `pfm install --yes` at once (atomic writers hold); `pfm doctor` every row green or a named advisory (no systemd in the container is the named one); `heal`, `reap --preview`, `archive`, `index`; headless on cc and cx; harvester: `pfm harvest` ask + the sidecar provisioning (real on x86_64; arm64 = known gap) → `uninstall` removes everything owned, keeps a foreign hook planted before install, leaves no ledger → lane end.

## Planned overlap (the seams every pair of lanes crosses on purpose)

| Seam | Lanes | Why twice |
| --- | --- | --- |
| reload while the chat is busy | E1 + O (inject during busy) | the hold notice from the user's side and from the operator's side |
| a chat with a background sub-agent | E1 (`status` → working) + F (idle-down must keep it) | the P12 class, read by two consumers |
| expired / absent credential | O (doctor, chat new) + E1 (`/reload --account`) | absence vs error at two surfaces |
| symlinked home / blueprint | O (`~/.claude` link) + A (`pfm update` via a linked blueprint) | the P10.1 class, installer side and update side |
| dropped seat | O (hooks + ledger) + M (daemon's seat roster) | one truth, two readers |
| concurrent writers | O (two installs) + F (N parallel `chat new`) | atomic writers under two load shapes |
| label grammar `{name}:{group}` | F (create, ls, TUI) + E1 (`name` converges title + statusline) | writer and every renderer |
| a storm beside a named chat | F (storm, kill-storm) → E1's chat afterwards (`status`, `last`, `inject`) | the sequence's first cross-lane state effect |
| daemon restart with live chats | M (exit-75 restart) → E1 + E2 chats' next MCP call | one daemon, every engine's wiring |
| adopter update while the fleet is up | A (`pfm update`, hook rewrite) → F (`pfm ls`) + E1 (hooks unchanged) | writes under the fleet's feet |
| dropped seat with a live chat on it | O₂ (drop) → E1 (chat keeps working, doctor names the seat) | ledger and runtime disagree or agree |

## Execution model and budgets

One container, lanes in canonical order, one Claude seat by default — the full sequence is the sum of its lanes, and that is the accepted cost of testing the shared state for real (dissent on record: the container-per-lane draft would have run in ≤ 15 min; the user chose realism over wall time, and the daily loop is a solo lane, not the sequence). Targets: root ≤ 15 min (paid once per template change), a solo lane ≤ 12 min, the full sequence ≤ 75 min with the root cached; budgets pinned from the first three green runs (median), ratchet-down. Several sequences may run at once only as separate containers from separate worktrees (the fence already supports that) — never two lanes in one container.

## Not covered here (named)

Tier B runs on linux containers only — darwin has no Tier B; darwin behaviour is Tier U's edge-case fixtures plus Tier A on a Mac. The self-update from an older release stays Tier A (`TestOlderPFMDiscoversUpdate…`). The VS Code extension and the name-sync scheduler units need a host with a service manager — Tier U covers their file shapes; a hosted run is a later train.

## Build order

1. `lanes/lib.sh` + `run.sh` + `root.sh` + `creds.sh` (linux path) + `check-map.sh` + `budgets.yml` + `known-gaps.yml` — the harness, exercised first with ONE lane solo (E1) end to end, then E1 in sequence after O₁.
2. Lanes F, M, A, O₁/O₂ (with their cross-lane beats); then E2, E3.
3. `infra/demo/verify.sh` re-based on `lib.sh`; `docs/dev/testing/lanes.md` (how to run one lane, the sequence, read a red row from the timeline, extend — and the rule that a new landscape item lands with its beat in the same commit).
4. Three green sequences → budgets pinned → the sequence wired as the release gate in `/pfm:release` step 9 (guarded, GOD); the solo lane named in every wave spec that touches its area.

## Prior art (RR-2, `.professor/RR/agent-fleet-testing-release-chain-2026-09-17.md`)

- **zellij** is the only neighbour that drives its real binary end to end (binary in Docker, driven over SSH, output diffed against snapshots, `--debug` logging raw pty bytes) — adopted: a failed beat dumps `tmux capture-pane -e -p -S -` (escapes included) into the lane log beside the assertion, so a red row carries the bytes, not a paraphrase.
- **MCP conformance** (`modelcontextprotocol/conformance`, a real client running spec checks and writing `results/checks.json`; Inspector `--cli --format json` for scripted calls) — candidate for the M lane as an independent judge of both pfm servers: pinned to a ref, run in-container, validated before adoption (never an unvalidated install). Its exit-code map is unread — resolve before wiring.
- **No provider key in the merge gate** at Codex CLI, OpenCode, or Goose; live-model runs never block a merge — confirms Tier B's place: the release gate (`/pfm:release` step 9) and on demand, never per commit.
- **claude-squad** (the closest structural twin: Go + tmux + worktrees) ships no tests for its tmux layer and cross-compiles six targets as its CI — the anti-pattern this wave exists to close.
- **Cline's Checkpoints** renamed users' `.git` and nested `.git` dirs into `node_modules` across seven issues — destructive operations on user state are their own beat class: the O lane's `uninstall` (keeps a foreign hook), dropped seat (loses exactly its own), and second-install idempotence each assert a refusal or no-op path, not only the happy path.
- **Anthropic's April-23 post-mortem**: three regressions shipped because reports were "challenging to distinguish from normal variation" — the release chain needs a deterministic signal; here that is the known-gap ledger (red when a gap passes) and the per-lane budget ratchet, and budgets pin only after three green runs (a soak, not a first reading).

## Prior art (RR-1, `.professor/RR/hermetic-trustworthy-test-gates-2026-09-17.md`)

- **The four-tier release chain** (SWE@Google ch. 23): presubmit (fast, hermetic) → postsubmit (everything affected, tolerating latency) → release candidate (large tests over the whole candidate, rising fidelity) → production probers (the same suite against the live system, which also audits whether the tests still matter). Ours: U + A at every commit, the solo lane during work, the sequence at wave close and release, and the demo deck (`infra/demo/verify.sh` over the same `lib.sh`) as the prober that audits the beats against a live machine.
- **`pytest xfail(strict=True)`** is the only known-gap mechanism found that fails the build when a gap unexpectedly passes — `known-gaps.yml`'s red row is that rule; Chromium's `TestExpectations` requires a bug link but has no expiry, the rot this ledger's owner + date columns exist to prevent.
- **Hermetic, ephemeral SUTs at Google** cost 10–30 min startup, mitigated by pre-warmed pools — the hash-keyed root image is our pre-warmed pool; the benefit was never quantified there, so the first three sequences here record the flake count against the old demo verifier as the number.
- **External model APIs: record once, replay, error on anything unrecorded** — not adopted for Tier B on purpose (the lanes exist to hit the real engines); the recorded shapes live in Tier A's fakes, and a Tier B beat that fails only on model variance is a beat asserting the wrong thing (a report, a pane, a file — never a model's words).
