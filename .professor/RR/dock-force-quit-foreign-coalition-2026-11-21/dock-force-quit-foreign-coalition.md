# RR — Is macOS Dock force-quit killing a foreign coalition (via a reused pid) a publicly known bug?
Question: decide whether this macOS behavior is a publicly known bug (Dock _LSForceQuitApplication for an exited Chrome appPID=69809, after pid wrap, killed 79 pids of a different coalition — Herdr server + agent CLIs from a VS Code terminal — on Darwin 27.2.0, 2026-11-21); verdict KNOWN / RELATED-ONLY / NOT FOUND, searching Apple forums & Support Community, terminal/browser trackers, HN/Reddit/OpenRadar, macOS 26.x/27.x release notes, and the pid->coalition mechanism in XNU.

Verdict: RELATED-ONLY. The closest public reports are two GitHub issues on macOS 27.0.1 where a Dock Force Quit killed processes the force-quit app did not launch ([claude-code#103974](https://github.com/anthropics/claude-code/issues/103974), [t3code#26604](https://github.com/pingdotgg/t3code/issues/26604)), but neither mentions pid reuse or carries an Apple FB number, and no Apple release note read mentions Force Quit, LaunchServices or coalitions. What XNU does show is that a lookup from a bare pid returns the coalition of whatever process now holds that number ([proc_info.c](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L2170-L2192), [sys_coalition.c](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/sys_coalition.c#L740-L795)), so a Dock that resolved the coalition from the stored appPID at kill time would produce this case — an inference no public source confirms, because Dock and LaunchServices are closed source.

### Mechanism (XNU source, clone-distiller @ f6217f8)
- `proc_pidinfo` resolves the pid with a bare `proc_find(pid)` ([proc_info.c:2170-2192](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L2170-L2192)), and `PROC_PIDCOALITIONINFO` returns `task->coalition[i]->id` of whatever task holds that number now ([proc_info.c:2408-2416](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L2408-L2416), [coalition.c:1527-1540](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/coalition.c#L1527-L1540)). The only guard is opt-in: `proc_info_extended_id` with `PIF_COMPARE_IDVERSION`/`PIF_COMPARE_UNIQUEID` returns ESRCH on a mismatch ([proc_info.c:285-305](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/proc_info.c#L285-L305)).
- The only member-pid listing is the `kern.coalition_pid_list` sysctl, keyed by a pid, not a coalition id: `tproc = proc_find(pid);` followed by every member of that proc's coalition ([sys_coalition.c:740-795](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/sys_coalition.c#L740-L795)). A stale pid lists the new owner's coalition.
- Every process has exactly one resource and one jetsam coalition, set at spawn by launchd via `posix_spawnattr_setcoalition_np`, inherited across fork/exec and fixed after creation ([coalitions.md:10-17](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/doc/observability/coalitions.md#L10-L17), [kern_fork.c:314-318](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/kern_fork.c#L314-L318)). Both types share one id counter, `coalition_next_id`, which starts at 1, is post-incremented for every creation and never reset, so coalition ids are never reused ([coalition.c:95-98](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/coalition.c#L95-L98), [coalition.c:1360-1365](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/coalition.c#L1360-L1365)).
- `coalition_info_resource_usage(cid, …)` returns accounting only (tasks started/exited, CPU, energy, I/O, GPU, per-QoS CPU) ([libsyscall coalition.c:36-76](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/libsyscall/wrappers/coalition.c#L36-L76)). `coalition_policy_set` (e.g. `COALITION_POLICY_SUPPRESS`) requires `COALITION_POLICY_ENTITLEMENT` ([sys_coalition.c:525-536](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/kern/sys_coalition.c#L525-L536)). Kernel coalition terminate only sets `termrequested` and signals no members ([coalition.c:2183-2200](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/coalition.c#L2183-L2200)), so the SIGTERM sweep is done in user space by Dock/LaunchServices.
- A coalition with live members stays findable by id ([coalition.c:1470-1502](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/coalition.c#L1470-L1502), [coalition.c:2255-2270](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/osfmk/kern/coalition.c#L2255-L2270)). Chrome's original coalition therefore still existed at 07:51 while its two helpers lived, and LaunchServices could have killed by that id.
- Inference (unverified, closed source): the case's log pairs `appPID=69809` with `coalition=189852`, and the kill set was a different coalition from Chrome's. That fits a Dock/LaunchServices path that resolves the coalition from the stored appPID at kill time (or lists members via `kern.coalition_pid_list(69809)`), after 69809 had been reused by a process in the Herdr/VS Code coalition. If 189852 is that coalition's id rather than Chrome's, the stale-pid resolution is confirmed locally. No public source states how LaunchServices obtains the coalition (reports 06, 11).
