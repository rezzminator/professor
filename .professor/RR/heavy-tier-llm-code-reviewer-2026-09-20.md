# RR — The HEAVY tier of a two-tier LLM code reviewer: most accuracy per token on a large or risky diff

Question: the HEAVY tier of a two-tier LLM code reviewer — the design that reviews a LARGE or RISKY diff with the most accuracy for the fewest tokens. North star: least token price AND most accuracy, judged together — which stage buys how much accuracy per token. Decide ADOPT (take one existing open implementation and adapt it in one place) versus DISTILL-AND-BUILD (take the proven parts of several and write our own). Goal and artifact: your standard saved RR map (.professor/RR/{slug}-{date}.md); return its path first, then a decision matrix and a recommendation.

---

## Answer

**DISTILL-AND-BUILD.** No open implementation both fits a single-markdown Claude Code sub-agent and carries the evidence — the closest in shape (`/code-review`) has no decomposition, no execution and a same-family validator; the closest in ambition (`agent-review-panel`) burns 69% of its spend on orchestration and is self-admittedly unbenchmarked. The evidence points at one design and it is not "more seats on a bigger model": spend goes into **mechanical decomposition into file-clustered lanes sized to the band where models work**, a **cheap over-producing finder**, one **strong context-asymmetric verifier** (the single stage with the largest measured effect sizes anywhere in this literature), and an **execution gate on survivors** — while *removing* the "read every body in full" context that two benchmarks now show is flat-to-harmful. At our current reviewer's price (~$0.9 at 500 lines, ~$2.6 at 2,500) that reallocation buys the two measured stages we currently do not have at all.

## Map

### 1. The controlling constraint: diff size, and what one unit of context is worth

- Review F1 collapses with diff size — **0.657 under 10 changed lines → 0.043 over 150 lines**; the 10–50 line band is the sweet spot; the authors call preprocessing large diffs "the most actionable finding" ([arXiv 2606.15689](https://arxiv.org/html/2606.15689v1), prior RR). Model size does not rescue it: Haiku 4.5 beat Sonnet 4.6 on F1 (0.365 vs 0.343) and recall (+18.1%) at 3.2x lower cost, while Sonnet won precision (0.558 vs 0.486) — **small model as finder, large model as filter** is an empirical result, not an economy measure.
- **More context is flat-to-harmful, not free.** AACR-Bench shows non-agentic recall declining monotonically Diff > File > Repo (Qwen-480B-Coder: 33.82% → 22.59% → 17.60%), and Claude-4.5-Sonnet's F1 dropping 31% when given BM25 top-3 versus no retrieval ([arXiv 2601.19494](https://arxiv.org/html/2601.19494v1)). CodeFuse-CR-Bench shows most models peaking at BM25 **top-1** and degrading to top-5 (DeepSeek-v3.1 48.13→36.42; Claude-Sonnet-4 51.02→41.91), with top-1 ≈ oracle context for Gemini (52.24 vs 52.37) ([arXiv 2509.14856](https://arxiv.org/html/2509.14856)).
  - **Tension, stated honestly:** the two benchmarks disagree on strength. AACR-Bench reads as net-negative; CodeFuse reads as flat for the robust model, and AACR-Bench's *agent* methods improve with repo context (DeepSeek 4.28→8.00%). The defensible common floor is: **additional context is not reliably additive, and paying for whole-file reads is unjustified by evidence.** "Lost in the middle" (>30% degradation when the relevant span sits mid-context) is the mechanism to design around by front/back-loading high-signal hunks.
- c-CRAB, read off the PDF's own tables, confirms where agents fail and why: pass rates **Claude Code 32.1% · Devin 24.8% · PR-Agent 23.1% · Codex 20.1%**, union 97/234 = **41.5%**; human baseline 100%. Average modified lines per PR **418.1**, 234 tests (82.1% structural, 17.9% behavioral), 1.27 tests/instance, 67 repos ([arXiv 2603.23448](https://arxiv.org/html/2603.23448v2)). Agents **over-review robustness** (~22% of comments vs humans' ~14%) and **under-review design and documentation** (~5–8% vs humans' ~14–16%), and pass rates are lowest exactly there (maintainability 7.9–27.0%). c-CRAB reports **no cost, token or latency figures for any agent** — a named gap.

**The cheap-verifier trap — the most important new constraint.** "Cheap Verifiers, Large Blind Spots" measures β, the fraction of the generator's wrong answers a verifier wrongly accepts: **β grows 0.12 → 0.55 as the generator scales from 0.5B to 32B**, falling to ≈0.05 only with a *frontier* verifier — which then escalates 46% of hard queries against a 39% true error rate. Worse, in the self-improving condition the verifier's own dashboard read a flat ~3% error rate while true delivered error rose to **32%**: the cascade is blind to its own degradation by construction ([arXiv 2609.01345](https://arxiv.org/abs/2609.01345)). **Consequence for us: the verifier must be the strongest model available and must never be the metric of its own health.**

### 3. Large-diff decomposition (Question 2)

- **Granularity, measured — but on the wrong task.** "Beyond Summaries" compares per-hunk / per-file / per-patch: per-hunk costs the most tokens (~1300–1500 in) for the lowest accuracy; **per-file wins for 3 of 4 models** (Gemini-3 per-file 81% IoP / 84% IoGT vs per-patch 68%/70%); per-patch is cheapest (~430–530 tokens) at mid accuracy. It measures **change-type labeling, not defect review** — adjacent evidence, not proof ([arXiv 2605.26100](https://arxiv.org/html/2605.26100)).
- **Commit untangling is a real research line with accuracy numbers**: UTANGO reports 28.6–462.5% relative gains over prior SOTA; SmartCommit 71–83.5% decomposition accuracy; CoRA +6.3% over SOTA and additionally *describes* each slice for reviewers ([UTANGO FSE'22](https://dl.acm.org/doi/abs/10.1145/3540250.3549171), [SmartCommit FSE'21](https://www.cs.cmu.edu/~ckaestne/pdf/fse21_sc.pdf)). **What fraction of untangled clusters span more than one file is never published** — looked in all three primary papers, found none. That is the number that would tell us whether cutting by file loses atomic units.
- **Cross-file bug fraction (the load-bearing number):** the Linux-kernel SZZ evaluation over **76,046 developer-labeled fix ↔ inducing-commit pairs** finds **34.6%** of bug-inducing commits in the fixed *function's* history, **27.5%** in the file's but not the function's, and **37.9% in neither the file's nor the function's history** ([arXiv 2308.05060](https://arxiv.org/abs/2308.05060)). Files-per-bug-fix is project-dependent (43% single-file, avg 2.43 in one study; 3.1–15.9 in others) — UNVERIFIED as a single canonical constant. **Reading: roughly a third of real defect origins are not co-located at file granularity, so per-file lanes must be crossed by at least one diff-wide lens.**
- **Slicing does not transfer.** SLICEMATE is not dataflow-based despite the name — Tree-sitter syntax plus an LLM agent trio; +62.5% F1 on large programs, **~$0.15/slice** with GPT-4o; **Java and Python only, Go unaddressed** ([arXiv 2507.18957](https://arxiv.org/html/2507.18957)).
- **Call-graph component splitting: buildable, not built.** No published tool splits a diff by connected components of a call graph. The pieces are Bash-runnable for Go — `golang.org/x/tools/go/callgraph` (cha/rta/vta) and `cmd/callgraph` emit a static graph one could intersect with the changed-symbol set; `gopls`/`guru` answer per-symbol queries only ([pkg.go.dev/golang.org/x/tools/go/callgraph](https://pkg.go.dev/golang.org/x/tools/go/callgraph)).
- **Does piecewise beat whole-diff for defect review? NOTHING FOUND.** Looked; the size-collapse paper is correlational and recommends chunking without running the ablation. This is the single largest evidence gap under the recommendation.

### 4. Fan-out that helps vs fan-out that hurts (Question 3)

- **Role split was isolated once, and it carried value:** RADAR (the multi-agent-debate paper, arXiv 2509.25271 — not Meta's diff-review RADAR) ablates specialized roles vs. the same LLMs in free-form debate under one generic prompt vs. no debate. No-debate is worst; generic debate improves; **specialized roles beat generic debate**, attributed to perspective specialization and bias compensation ([2509.25271](https://arxiv.org/pdf/2509.25271)). Dynamic role assignment reports up to 74.8% over uniform roles — **non-code-review tasks, UNVERIFIED for review lenses**.
- **Same-question ensembling hurts** (F1 0.365 → 0.30–0.33). The distinction is different-questions (helps) vs same-question-unioned (hurts).
- **Same-model panels make agreement uninformative.** Refute-or-Promote's ten reviewers unanimously endorsed a nonexistent OpenSSL oracle that only an empirical test caught — "unanimity is a low-signal event". The quantitative backing (r≈0.77 pairwise error correlation between frontier models; debate under homogeneous models as a martingale) comes only from **secondary blog synthesis and is UNVERIFIED at primary source**. `agent-review-panel`'s own author flags this limitation of its debate design unprompted.
- **Convergence/early exit has a concrete, copyable implementation.** calimero's `docs/ARCHITECTURE.md`: `consensus_score = unique_agents_in_cluster / total_agents`, clustering on same file + category + overlapping lines ±5 + title/description similarity ≥0.85; severity-dependent confidence floors (≥3 agents: critical 0.3 / warning 0.4 / suggestion 0.5 / nitpick 0.6; 1–2 agents: 0.5/0.6/0.7/0.8); cross-review drops findings with <2/3 validation agreement **except CRITICAL+SECURITY, which always bypass**. Halt is outcome-based with no iteration cap: skip on same commit, skip when the diff touches no finding-relevant file, LGTM fast path after ≥2 clean reviews, and `should_skip_review` once `new_findings == 0 AND fixed_findings == 0` ([ARCHITECTURE.md](https://raw.githubusercontent.com/calimero-network/ai-code-reviewer/master/docs/ARCHITECTURE.md), MIT).

### 5. Model tiering and the real caching economics (Question 4)

- **Pricing, $/MTok (base in / 5m cache write / 1h write / cache read / out):** Opus 5 **5 / 6.25 / 10 / 0.50 / 25** · Sonnet 5 **2 / 2.50 / 4 / 0.20 / 10** · Sonnet 4.6 **3 / 3.75 / 6 / 0.30 / 15** · Haiku 4.5 **1 / 1.25 / 2 / 0.10 / 5** ([pricing docs](https://platform.claude.com/docs/en/about-claude/pricing)). Cache read is **0.1x** base input; 5-minute write 1.25x, 1-hour 2x.
- **Caching mechanics that decide seat design:** hierarchical exact-hash prefix over **tools → system → messages**; any change at or before a breakpoint invalidates it and everything after; ≤4 explicit breakpoints; minimum cacheable length **1,024 tokens** for Sonnet 5/4.6/4.5 and Opus 5, **4,096** for Haiku 4.5 and Opus 4.6/4.5 ([prompt caching docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)).
- **The parallel-seat trap, documented:** "a cache entry only becomes available after the first response begins" — seats fired simultaneously against a cold prefix **all miss**. Anthropic's remedy is a warm-up call; Claude Code itself holds all but the first same-prefix agent **up to 5 seconds** so the rest can read the prefix the first one wrote ([Claude Code prompt-caching docs](https://code.claude.com/docs/en/prompt-caching)). Crucially, **a sub-agent does not read the parent's cache** — it starts its own conversation and warms its own, on the 5-minute bucket by default (`subagentPromptCacheTtl`); a *fork* does inherit.
  - **Design consequence:** for the shared diff prefix to cache across seats, every seat prompt must be byte-identical up to the breakpoint — **shared diff and shared instructions first, the seat's lane assignment last**. Cloudflare reports an **85.7% prompt-cache hit rate** in production AI review across 131,246 runs, so this is achievable at scale ([Cloudflare](https://blog.cloudflare.com/ai-code-review/)).
  - **Caveat:** Opus 4.7+ uses a newer tokenizer producing **~30% more tokens for identical text** than Sonnet/Haiku — cross-model token counts are not directly comparable.
- **Cascade economics:** FrugalGPT matches GPT-4 at **up to 98% cost reduction**, or +4pp accuracy at equal cost, by escalating only on a confidence gate ([2305.05176](https://arxiv.org/abs/2305.05176)). **No code-review-specific cascade paper exists** — looked and found none; FrugalGPT is the closest verified analogue, and §2's β finding is the binding caveat on it.
- **Tokens per diff line: UNVERIFIED at any primary tokenizer measurement.** No diff-specific benchmark found. We use ~4 chars/token on ~48-char unified-diff lines → **~12 tokens/line (COMPUTED)**.

### 6. Verifier design (Question 5)

- **Context asymmetry is a design principle with kill rates but no isolated ablation.** Refute-or-Promote's adversaries see only the *claim, not the advocate's reasoning* (anti-anchoring); Stage A kills ~63% of 171 candidates, Stage B ~42% of survivors, ~79% aggregate, 83% (25/30) prospectively. The asymmetry is between claim and **reasoning**, not claim and **code context** — so **no controlled study of claim-only vs claim-plus-code verification for code review exists**. Looked; found only a non-peer-reviewed agent-memory result (recall 0.08→0.88 at fixed false-accept 0.02 when real code context replaces bare tokens) in a different domain — suggestive only, UNVERIFIED.
- **Write-and-run vs read-only verification:** AnyPoC's checker genuinely re-executes PoCs in fresh environments and roughly **doubles cost** ($5.02 vs $2.42/report with Claude). No head-to-head against a read-only reasoning verifier exists in the paper. Counter-caution from the prior RR: **46% of "passing" validation events carried no bug-discriminating information** — the test must discriminate, not merely pass.
- **Confidence thresholds are unvalidated for review.** pr-review-toolkit reports only ≥80/100; onmax/pr-review-agent uses 80%; Meta RADAR requires ≥8/10 — and RADAR reports only downstream proxies (1/3 revert rate, 1/50 production-incident rate) and **never the precision/recall of the 8/10 score itself**. No code-review-specific calibration study exists; general work puts LLM self-assessment at 49–54% accuracy. **Anthropic's own security-review filter defaults to maximum confidence when its API call fails** — the canonical example of a verifier that fails open.
- **Finding dedup/ranking across parallel agents has no published effect size.** Qodo's judge agent and calimero's agreement weighting both assert; neither measures. Looked and found none.

### 7. Completeness forcing (Question 6)

**Confirmed: no measured technique exists.** Two independent search passes (code review literature, then general agent literature — checklist prompting, plan-and-solve, coverage-guided agents, structured enumeration) returned nothing with a recall or coverage number. The closest adjacent evidence is a two-phase enumeration approach for agent tool-safety testing with no transferable figure ([arXiv 2603.18245](https://arxiv.org/pdf/2603.18245)). The only *implementations* are unmeasured: `agent-review-panel`'s Phase 8 Completeness Audit (re-reads source line-by-line for panel gaps) and its Phase 13.5 / 14.5 hard gates that confirm phase outputs exist on disk pre-judge and catch judge-introduced hallucinations post-judge. **This remains the largest open design space in the HEAVY tier — and it is precisely where our current reviewer's worst defect lives (a ledger narrated rather than derived).**

### 8. The routing rule into this tier (Question 7)

- **No vendor publishes a numeric threshold.** Qodo names hunk count plus a minimum changed-line gate and argues raw size is the wrong signal (a 1000-line rename ranks below a 40-line scatter), but withholds the values; Copilot's Lite/Balanced and Bugbot's effort levels have no public numeric spec. Qodo's measured router result stands: **−21% cost, −30% tokens, −27% average runtime at all-Deep F1**, with uncertainty as a **one-way escalation**.
- **Computable metrics do exist, from Kamei's JIT defect prediction:** NS (modified subsystems), ND (modified directories), NF (modified files), **Entropy** (Shannon entropy of modified lines distributed across touched files), LA/LD, LT (pre-change file size, the churn normalizer), FIX. Reported power: ~68% accuracy / 64% recall, and **35–50% of defect-inducing changes flagged at 20% inspection effort**. All computable from `git diff --numstat` ([Kamei TSE 2013](https://posl.ait.kyushu-u.ac.jp/~kamei/publications/Kamei_TSE2013.pdf) — **named failed lookup: the PDF would not render through either fetch path and ResearchGate returned 403, so the exact entropy formula is from secondary description, UNVERIFIED verbatim**).
- **Does dispersion actually beat size? The evidence is mixed and does not confirm Qodo's claim.** One benchmark found process metrics and code churn best, entropy-of-change metrics *poor*; Hassan's original entropy-of-changes work found the opposite; comparative work found entropy beats churn-entropy mainly on small systems. **No source validates "dispersion beats line count" as stated.**

### 9. Orchestration cost (Question 8)

- **Anthropic's own numbers:** agents use ~4x the tokens of a chat, **multi-agent systems ~15x**; a multi-agent system (Opus lead, Sonnet subagents) beat single-agent Opus by **90.2%** on their research eval — quality gain and cost multiplier reported separately, never combined ([Anthropic](https://www.anthropic.com/engineering/built-multi-agent-research-system)). Cognition argues single-threaded by default with **no numbers at all** ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). **No quantified compaction-vs-multi-agent comparison exists** — looked and found none.
- **The one real measurement of where orchestration money goes** is `agent-review-panel`'s own token audit of a single full run: **the orchestrator main loop alone consumed 69% of spend** (157 turns, context growing 270k → 630k), judge 11%, all four reviewers across phases 3–7 combined **7%**, verification agents 7%, HTML report 4% ([token-split audit](https://github.com/wan-huiyan/agent-review-panel/blob/main/docs/analysis/2026-07-16-panel-token-split-audit.md)). **The lesson is exact: the seats are nearly free; the lead's growing context is the bill.** The lead must hold the ledger, the lane map and the finding table — and must never hold file bodies, seat transcripts or the diff twice.

## Recommendation: DISTILL-AND-BUILD

**Why not ADOPT.** `/code-review` is the only candidate whose shape is close, and it is missing exactly the three stages the evidence rewards (decomposition, execution, a cross-context verifier) while being `gh`-bound. `agent-review-panel` has the phases but spends 69% of its money on the orchestrator and publishes no quality number. `calimero` has the best logic and no evaluation. Nothing to adopt wholesale; plenty to take.

### The design

**Stage 0 — Lead (Sonnet), mechanical.** Derive the ledger from `git diff --numstat` and hunk headers **by Bash, never by narration** — this alone fixes our worst recorded defect. Compute Kamei metrics (NF, ND, NS, Entropy, LA/LD, LT) for routing and lane sizing. Cut lanes **by file cluster**, joined where `go/callgraph` shows changed symbols calling each other, else by directory — targeting the 10–50-line band and never exceeding ~150 changed lines per lane. *(Per-file over per-hunk from "Beyond Summaries", transferred by analogy and flagged as such.)*

**Stage 1 — Finders (Haiku 4.5), over-produce.** One per lane, plus **two diff-wide different-question lenses** — structure (removed invariants, callers) and honesty (failure branches, repo conventions) — which are what covers the ~37.9% of defect origins that are not file-local. Lens seats read the **lane diff plus at most top-1-equivalent targeted context**, never whole bodies. Every seat prompt is byte-identical up to the breakpoint (shared diff + shared instructions first, lane assignment last), and the lead **staggers the first seat** so the rest read its cache.

**Stage 2 — Verifier (Opus 5), context-asymmetric, batched.** Sees the **claim and cited lines, never the finder's reasoning**. Must state a concrete triggering input or the finding dies. Opus and not the lead: the cheap-verifier β result forbids a weak verifier, and the lead is anchored. Batch candidates per call.

**Stage 3 — Execution gate (Sonnet + Bash) on top-severity survivors only.** Write a failing check in the scratch dir, run the project's test command, keep the finding only if the check **discriminates**. Budget-capped — this is the ~2x stage.

**Stage 4 — Completeness audit (Haiku).** Diff the ledger's covered-hunk set against all hunks; a second pass runs on the remainder. **Unmeasured — no technique with a published recall gain exists** — but it is cheap and it closes our known hole.

**Stage 5 — Fold (lead).** calimero's `consensus_score` clustering and severity floors verbatim (MIT); convergence halt on `new_findings == 0 AND fixed_findings == 0`; CRITICAL+SECURITY bypass the agreement filter. The lead holds the ledger, lane map and finding table — **never file bodies, never seat transcripts, never the diff twice**.

### What survives from our current reviewer
The per-hunk ledger (now *derived*), the lane concept (now cut by file cluster and sized to the band, not `ceil(hunks/150)`), both angle seats, the test seat, and one-message dispatch.
**What dies:** the lead's spot-check as the verification stage (it checks the quote, not the failure, and is same-model and anchored); "reads every body on the lane in full" (unsupported-to-harmful and it is where our money goes); fewer seats per line on big diffs; final judgment on the mid model.

### The smallest bake-off that would confirm it

1. **Mine labels.** Run **PySZZ** (`grosa1/pyszz_v2`) with **R-SZZ** (highest precision ~70–73%, best F1 ~0.64) over the repo's fix commits; B-SZZ or SZZUnleashed as a recall supplement. **Hand-verify every pair** — SZZ precision is ~70% at best, LLM4SZZ reaches only 40.7% on a curated set, and ~25% of bug-inducing commits are inherently untraceable by line tracing.
2. **Convert c-CRAB-style.** Per verified pair, build the environment, write a test that **fails at the pre-fix commit and passes at the post-fix commit**, then apply c-CRAB's validation gate: an independent agent must fix it from the issue text alone or the item is discarded. Expect c-CRAB's yield — **~27% survival from raw candidates** — so mine ~4x your target.
3. **Size it.** McNemar's test on paired pass/fail. **COMPUTED** from n = (z₀.₀₂₅√p_d + z₀.₂₀√(p_d − δ²))² / δ²: at discordance p₁₂=0.25/p₂₁=0.05 (δ=0.20) **n ≈ 57 pairs**; at 0.20/0.05 (δ=0.15) **n ≈ 85**. So **~60 validated bugs detects a 20pp swing at 80% power / α=0.05, ~85 for 15pp.** Below ~40 only very large differences are detectable. The discordance rate must come from a pilot — it is the real blocker on sizing.
4. **Score accuracy and noise together.** `Score = Recall × UsefulnessRate` — recall from the executable tests, usefulness from the fraction of emitted comments judged non-spurious. This follows CR-Bench's usefulness-rate / signal-to-noise framing ([OpenReview PDF](https://openreview.net/pdf?id=6RmpFMEeOX), now reachable) and deliberately rejects Greptile's method, which excludes false positives from scoring entirely. **The multiplicative form is our reconstruction, not CR-Bench's quoted equation.**
5. **Control the confounds.** Fix reasoning effort across arms (a public bake-off was invalidated by exactly this), log tokens and dollars per arm per item, and ablate one stage at a time — **verifier off**, **execution gate off**, **decomposition off** — because that is the only way to get the per-stage accuracy-per-token curve that nobody has published.
6. **Go-specific caveat:** **GoBench/GoKer** (82 real bugs from 9 projects + 103 kernels) is concurrency-only and carries **no explicit licence**; there is **no Defects4J for Go** and **no shell-script defect dataset at all** — so the shell and markdown portions of the repo have no external corpus and must be labelled by hand.
