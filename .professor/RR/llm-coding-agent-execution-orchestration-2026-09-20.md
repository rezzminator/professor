# RR — How do others execute and orchestrate LLM coding agents once the work is specified, and which workflows are most novel and most efficient?

Question: how do other people execute and orchestrate LLM coding agents once the work is specified — the "execution" half of an AI software development lifecycle — and which workflows are the most novel and the most efficient (measured in tokens, dollars, wall-clock, or success rate)?

---

## Answer

Your design is close to the industry's converged answer — fresh isolated executor per task, dependency-gated dispatch, single writer at the end — and the two mechanisms it is missing are both proven elsewhere: **atomic task claiming from a dependency graph** (Claude Code Agent Teams' file-locked claim; Beads' Dolt-backed `bd update --claim`) and a **guarded delivery/completion state machine** that distinguishes finished from blocked from stuck (agentmux's five-state FIFO; OpenHands' StuckDetector). The one place the evidence actually cuts against you is the cost model: fresh executors forfeit the prompt cache (Anthropic cache reads are 0.10x input, writes 1.25-2.0x), and nobody has ever measured fresh-session-per-subtask against one continuous session on a coding benchmark — the central claim of your design is unmeasured in the literature.

---

## The map

### 1. Where the field agrees with your design

**Fresh isolated executor per unit of work is universal.** Every production system dispatches a task into a clean, isolated environment: OpenAI Codex cloud gives each task a dedicated container with network disabled and returns a reviewable diff, with the human opening the PR ([Codex cloud docs](https://learn.chatgpt.com/docs/cloud)); GitHub Copilot coding agent takes a GitHub issue as its dispatch unit, runs in an ephemeral Actions-backed environment, works one branch at a time and opens exactly one draft PR ([GitHub docs](https://docs.github.com/copilot/concepts/agents/coding-agent/about-coding-agent)); Google Jules runs each task in its own Cloud VM behind a plan-approval gate ([Jules docs](https://jules.google/docs/tasks-repos/)); Cursor cloud agents use isolated Ubuntu VMs. The open-source tier does the same with git worktrees — Conductor, Claude Squad, Crystal, Vibe Kanban all bind one prompt to one worktree plus branch, and Composio's Agent Orchestrator (12.2k stars) makes the unit a "worker": one task, one agent, one worktree/branch ([ComposioHQ/agent-orchestrator](https://github.com/ComposioHQ/agent-orchestrator)). Dagger's container-use goes a layer further, giving each agent a fresh container bound to its own branch ([dagger/container-use](https://github.com/dagger/container-use)).

**Single-threaded writes is now the explicit doctrine, including from the loudest multi-agent skeptic.** Cognition's "Don't Build Multi-Agents" argued parallel subagents make conflicting implicit decisions because they share only summaries, not full traces ([Cognition](https://cognition.com/blog/dont-build-multi-agents)) — evidence anecdotal, a Flappy Bird demo, not benchmarked. Cognition then walked it back: multi-agent works when **writes stay single-threaded** and extra agents contribute intelligence rather than actions, and they now run manager-Devin/child-Devin map-reduce delegation ([Multi-Agents: What's Actually Working](https://cognition.com/blog/multi-agents-working)). Your single git-owning agent is exactly this discipline.

**Orchestrator-holds-only-the-index matches Anthropic's stated guidance.** "Building effective agents" names orchestrator-workers (lead decomposes, workers execute, lead synthesizes) as the right pattern when subtasks cannot be predicted in advance, and tells you to add agentic complexity only when simpler solutions fall short ([Anthropic](https://www.anthropic.com/engineering/building-effective-agents)).

**Blocking waits, not polling, is what the best implementations do.** Claude Code Agent Teams documents it outright: "when teammates send messages, they're delivered automatically to recipients. The lead doesn't need to poll for updates," with idle teammates auto-notifying the lead with their final answer ([Agent Teams docs](https://code.claude.com/docs/en/agent-teams)). OpenHands' `Conversation.run()` blocks synchronously until a `FinishAction`, stuck-detection or budget exhaustion; delegated sub-agents run as parallel threads with independent EventLogs while the parent blocks. Composio's orchestrator uses an event-driven daemon watching agent and source-control state, not a poll loop.

### 3. Novelty ranking — the mechanisms worth studying

1. **Beads: the dependency graph as a version-controlled database.** Dolt-backed distributed issue tracker giving agents ready-work discovery by query (no open blockers), **atomic claiming** via `bd update --claim` (race-free, unlike editing a file), automatic blocker release by relational cascade when a dependency closes, full audit trail, and cross-machine sync with cell-level merge ([gastownhall/beads](https://github.com/gastownhall/beads)). This is a strict upgrade over a plain directory of task files plus an index on exactly the axes your design needs.
2. **agentmux's delivery state machine.** Per-pane single-writer FIFO with an explicit five-state lifecycle `pending → pasting → drafted → submitted → acknowledged | delivered_unverified`, where a 60-minute unconfirmed delivery becomes a terminal **fence** state that is never blindly retried (avoiding double-paste corruption) and escalates instead; state detection prefers harness hooks pushing JSON to `~/.agentmux/events.jsonl` over terminal scraping, under the rule that "a pushed event may only refine a scraped idle/unknown, never contradict a live observation" ([agentmux](https://github.com/adelost/agentmux)). The most rigorous "did it finish or is it stuck" design found anywhere.
3. **Claude Code Agent Teams' mailbox.** Literal path `~/.claude/teams/{team}/inboxes/{agent}.json`; entries validated on read with malformed ones stripped and reported; a send counts as successful only when the recipient's file write succeeds, so nothing is silently dropped; task self-claim uses **file locking**; `TeammateIdle` is the report-once signal. Documented limits: no session resumption for in-process teammates, status lag ("teammates sometimes fail to mark tasks as completed"), no nested teams, token cost "scales linearly" per teammate, start with 3-5 ([Agent Teams docs](https://code.claude.com/docs/en/agent-teams)).
4. **Cognition's clean-context reviewer.** A reviewer agent with no inherited history reviewing the coder's PR — the architectural insight being that review quality depends on *not* sharing the author's context. (The "~2 bugs/PR, 58% severe" figure is a **vendor claim with no sample size or methodology**, not a measurement.)
5. **Ralph loop / Antfarm: progress lives outside the agent.** `while :; do cat PROMPT.md | claude-code; done` — the prompt file replays verbatim each iteration and all state lives in files on disk plus git history, so a fresh agent resumes without inheriting context. Bare Ralph has **no termination condition** beyond a human hitting Ctrl-C; packaged variants stop when every story reads `passes: true` or a max-iteration cap fires. No quantitative measurements exist for it.
6. **OpenHands' typed event architecture.** Stateless agent emitting `Action` objects into an append-only `EventLog`, blocking `Conversation.run()`, LLM-scored action risk tiers (LOW/MEDIUM/HIGH) with a `ConfirmRisky` pause policy, and a `StuckDetector` watching five patterns (4+ identical actions, 3+ error cycles, 3+ consecutive agent messages, 6+ action-observation ping-pong, context-window errors) via semantic rather than identity comparison ([OpenHands docs](https://docs.openhands.dev/sdk/guides/agent-stuck-detector)).
7. **A2A's task lifecycle as a formal contract.** Eight states (submitted, working, input-required, auth-required; completed, failed, canceled, rejected), three delivery patterns (poll `GetTask`, SSE `SubscribeToTask`, webhook push), a `returnImmediately` flag toggling blocking vs async, results returned as **Artifacts separate from messages**, and `SubscribeToTask` required to emit the current snapshot as its first event so reconnection never loses state ([A2A spec](https://a2a-protocol.org/latest/specification/), [streaming topics](https://a2a-protocol.org/latest/topics/streaming-and-async/)). Retry, idempotency and webhook-ack semantics are **not defined** — reliability is pushed onto implementers.

### 4. Cross-harness dispatch — what is actually documented

- **Codex CLI** has the richest native contract: `codex exec "<task>"` (or `-` for stdin), `--json` streaming JSONL (`thread.started`, `turn.started`, `item.started`/`item.completed`, `turn.completed` carrying `usage`), `--output-schema <path>` enforcing a JSON Schema on the final response, `-o/--output-last-message <path>`, `codex exec resume --last | <SESSION_ID>`, `--ephemeral`, and `--sandbox read-only|workspace-write|danger-full-access`. Completion = the `turn.completed` event. **Exit codes are not documented** ([Codex non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode)).
- **OpenCode** offers the cleanest blocking primitive: `opencode serve` (default `127.0.0.1:4096`, OpenAPI 3.1), `POST /session` then `POST /session/:id/message` which **blocks and returns the full structured `Message` + `Part[]`** — result received means done; `POST /session/:id/prompt_async` is fire-and-forget returning 204 ([OpenCode server docs](https://opencode.ai/docs/server/)).
- **Claude Code**: `-p/--print`, `--output-format stream-json`, `--include-partial-messages`, `--resume/-r <session-id>`, `--fork-session`; exit 0 success / 1 failure. The **terminal event type inside the stream-json stream is not documented**, and `claude mcp serve` does not appear on the primary CLI reference at all — treat "Claude Code as an MCP server" as community-reported, unverified.
- **Hooks**: `SubagentStop` (`agent_id`, `agent_type`, `last_assistant_message`) **cannot block**; `Stop` **can block via exit code 2** to keep the agent working, with no documented retry bound; `TeammateIdle` is informational only; `SessionEnd` carries a `reason` and shares a 1.5s budget ([hooks reference](https://code.claude.com/docs/en/hooks)).
- **MCP elicitation/sampling**: `elicitation/create` (`message`, flat `requestedSchema`) returns `accept`/`decline`/`cancel`; `sampling/createMessage` returns `{role, content, model, stopReason}`. **Neither spec page defines timeout or cancellation** — a server blocks by protocol design and the duration contract is yours to define ([elicitation](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation), [sampling](https://modelcontextprotocol.io/specification/2025-06-18/client/sampling)).
- **NOTHING FOUND**: no case study of one orchestrator driving mixed-vendor executors with wall-clock, cost or success numbers. Only same-task-different-harness comparisons exist. Devin's manager-child "internal MCP" is a single marketing sentence with no published schema.

### 5. The cost model, honestly

Your claim — context only grows, every call re-sends it, so fresh executors win — is **supported on the quality axis and contested on the cost axis**.

Supporting: the 39% multi-turn drop, the coding-specific 8/10→3/10 degradation, Chroma's universal pre-window degradation, LangWatch's 250x-cost-for-8x-window power law, and ContextRot's finding that models increasingly terminate prematurely as context grows ([arXiv:2606.29718](https://arxiv.org/abs/2606.29718)).

Contesting: Anthropic cache reads cost **0.10x** input with writes at 1.25x (5-min TTL) or 2.0x (1-hour), default TTL 5 minutes ([Claude docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)); OpenAI caches automatically above a 1,024-token stable prefix at roughly 50% with retention up to 24 hours ([OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)). Per call, a long-running agent inside the TTL is cheaper; a fresh executor pays cold prefill every time. Working that arithmetic through is **our inference from unit prices, not a measured head-to-head**.

Complicating both: ContextRot found sub-agent context isolation is the **best** mitigation for the strongest model tested (Qwen3.5) and **among the worst** for a weaker one (GLM-4.7), where keep-latest-with-summarization won — isolation's benefit is model-dependent, not universal. And compaction recovers some of what isolation buys: OpenHands' `LLMSummarizingCondenser` self-reports up to 2x cost reduction "with no degradation," while a third-party analysis claims Claude Code's auto-compact retains only ~20-30% of original detail (**unverified, third-party blog**).

**The decisive experiment has never been run.** No source measures fresh-session-per-subtask against one continuous session on a coding benchmark for cost, wall-clock or resolve rate. That is the single biggest evidence gap under your design.

### 6. What nobody has solved

- **Port, test-database and build-cache collisions across concurrent agents.** Not one surveyed tool — Conductor, Claude Squad, Crystal, Vibe Kanban, Composio AO, container-use — documents this; container-use isolates at the container-and-branch level and delegates the rest downward. The only documented schemes are practitioner-level: slug-derived port allocation, one schema or disposable container per agent, unique Compose project names (which namespace containers/networks/volumes but **not fixed host ports**), per-agent artifact directories, and read-only shared caches for mutation-safe tools ([Matrix OS](https://matrix-os.com/blog/avoid-parallel-agent-port-database-conflicts), [Docktree](https://docktree.dev/)). Your index naming shared resources per task is ahead of the tooling here.
- **Semantic conflicts.** AgenticFlict measures them and names them — code that merges and builds yet contains logical contradictions Git cannot catch — but proposes only unmeasured "Integration Guard" patterns. Your single standing-checks pass after the last task is the layer that catches the build-level subset.
- **Stuck detection accuracy.** No published false-positive rate for OpenHands' StuckDetector; its thresholds (4/3/6) appear hand-picked, and real issues document agents killed while legitimately waiting on long-running processes ([#5355](https://github.com/OpenHands/OpenHands/issues/5355)).
- **Where a cap should sit.** Copilot's hard, non-configurable 59-minute cap has no documented recovery path; OpenHands' cap fires as a generic `ERROR` indistinguishable from infrastructure failure, with no chance to synthesize partial work, and subagents with unset limits can drain a parent's budget ([issue #2406](https://github.com/OpenHands/software-agent-sdk/issues/2406)). **No data exists anywhere** on how often an agent that has not finished by iteration N would have finished.
- **Retry-fresh vs continue-same-agent after failure.** NOTHING FOUND as a direct measurement. Nearest proxy, secondhand and unfetched: "chat-only recovery" scoring 8-13% correctness vs 100% for semantics-aware checkpoint/restore on Terminal-Bench.
- **Blocker-triggered re-planning.** DynTaskMAS' Adaptive Workflow Manager re-optimizes a DAG on performance metrics, but that is scheduling optimization on a non-coding toy task, not graph revision in response to a reported blocker. No measurement isolates the benefit.
- **Review granularity for agent diffs.** No agent-specific study compares one combined diff against per-task review. The human literature (SmartBear/Cisco 200-400 LOC band) implies a large combined diff falls outside the high-yield detection window — flagged as an **extrapolation**, not a finding.
- **Merge order effects.** Only practitioner anecdote (merge tax exceeding safe-merge infrastructure cost past ~5 parallel agents), no controlled study.
- **Coding-specific multi-agent token multiplier.** Anthropic's 15x figure is verified at source but is cross-domain research-workload data, and the same post says "most coding tasks involve fewer truly parallelizable tasks than research." No independent coding replication exists.

## The five ideas most worth adopting

1. **Make task claiming atomic, not file-based.** Beads' `bd update --claim` over a version-controlled graph, or Agent Teams' file-locked claim, removes the race your index-plus-directory has by construction, and gives cascade-on-close blocker release for free instead of a re-scan. This is the single highest-value borrow.
2. **Give the executor an explicit delivery/completion state machine with a terminal fence.** agentmux's `pending → … → acknowledged | delivered_unverified` with a never-blindly-retried fence state, plus the rule that a pushed hook event may refine but never contradict a live observation, solves "finished vs blocked vs stuck" far better than behavioural heuristics. Prefer a sentinel/exit-code/structured-final-message signal from the executor over StuckDetector-style pattern matching, which has no published accuracy.
3. **Route by decomposability, not by convenience.** The Google scaling result (+80.8% decomposable, −70.0% sequential) and the cohesion-partitioning result (+60% cost for +3.2% pass rate when files share contracts) both say the same thing: fan out only genuinely independent, file-disjoint task files, and keep a tightly coupled chain inside one executor. Your index already carries the dependency data to enforce this — make it a dispatch rule, not a hint.
4. **Keep the reviewer's context clean and the review chunk small.** Cognition's clean-context reviewer plus the SmartBear 200-400 LOC band argue against one review pass over a large combined diff. Given the habituation evidence (+14.5pp approval, 3.5x latency, −22% inspection effort), add a risk threshold that escalates only some diffs to a human, and let an agent reviewer triage the rest.
5. **Treat the difficulty rating as a soft prior and instrument real cost.** Pre-execution difficulty prediction correlates only ~0.39 in-distribution and ~0.225 out-of-distribution, and identical tasks vary up to 30x in tokens — so never route on a single run's cost, report P90 rather than means, and exploit repeated sampling (15.9%→56%) only on task files that carry a real verifier. Cascade economics (FrugalGPT's up to 98.3%) are promising but unvalidated for coding escalation.

## Rabbit holes left open

**Unmeasured, load-bearing:** fresh-session-per-subtask vs one continuous session on a coding benchmark (the core claim of the design); retry-with-a-fresh-agent vs continue-the-same-agent after failure; where an iteration/budget cap should sit; blocker-triggered re-planning benefit; combined-diff vs per-task review for agent code; rework cost by merge order; a coding-specific multi-agent token multiplier.

**Verification debt:** swebench.com's leaderboard is JS-rendered and returned no numbers (SOURCE UNREACHABLE) — current top resolve rates and any cost-per-instance are unconfirmed; the Claude Code 32% / Aider 82% revert-rate figures were traced to plausible ratios (0.68x, 0.18x) but the primary study was never fetched (PARTIALLY VERIFIED); `claude mcp serve` is absent from Anthropic's own CLI reference; `codex exec` exit codes and the terminal event type in Claude Code's stream-json are undocumented; whether `--output-format stream-json` truly requires `--verbose` is secondary-source only; Chroma's per-model degradation onset thresholds were not pulled from a direct primary fetch; ContextRot's exact accuracy deltas were stripped by HTML extraction; the "~20-30% detail survives Claude Code compaction" figure is an unverified third-party blog claim.

**Vendor claims, never measurements:** Devin's 13.86% SWE-bench rate (self-published, contamination-flagged by Cognition itself, rising to 23% when given the hidden tests); Devin Review's "~2 bugs/PR, 58% severe" (no sample size or design); Cursor's "35% of internally-merged PRs from agents" and ">30% merge rate"; Jules' concurrency tiers; OpenHands' "2x cost reduction with no degradation" from its own condenser; every parallelism cost/speedup ratio in practitioner blogs ("3 agents in 1/3 the time", "1.5-2x cost for 1/4 time", "5-7 agents comfortable", "~10 diffs/hour reviewable").
