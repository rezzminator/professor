# RR — How mature projects release software adopters update, and how to write release notes an (AI) upgrader can execute across skipped versions

Question: Heavy RR: how mature projects release software that ADOPTERS UPDATE — the end-to-end release flow, and above all how release notes are written so an upgrader (increasingly an AI agent acting for the upgrader) can carry out every migration action correctly across one or many skipped versions. (Full brief: 9 questions — release pipelines of Rust/Go/Kubernetes/Node/Python/Homebrew/Terraform/Angular/Nx/Rails/template updaters/dotfile frameworks; release notes for upgraders; when/who writes notes; empirical research incl. LLM-generated notes; upgrade rehearsal and docs-as-tests; reviewing a very large release diff; post-publish verification; version-bump decisions; agentic/LLM release tooling — plus a ranked "What to steal" list.)

## Answer

The mature pattern is to write upgrade notes at change time as typed fragments. Kubernetes, Go, OpenStack reno, towncrier, changesets, CPython blurb and HashiCorp go-changelog all do this, and CI enforces it: Go's tooling flags missing notes, and go-changelog ships a PR check. Each action is tied to the surface it touches and marked as needed before or after the upgrade (Kubernetes "Urgent Upgrade Notes", reno "upgrade", Mattermost and Elastic "before upgrading"). Wherever possible the action ships as a runnable, version-gated migration (Nx migrations.json, Angular schematics, OpenRewrite composite recipes, copier `_migrations`), with prose kept for what cannot be automated. Across skipped versions, projects either forbid skipping (k8s kube-apiserver, GitLab required stops, Nx/Rails/Django "one step at a time") or merge only the entries inside the from→to range (Renovate, changelogd, the Angular Update Guide's data model). The evidence says notes most often fail by omission, especially of breaking changes (Wu et al. 2022). LLMs capture the "what" better than the "why", and no study yet measures hallucination rates in LLM-written changelogs.

Evidence strength tags: **[D]** documented practice, **[M]** measured study, **[A]** anecdote or single-source claim. `unquoted` = no verbatim quote backs it.

## Q1. End-to-end release pipelines

### Rust
- **[D]** A six-week train (nightly→beta→stable). "Both promotions should happen on Monday… prioritize landing the stable promotion first"; "As of September 2024 a release takes between 75 and 90 minutes to complete"; only "authorized members of the release team can invoke" `start-release.py` ([forge release process](https://forge.rust-lang.org/release/process.html)).
- **[D]** Crater is the ecosystem rehearsal. It works by "building a large number of crates, running their test suites and comparing the results between two versions of the Rust compiler" ([crater README](https://github.com/rust-lang/crater)). Timing: "A crater run for beta should be started as soon as we have beta out", and confirmed regressions are filed as issues with "the `regression-from-stable-to-beta` and `T-compiler` label by default" ([forge crater](https://forge.rust-lang.org/release/crater.html)). Ownership: "beta runs should be triaged by the release team, and PR runs should be triaged by the people involved in that PR" ([report-triage.md](https://github.com/rust-lang/crater/blob/master/docs/report-triage.md)).
- **[D]** Staged publish: the "dev-static step… runs on the Monday and the production step… on the Thursday, so the artifacts are reachable for up to three days before release", and can be tested with `RUSTUP_DIST_SERVER=https://dev-static.rust-lang.org rustup update stable` ([forge release process](https://forge.rust-lang.org/release/process.html)).
- **[D]** Release notes carry a "Compatibility Notes" section, e.g. v0 symbol mangling "may cause some tools… to fail to demangle symbols" ([Rust releases](https://doc.rust-lang.org/beta/releases.html)).

### Go
- **[D]** "Go is released every six months… a development phase lasting about 4 months, followed by a 3-month period of testing and polishing called the release freeze"; "During the freeze, only bug fixes, test-only changes, and doc updates are accepted" ([Go release cycle](https://go.dev/wiki/Go-Release-Cycle)).
- **[D]** Notes are written during development: "Release notes should be added to `next` by editing existing files or creating new files. **Do not add RELNOTE=yes comments in CLs.**" "Files in this repo's `api/next` directory must have corresponding files in `doc/next/*stdlib/*minor`." "If an accepted proposal is mentioned in a CL but not in the release notes, it will be flagged as a TODO by the automated tooling." "The files will be merged by being concatenated in sorted order by pathname." ([golang/go doc/README.md](https://github.com/golang/go/blob/master/doc/README.md))
- **[D]** Behavior changes are gated by GODEBUG: "GODEBUG settings added for compatibility will be maintained for a minimum of two years (four Go releases)" ([go.dev/doc/godebug](https://go.dev/doc/godebug)).

### Kubernetes
- **[D]** PR-level notes: "For pull requests that require additional action from users switching to the new release, include the string 'action required' (case insensitive) in the release note"; "Write your release notes in the past tense"; "Reviewing the release notes of a pull request should be a dedicated step in the overall review process" ([k8s release-notes guide](https://github.com/kubernetes/community/blob/master/contributors/guide/release-notes.md)).
- **[D]** A release notes team edits the notes: "It is recommended that the team splits the work among all members and runs the editing flow on a weekly or biweekly basis" (handbook read via a fork mirror because upstream returned 404: [sig-release handbook mirror](https://github.com/sanchita-07/sig-release/blob/master/release-team/role-handbooks/release-notes/README.md)). `krel release-notes` "can be used to generate release notes pull requests to update the Release Notes Draft and the Kubernetes Release Notes Website" ([krel release-notes](https://github.com/kubernetes/release/blob/master/docs/krel/release-notes.md)).
- **[D]** Output structure: the CHANGELOG has an "Urgent Upgrade Notes — (No, really, you MUST read this before you upgrade)" section, e.g. "ACTION REQUIRED: Graduated the `SELinuxMount` feature gate to GA… which may break existing workloads" ([CHANGELOG-1.37](https://github.com/kubernetes/kubernetes/blob/master/CHANGELOG/CHANGELOG-1.37.md)).
- **[D]** Freeze authority: "Adding the in-progress release milestone to pull requests after the Code Freeze is strictly prohibited" ([release-team README](https://github.com/kubernetes/sig-release/blob/master/release-team/README.md)). Release-blocking CI: jobs "should block that release if they do not have at least three successive 'green' runs at go/nogo decision time" ([release-blocking-jobs.md](https://github.com/kubernetes/sig-release/blob/master/release-blocking-jobs.md)).
- **[D]** Skipping versions is forbidden: "require `kube-apiserver` to not skip minor versions when upgrading, even in single-instance clusters"; "`kubelet` may be up to three minor versions older than `kube-apiserver`" ([version skew policy](https://kubernetes.io/releases/version-skew-policy/)).

### Node.js
- **[D]** "New Node.js Major releases happen once per year: Branch-off is in October. Semver-major release is in April." Release proposal PRs "should be left open for at least 24 hours". After promotion: "Your release should be available at `https://nodejs.org/dist/vx.y.z/`… Check that the appropriate files are in place", plus checks on `index.json`/`index.tab` ([releases.md](https://github.com/nodejs/node/blob/main/doc/contributing/releases.md)).
- **[D]** "The Node.js project uses citgm to smoke test our releases and controversial changes" ([CITGM](https://github.com/nodejs/citgm)).

### Python (PEP 101)
- **[D]** "Most of the steps are now automated or guided by automation"; notes are assembled with "`blurb release <version>`… This merges all the recent news blurbs into a single file"; post-build: "Verify! Pretend you're a user: download the files from www.python.org, and make Python from it." ([PEP 101](https://peps.python.org/pep-0101/)). Blurb exists "to rid CPython core development of the scourge of Misc/NEWS conflicts" ([blurb](https://github.com/python/blurb)).
- **[D]** Downstream rehearsal: Fedora rebuilds "~4000 known packages" against Python betas: "By building Fedora's packages against 3.13 while it's still in development, we can catch critical bugs before the final 3.13.0 release" ([Fedora Changes/Python3.13](https://fedoraproject.org/wiki/Changes/Python3.13)).

### Homebrew
- **[D]** "Homebrew users receive new versions of Homebrew/brew from GitHub release tags. Only maintainers with write access to Homebrew/brew can create a release." ([Releases](https://docs.brew.sh/Releases)). Formula CI: "every formula change must at least build successfully in the required BrewTestBot jobs" ([maintainer guide](https://docs.brew.sh/Homebrew-homebrew-core-Maintainer-Guide)).

### Terraform / HashiCorp
- **[D]** "you should be able to upgrade from any v1.x release to any later v1.x release"; "We aim to make upgrades between v1.x releases straightforward, requiring no changes to your configuration, no extra commands to run upgrade steps" ([v1 compatibility promises](https://developer.hashicorp.com/terraform/language/v1-compatibility-promises)).
- **[D]** PR-time fragments: "a PR would include a `.changelog/PR#.txt` file", with a "`changelog-check` binary… to show how a GitHub PR can be checked to ensure that a changelog entry is attached" ([go-changelog](https://github.com/hashicorp/go-changelog/blob/main/README.md)).

### Angular, Nx, Rails (migration-running updaters)
- **[D]** Angular `ng update`: `--migrate-only` means "Only perform a migration, do not update the installed version"; `--to` is the "Version up to which to apply migrations… Requires 'from' to be specified" ([ng update](https://angular.dev/cli/update)). The Update Guide's data entries carry `possibleIn`/`necessaryAsOf` version keys; the from→to filter is inferred from that data, not read from docs (`unquoted`; [archived update-guide repo](https://github.com/angular/angular-update-guide)).
- **[D]** Nx: "Updating one major version at a time is the safest path and is what Nx recommends"; "Generator-based changes run first, and the agent validates the results"; "Nx creates a commit for each migration while the agentic flow is enabled, so the agent reviews each migration's changes in isolation" ([Nx automate updating](https://nx.dev/docs/features/automate-updating-dependencies)). `migrations.json` "You can modify migrations.json and run this command many times" ([nx migrate](https://nx.dev/reference/core-api/nx/documents/migrate)).
- **[D]** Rails: "it's best to move slowly, one minor version at a time, in order to make good use of the deprecation warnings"; `app:update` runs "in an interactive session"; new framework defaults can be enabled "gradually over several deployments" ([Rails upgrading guide](https://guides.rubyonrails.org/upgrading_ruby_on_rails.html)).

### Template / scaffold updaters (closest analog to "scaffolded once, then owned")
- **[D]** copier does a real three-way update: it "compares both version to get the diff from 'fresh project' to 'current project'… it re-applies the previously obtained diff and then runs the post-migrations"; never edit `.copier-answers.yml` because "This will trick Copier" ([copier updating](https://copier.readthedocs.io/en/stable/updating/)).
- **[D]** cruft stores "the git hash of the template used as well as the template variables", and files can be skipped ([cruft](https://github.com/cruft/cruft)).
- **[D]** projen takes the opposite stance: "Synthesized files should never be manually edited (in fact, projen enforces that)"; "an 'anti tamper' check is configured in the CI build workflow" ([projen](https://github.com/projen/projen)).
- **[D]** Backstage's Upgrade Helper gives "a consolidated view of all the changes between two versions of Backstage" for template-created files ([Backstage keeping updated](https://backstage.io/docs/getting-started/keeping-backstage-updated/)). This is the closest match to a per-file diff report the adopter applies by hand.

### Dotfile/editor frameworks
- **[D]** LazyVim: "When enabled, NEWS.md will be shown when changed. This only contains big new features and breaking changes." ([LazyVim config](https://www.lazyvim.org/configuration)).
- **[D]** oh-my-zsh `upgrade.sh` runs `changelog.sh` only in interactive, default-verbosity mode; otherwise it prints "You can see the changelog with `omz changelog`" ([upgrade.sh](https://github.com/ohmyzsh/ohmyzsh/blob/master/tools/upgrade.sh)).
- **[A]** Doom Emacs announces breaking changes informally: "Keep an eye on the #announcements channel, where I announce breaking updates" ([Doom Emacs](https://github.com/doomemacs/doomemacs)). No source found showing `doom upgrade` displaying a changelog.
- **[D]** chezmoi `upgrade` "will call the GitHub API to determine if there is a new version" ([chezmoi upgrade](https://www.chezmoi.io/reference/commands/upgrade/)). The page does not say whether notes are shown.

## Q2. Release notes for upgraders — structure, before/after, ranges, executability

- **[D]** Separate sections for actions: reno defines "Upgrade Section: A list of upgrade notes in the release. For example, if a database schema alteration is needed", and "Deprecations should not be used for something that is removed in the release, use upgrade section instead" ([reno usage](https://docs.openstack.org/reno/latest/user/usage.html)). Keep a Changelog: Added/Changed/Deprecated/Removed/Fixed/Security plus an "Unreleased" section ([keepachangelog 1.0.0](https://keepachangelog.com/en/1.0.0/)).
- **[D]** Before/after split, tied to surfaces: Mattermost writes conditional items per surface, e.g. "Before upgrading, FIPS deployments should verify that the password in `SqlSettings.DataSource` is at least 14 characters", and flags downgrade hazards ([Mattermost Important Upgrade Notes](https://docs.mattermost.com/upgrade/important-upgrade-notes.html) — the digger cited this at domain level). Elastic: "You must address the reported issues before upgrading to the next major version"; "run 8.19.latest, and run the assistant there" before 9.x ([Elastic Upgrade Assistant](https://www.elastic.co/guide/en/kibana/current/upgrade-assistant.html) — the digger cited this at domain level). Django: "Before upgrading, it's a good idea to resolve any deprecation warnings raised by your project while using your current version" ([Django upgrade](https://docs.djangoproject.com/en/6.0/howto/upgrade-version/)).
- **[D]** Skipped versions, sequencing: GitLab "required upgrade stops… versions of GitLab that you must upgrade to before upgrading to later versions"; since 17.5 they fall at "`x.2.z`, `x.5.z`, `x.8.z`, and `x.11.z`"; "Allow the background migrations for the upgrade to finish" before the next stop ([GitLab upgrade paths](https://docs.gitlab.com/update/upgrade_paths/)). Its tool computes the stops for a current→target pair: "This assumes a default conservative approach. You may not need every step." ([upgrade-path tool](https://gitlab-com.gitlab.io/support/toolbox/upgrade-path/)). Django: "upgrade through each feature release incrementally… For each feature release, use the latest patch release" ([Django](https://docs.djangoproject.com/en/6.0/howto/upgrade-version/)).
- **[D]** Skipped versions, merging only the range: Renovate builds its changelog by "Filtering the found releases to only include those versions being updated by the current PR" ([Renovate changelogs](https://docs.renovatebot.com/key-concepts/changelogs/)). changelogd prints "a diff of CHANGELOG's between versions" via `--from/--to` ([changelogd](https://github.com/harlan-zw/changelogd)). Dependabot PRs include "release notes, changelog entries, and commit details" ([Dependabot](https://docs.github.com/en/code-security/dependabot/dependabot-version-updates/about-dependabot-version-updates)), but whether every intermediate version is covered is not stated.
- **[D]** Executable migrations: OpenRewrite `UpgradeSpringBoot_3_0` "will also chain additional framework migrations… required as part of the migration to Spring Boot 2.7", and its first step is "Migrate to Spring Boot 2.7". The composite recipe per version already contains the earlier hop ([OpenRewrite](https://docs.openrewrite.org/recipes/java/spring/boot3/upgradespringboot_3_0-community-edition)). Nx migrations can be generator-only, prompt-based ("AI-aided changes that can't be expressed deterministically") or hybrid ([Nx](https://nx.dev/docs/features/automate-updating-dependencies)); `agentContext` "only reaches an AI agent" ([Nx migration generators](https://nx.dev/docs/kb/migration-generators)). Svelte's `sv migrate` marks unfinished work: "annotate your codebase with tasks for completion that you can find by searching for `@migration`" ([sv migrate](https://svelte.dev/docs/cli/sv-migrate)). Tailwind's upgrade tool "can only be run on v3 projects" because some transforms are unsafe to re-run ([tailwind #15080](https://github.com/tailwindlabs/tailwindcss/discussions/15080)). This is the idempotency lesson.
- **[D]** Notes written for AI readers: Next.js writes a managed `AGENTS.md` block: "This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/`… before writing any code. Heed deprecation notices." "[Upgrading Next.js] also upgrades the bundled docs." It adds that benchmarks "show that always-available context outperforms on-demand retrieval" ([Next.js AI agents](https://nextjs.org/docs/app/guides/ai-agents)).

## Q3. When and who writes notes

- **[D]** At PR time: changesets — "A changeset is a Markdown file with YAML front matter… the YAML front matter describes what packages have changed and what semver bump types they should be" ([changesets](https://github.com/changesets/changesets/blob/main/docs/detailed-explanation.md)). towncrier — "towncrier delivers the news which is convenient to those that hear it, not those that write it" ([towncrier](https://github.com/twisted/towncrier)). k8s PR blocks, Go doc/next, go-changelog and blurb are covered in Q1.
- **[D]** At release time, derived: release-please "examines git history for 'Conventional Commit messages'", maintains a release PR and tags on merge ([release-please](https://github.com/googleapis/release-please)). GitHub's generated notes group PRs by label via `.github/release.yml` ([GitHub docs](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)).
- **[D/A]** Tradeoff evidence: "Using commit log diffs as changelogs is a bad idea: they're full of noise" ([keepachangelog 1.0.0](https://keepachangelog.com/en/1.0.0/)). "Git commit messages and changelogs do not have the same target audience" ([agateau 2022](https://agateau.com/2022/your-git-log-is-not-a-changelog/)). Merge conflicts drove CPython to fragments (blurb, above). Go's fragment rule plus TODO flagging is the mechanism that prevents omissions.
- **[M]** Omission is the measured failure (Q4, Wu et al.), which favors enforced, per-change fragments over reconstructing notes at release time.

## Q4. Empirical research

- **[M]** Bi, Xia, Lo, Grundy, Zimmermann (TSE 2022) studied "32,425 release notes in 1,000 GitHub projects", identified "eight categories of information", ran "interviews with 15 professionals and an online survey with 314 respondents", and found "significant discrepancies between release note producers and users" ([preprint](https://xin-xia.github.io/publication/tse207.pdf)). UNCHECKED at step 6: the PDF was unreadable to the checker; the digger quoted it from the harvester copy.
- **[M]** Abebe, Ali, Hassan (EMSE 2016): "most release notes list only a selected number of addressed issues (i.e., 6-26 % of all addressed issues in a release)"; inclusion is predictable "with an average precision of 84 % and an average recall of 90 %" ([Springer](https://link.springer.com/article/10.1007/s10664-015-9377-5)).
- **[M]** ARENA (FSE 2014): based on "1,000 existing release notes"; "53 participants"; generated notes "often include important information that is missing in the manually produced release notes" ([ACM](https://dl.acm.org/doi/10.1145/2635868.2635870)).
- **[M]** Wu et al. (ICPC 2022): "1,731 latest GitHub issues"; "nearly half (48.47%) of them focus on Production"; "RN producers are more likely to miss information than to include incorrect information, especially for breaking changes"; many users find notes inaccessible "due to link deterioration, lack of notification" ([ACM](https://dl.acm.org/doi/10.1145/3524610.3527919)). UNCHECKED at step 6 (HTTP 403).
- **[M]** Breaking changes: Raemaekers et al. found "around one third of all releases introduce at least one breaking change" ([TU Delft PDF](https://pure.tudelft.nl/ws/files/19482719/TUD_SERG_2016_011_cc.pdf)). **DISPUTED** by the Ochoa et al. replication (EMSE 2022): "119,879 library upgrades and 293,817 clients… 83.4% of these upgrades do comply with semantic versioning… only 7.9% of all clients are affected by BCs" ([Springer](https://link.springer.com/article/10.1007/s10664-021-10052-y); UNCHECKED at step 6 because of an auth redirect).
- **[M]** Bogart et al. (TOSEM 2021, 18 ecosystems): norms for breaking changes "shift the costs of using and maintaining the software among stakeholders" ([ACM](https://dl.acm.org/doi/10.1145/3447245)).
- **[M]** Kula et al.: "81.5% of the studied systems still keep their outdated dependencies"; "69% of the interviewees claim that they were unaware of their vulnerable dependencies" ([arXiv 1709.04621](https://arxiv.org/abs/1709.04621)).
- **[M]** LLM-written notes. SmartNote (FSE 2025) scored completeness 4.00 against 3.71 for the original human notes and 2.74 for Conventional Changelog. Its failure modes include "Verbose Results for Simple Changes" (a 36-line note for one simple change) ([arXiv html 2505.17977](https://arxiv.org/html/2505.17977)). For commit messages, LLMs "generally score higher in terms of the 'What' aspect than the 'Why' aspect", because they "can hardly capture the motivation behind code diffs" ([arXiv 2404.14824](https://arxiv.org/html/2404.14824v2)). ReleaseEval found LLMs beat baselines but are "still struggling on diff2sum" ([arXiv 2511.02713](https://arxiv.org/abs/2511.02713)). One industrial LLM release-summary paper admits: "We have not conducted a controlled study measuring the factual accuracy or completeness of the LLM-generated summaries" ([arXiv 2603.14619](https://arxiv.org/html/2603.14619v1)).
- **[M]** Documentation drift: "README updates empirically occur in only 0.8% of the 4.4 million PRs analysed"; the best LLM reached "User-Facing Accuracy: 28.7%" ([arXiv 2603.00489](https://arxiv.org/html/2603.00489v1)).
- **[M]** Do agents benefit from change docs? CodeUpdateArena: "prepending documentation of the update to open-source code LLMs… does not allow them to incorporate changes for problem solving". Gains were small, e.g. DeepSeek-Coder-v1.5 UPass@1 went from 3.2 to 11.8 ([arXiv html 2407.06249](https://arxiv.org/html/2407.06249)). MigrationBench: "71.67% and 53.33% success rate (pass@1) for minimal and maximal migration" with Claude-4.5-Sonnet ([arXiv 2505.09569](https://arxiv.org/abs/2505.09569)). GitChameleon: "GPT-4o achieves a pass@10 of only 39.9% (43.7% when provided with error feedback)" ([arXiv 2411.05830](https://arxiv.org/abs/2411.05830)). A dependency-upgrade agent that uses "migration documentation" reports "a precision of 71.4%", with no ablation isolating what the documentation contributed ([arXiv 2510.03480](https://arxiv.org/abs/2510.03480)).

## Q5. Upgrade rehearsal and docs-as-tests

- **[D]** Ecosystem rehearsals: crater (Q1), CITGM (Q1), and the Fedora mass rebuild (Q1). TypeScript's "test top100" "runs the top 100 TypeScript repos on GitHub, by stars, against the PR and against main" ([TypeScript bot](https://github.com/microsoft/TypeScript/wiki/Triggering-TypeScript-Bot)).
- **[D]** Upgrade testing: Debian piuparts "tests .deb packages by installing, upgrading, and removing packages in a minimal Debian chroot" and "is run constantly on all suites" ([piuparts](https://wiki.debian.org/piuparts)). pg_upgrade: "You can use pg_upgrade --check to perform only the checks, even if the old server is still running"; rollback depends on the mode, and once the new cluster has started in link mode "it is unsafe to use the old cluster" ([pg_upgrade](https://www.postgresql.org/docs/current/pgupgrade.html)). kubeadm upgrade e2e jobs alert after "4 failed runs" ([kubeadm e2e](https://github.com/kubernetes/kubeadm/blob/main/docs/managing-e2e-tests.md)).
- **[D]** Docs as tests: "Each doc is a test suite, each procedure a test case, each step an assertion" ([Docs as Tests](https://www.docsastests.com/docs-as-tests/concept/2024/01/09/intro-docs-as-tests.html)). Doc Detective "performs your instructions step-by-step, just like your users would, and reports what works and what doesn't" ([Doc Detective](https://docs.doc-detective.com)).
- **[M]** LLM agents following install docs: Installamatic covers "40 open source Python projects"; "55% of the studied repositories can be automatically installed by our agent at least one out of ten times" ([arXiv 2412.06294](https://arxiv.org/abs/2412.06294)). EnvBench: "6.69% repositories for Python and 29.47% repositories for JVM" ([arXiv 2503.14443](https://arxiv.org/abs/2503.14443)).
- **[D]** Feeding failures back: Fedora maintainers "will be asked, using e-mail and bugzilla, to fix or remove their packages", else "we defer the change" ([Fedora](https://fedoraproject.org/wiki/Changes/Python3.13)). A failing k8s blocking job needs "an issue… detailing that there is at least one person from the owning SIG working to resolve" ([release-blocking-jobs](https://github.com/kubernetes/sig-release/blob/master/release-blocking-jobs.md)).

## Q6. Reviewing a very large release diff

- **[D]** Nobody reviews the release diff in one pass. Linux spreads review across subsystem trees and linux-next: "all patches merged during a given merge window should really have found their way into linux-next some time before the merge window opens", with merges running "at a rate approaching 1,000 changes per day" ([kernel process](https://www.kernel.org/doc/html/latest/process/2.Process.html)).
- **[D]** At release time, review is weighted by risk: "We uplift low-risk fixes for high-severity issues. We do not uplift low-severity issues, high-risk changes, or new features" ([Mozilla uplift rules](https://wiki.mozilla.org/Release_Management/Uplift_rules)). Chromium narrows what may merge by phase, and "Release managers and automation review and approve, reject, or ask questions about the merge within two business days" ([Chromium merge request](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/process/merge_request.md)).
- **[M]** How well review works at scale: in the SmartBear/Cisco study (2,500 reviews), inspection rates "less than 300 LOC/hour result in best defect detection", and detection "plummet[s]" after 90 minutes ([summary](https://mikeconley.ca/blog/2009/09/14/smart-bear-cisco-and-the-largest-study-on-code-review-ever/)). McIntosh et al.: "Low code review coverage and participation are estimated to produce components with up to two and five additional post-release defects" ([MSR 2014, DOI 10.1145/2597073.2597076](https://doi.org/10.1145/2597073.2597076)). Bacchelli & Bird: "code and change understanding is the key aspect of code reviewing" ([ICSE 2013](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/ICSE202013-codereview.pdf)). No study of reviewing a whole release diff at once was found.

## Q7. Post-publish verification

- **[D]** GoReleaser `verify`: "After a release is published, `verify` re-downloads the published release assets from their public URLs… and runs your verification commands against them", "right before announcing", catching "broken or truncated uploads, bad signatures, and CDN propagation issues" ([GoReleaser verify](https://goreleaser.com/customization/verify/)).
- **[D]** Provenance: GitHub attestations give "SLSA v1.0 Build Level 2", or Level 3 with reusable workflows, and "Generating attestations alone doesn't provide any security benefit, the attestations must be verified" ([GitHub attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)). With npm trusted publishing, "provenance attestations are automatically generated" ([npm provenance](https://docs.npmjs.com/generating-provenance-statements/)). PyPI PEP 740 binds each distribution to a digest attested by an identity ([PyPI attestations](https://docs.pypi.org/attestations/)).
- **[D]** Channel visibility: "The latest release is the most recent non-prerelease, non-draft release, sorted by the created_at attribute" ([GitHub REST](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)). Go retractions change what `@latest` resolves to ([go.dev/ref/mod](https://go.dev/ref/mod)). PEP 101 and Node's post-promotion checks are covered in Q1.

## Q8. Version bumps

- **[D]** "Major version zero (0.y.z) is for initial development. Anything MAY change at any time"; "If your software is being used in production, it should probably already be 1.0.0" ([SemVer](https://semver.org/)). Cargo: "only changes in the left-most non-zero component are considered incompatible" ([Cargo semver](https://doc.rust-lang.org/cargo/reference/semver.html)). uv: "the minor version number is bumped for breaking changes"; "The care we take… is proportional to the expected real-world impact" ([uv](https://docs.astral.sh/uv/reference/policies/versioning/)). Ruff does the same until its API is stable ([Ruff](https://docs.astral.sh/ruff/versioning/)).
- **[D]** Computed bumps: release-please maps "fix:" to patch, "feat:" to minor and "!" to major ([release-please](https://github.com/googleapis/release-please)). changesets takes "the maximum version bump" per package (Q3).
- **[D]** Judged bumps: Kubernetes follows a deprecation policy rather than semver-major, e.g. "Beta API versions… are no longer served 9 months or 3 minor releases after deprecation" ([k8s deprecation policy](https://kubernetes.io/docs/reference/using-api/deprecation-policy/)). Hyrum's law: "all observable behaviors of your system will be depended on by somebody" ([hyrumslaw.com](https://www.hyrumslaw.com/)).
- **[D]** 1.0 criteria are commitments, not a feature count. Tokio 1.0: "we commit to holding back on a Tokio 2.0 release for at least 3 years" and "maintain the Tokio 1.0 branch for a minimum of 5 years" ([Tokio 1.0](https://tokio.rs/blog/2020-12-tokio-1-0)). Terraform: v1.x "actively maintained for at least 18 months" ([Terraform](https://developer.hashicorp.com/terraform/language/v1-compatibility-promises)). Go 1: "programs written to the Go 1 specification will continue to compile and run correctly, unchanged" ([go1compat](https://go.dev/doc/go1compat)). ZeroVer satire: "Your software's major version should never exceed… zero" ([0ver.org](https://0ver.org/)).

## Q9. Agentic / LLM release tooling in the wild

- **[D]** Nx's agentic migrations (`--agentic=<agent>`, "claude-code, codex, or opencode") pair deterministic generators with prompt-based steps, make one commit per migration, and defer to the calling agent ([Nx](https://nx.dev/docs/features/automate-updating-dependencies), [nx migrate](https://nx.dev/reference/core-api/nx/documents/migrate)).
- **[D]** Angular's MCP server has `onpush_zoneless_migration`, and `run_target` "Executes a configured target (e.g., build, test, lint…)" so an agent can verify a migration ([Angular MCP](https://angular.dev/ai/mcp)).
- **[M]** Google: "74.45% of the code changes and 69.46% of the edits were generated by the LLM", with an estimated "50% reduction" in time ([arXiv 2504.09691](https://arxiv.org/abs/2504.09691)). "∼87% of the code generated by AI ended up committed without any change"; "We purposefully limited the number of changes we generate every weak to avoid overwhelming reviewers" ([arXiv html 2501.06972](https://arxiv.org/html/2501.06972)).
- **[M/A]** Amazon Q code transformation reports "85% higher success rate" on "62 large open-source applications". It verifies by building and testing in both the source and target Java versions ([AWS blog](https://aws.amazon.com/blogs/devops/dissecting-the-performance-gains-in-amazon-q-developer-agent-for-code-transformation/)).
- **[A]** An LLM changelog-on-merge workflow reads "the PR title, description, and changed files" at "~$0.0004 per entry" and reports no failure data ([dev.to](https://dev.to/aftabkh4n/i-added-ai-generated-release-notes-to-my-cicd-pipeline-using-claude-and-github-actions-3940)). A vendor blog: "The teams that get into trouble with AI-generated release notes… let AI output go out without a review step" ([doc.holiday](https://doc.holiday/blog/ai-generated-release-notes-setup)).
- **[D]** GitLab removed its Duo commit-message flag: "`generate_commit_message_flag` removed… in GitLab 17.7". The reason was not found ([GitLab docs](https://docs.gitlab.com/user/project/merge_requests/duo_in_merge_requests/)).
- **[D]** Agent upgrade skills: Callstack's Expo skill says "Read Expo and React Native release notes deeply before editing code, then map each breaking change to a concrete code/task item" ([callstack skill](https://github.com/callstackincubator/agent-skills/blob/main/skills/upgrading-react-native/references/expo-sdk-upgrade.md)). Next.js ships skills for multi-step adoption (Q2).

## What to steal (ranked)

1. **A required, CI-checked upgrade fragment per change** (Go doc/next with TODO flagging; HashiCorp `changelog-check`; k8s release-note block). It fixes the most common measured failure, omission, especially of breaking changes (Wu et al. [M]). [D]
2. **Split actions into required-before-upgrade and after-upgrade, tied to a named surface** (k8s "Urgent Upgrade Notes", reno `upgrade` vs `deprecations`, Mattermost "Before upgrading, FIPS deployments…", Elastic "address… before upgrading"). This gives the agent's checklist its before/after marks for free. [D]
3. **Machine-readable, version-gated migration entries with prose only as a fallback** (Nx migrations.json with generator + `prompt` + `agentContext`; Angular `possibleIn`/`necessaryAsOf`; OpenRewrite composite recipes). The agent then filters the from→to range with data instead of reading it from prose. [D]
4. **Range filtering at read time** (Renovate "only include those versions being updated", changelogd `--from/--to`, GitLab upgrade-path tool). This replaces the agent's hand-merging across skipped versions with a deterministic tool. [D]
5. **Declare required stops explicitly** (GitLab x.2/x.5/x.8/x.11, k8s no-skip, AWS/Nx/Rails/Django one-step advice). Where a skip is unsafe, the notes should say "stop at X" rather than let a merged checklist imply a direct jump is fine. This matters doubly because the update into vX runs the previous binary. [D]
6. **Verify from the published artifact before announcing** (GoReleaser `verify`, PEP 101 "Pretend you're a user", Node dist/index.json checks, Rust dev-static staging). This catches truncated uploads, missing notes files and CDN lag. [D]
7. **Keep up the rehearsal on the real update path, and make it block the release** (crater's beta run → `regression-from-stable-to-beta` issues; k8s "three successive green runs"; Fedora deferral). FRICTION reports then have an owner and a stop rule. [D]
8. **Treat the upgrade doc as a test suite** (Docs as Tests: "each step an assertion"; Doc Detective). Agents set up only 55% of repos from docs (Installamatic [M]) and 6.69% of Python repos in EnvBench [M], so literal-following runs are worth their cost. [D/M]
9. **Commit per migration step and validate each step in isolation** (Nx agentic flow). The upgrader's checklist then gets an audit trail and a rollback granularity. [D]
10. **Ship version-matched instructions for agents with the installed version** (Next.js `AGENTS.md` managed block + bundled docs: "may all differ from your training data… Heed deprecation notices"). The agent's stale priors are overridden by the installed version's instructions. [D]
11. **Pair any LLM-drafted notes with human review, grounded in PR metadata rather than raw diffs**. LLMs miss the "why" (arXiv 2404.14824 [M]) and struggle on diff2sum (ReleaseEval [M]), no measured hallucination rate exists, and Google capped change volume to protect its reviewers [M]. [M/A]
12. **Idempotent, version-guarded codemods** (Tailwind's upgrade tool refuses non-v3 projects; Svelte `@migration` markers leave greppable residue). Re-running an update or resuming a half-worked checklist then cannot corrupt the tree. [D]
13. **For scaffolded-then-owned files, publish the template diff between two versions** (Backstage Upgrade Helper; copier's fresh-vs-current diff). If the adopter must not edit, enforce it (projen anti-tamper). This validates the UPDATED/NEW/GONE report model and names the two alternatives. [D]
14. **Show NEWS on update, trimmed to breaking changes** (LazyVim "only contains big new features and breaking changes"; oh-my-zsh changelog after upgrade). Adopters who update without reading the release page still see the actions. [D]
15. **Review at release by risk tier, not as one whole diff** (Linux linux-next pre-soak; Mozilla/Chromium severity × risk matrix). Review effectiveness collapses beyond roughly 300 LOC/hour or 90 minutes (SmartBear/Cisco [M]), and low review coverage raises post-release defects (McIntosh [M]). [D/M]
16. **Make the 0.x bump rule and the 1.0 criteria explicit** (Cargo's left-most-non-zero rule; uv/Ruff minor = breaking; Tokio/Terraform commitment windows). Adopters and their agents then know which bumps carry actions. [D]
17. **Verify attestations as well as generating them** (GitHub: "must be verified for the benefit to be realized"; PEP 740; npm provenance). The build-from-source path gets a provenance check on the tag. [D]
