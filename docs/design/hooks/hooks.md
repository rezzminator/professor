# hooks

Professor reaches a chat through hooks at two tiers. pfm's twenty machine-global Claude hooks, one registration each, ride every Claude launch: `claudelaunch.Render` renders them into the `hooks` key of the single `--settings` JSON the chat starts with. `pfm init` scaffolds a project's `.claude/settings.json` from the template, with three hooks over the project's own scripts. Claude merges hooks across its settings layers, so the project's hooks run beside the launch's. Codex carries seven pfm handlers, `resume-unkill` and the six of the [Herdr reporter](#herdr-reporter), which `pfm install` writes into each Codex home's `hooks.json` and trusts; OpenCode carries the Herdr reporter's one staged plugin and no hook. This file holds the inventory, the ownership rule, and the design of the `pfm doctor` checks that prove each pfm hook is in place. The Bash guard over shared git state is designed in [git-guard.md](git-guard.md).

A change lands in this design doc first, then in the code or template, then in every surface listed under [Surfaces that stay in sync](#surfaces-that-stay-in-sync).

Every claim cites the file that proves it. `{claude config dir}` is one account's `configDir` from the pfm machine config; `{codex home}` is one Codex account's home.

## Decisions

- **One list is the truth for pfm's hooks.** `claudelaunch.HookTemplates` (`pfm/internal/claudelaunch/hooks.go`) names all twenty hooks, one registration each. `claudelaunch.Render` renders it into every launch's `--settings` payload, and spawn-audit compares each live chat's decoded payload against it. A new pfm hook is a new row there, never a second list.
- **Hooks ride the launch, never a file.** `pfm install` writes no key into any account `settings.json`: no `hooks`, no `statusLine`, no `subagentStatusLine`. A chat carries the hook set it was launched with; a changed set reaches a running chat at its next reload (`pfm chat reload`) or relaunch.
- **pfm never writes a project's `.claude/settings.json`.** The project tier is scaffolded once by `pfm init` (`pfm/internal/professor/scaffold.go:29`) and is the adopter's file from then on. Its hooks merge with the launch's; neither layer replaces the other.
- **Every pfm hook command is the installed binary, but one.** Each command is `$HOME/.local/bin/pfm` plus a subcommand (`pfm/internal/claudelaunch/hooks.go`); `tracer-intake` alone runs `python3` on the shipped tracetree kit, wrapped so its own failure is a non-blocking exit 1. `python3` is a required `deps.Registry` row (Linux and macOS): `pfm install` and `pfm doctor` check it and never install it. No pfm hook runs a shell script.
- **An ownership ledger records hooks pfm wrote into a file.** `$HOME/.local/share/pfm/install/settings-hook-ownership.json` is keyed by physical file, event, matcher and command (`pfm/internal/installer/settings_ownership.go`). Its readers are the Codex `hooks.json` writer and the `pfm-settings` host check. That check combines ledger entries with pfm command shapes to name hooks and status lines an old install left in `settings.json`. It returns BLOCK rows with edits for the operator; it never strips the file.
- **A retired hook is removed by the installer and reported by doctor.** One table names the retired subcommands (`pfm/internal/installer/settings.go:47-55`), with legacy shim hints at `:65-67`; the Codex writer strips them from every `hooks.json` event, and doctor flags any left behind as STALE.
- **pfm hooks fail open.** A pfm hook that cannot do its job writes one stderr line and lets the chat continue. Only the two intercepts exit 2, and only for the prompt they were built to stop; `git-guard` alone also denies a git command it cannot read ([git-guard.md](git-guard.md#how-it-fails)).

## Launch-time Claude hooks (pfm-owned)

`claudelaunch.Render` (`pfm/internal/claudelaunch/render.go`) turns `claudelaunch.HookTemplates` into the `hooks` object of the launch `--settings` JSON: one entry per (event, matcher) pair, each registration once. Every interactive door renders it — `pfm chat new`, the picker and `pfm chat open`, `pfm chat branch`, `pfm chat reload`, `pfm internal agent-open`, a `claude` typed at a shell through the managed launcher ([claude-launch.md](../engines/claude-launch.md#doors)). Three runs carry no pfm hook: a launcher passthrough (`-p`, `--version`, the Claude subcommands, `PFM_LAUNCH_PASSTHROUGH=1`), which execs the real binary untouched; the `claude agents --json` query; and `pfm headless exec`, which is config-free by design. Each command below is `$HOME/.local/bin/pfm …`.

Placement holds by construction: the renderer emits each registration once under its own pair, so a launch cannot carry a duplicate, a moved or a mis-typed pfm hook. The only place such a copy can still sit is an account `settings.json` an older install wrote, which the [pfm-settings row](#account-files-pfm-settings) names for the operator to fix.

The usage hook and the `pfm ls` Limits tab reach `GET https://api.anthropic.com/api/oauth/usage` only through `usagehook.Fetch` (`pfm/internal/usagehook/fetch.go`), which answers in this order:

1. A `cc-rate-limits` statusline snapshot of the seat (`ReadStatuslineSnapshot`): the same config dir, younger than the caller's TTL, its five-hour reset still ahead. No request.
2. The shared cache record `acct-<id>.json` fresh within the caller's TTL: the hook's 180 seconds (`CC_USAGE_TTL`), the Limits tab's 60 (`LiveLimitsTTL`).
3. An active shared backoff: the cached usage with the backoff's error. No request.
4. The `O_EXCL` refresh lock `acct-<id>.lock` beside the cache (`RefreshLockPath`). A lock older than 30 seconds (`lockStaleAfter`) is stale and taken over; a caller that cannot take the lock sends no request and answers from the cache; the holder re-reads the cache and answers if a peer refreshed or backed off meanwhile, and releases the lock on every path.
5. The request, sent with `User-Agent: pfm/{version}`. Success writes the record. A 429 writes the shared backoff (`BackoffFor`): `Retry-After` honored with a ten-minute floor, message `rate-limited — retry HH:MM (429 Too Many Requests)`. Any other failure backs off one minute.

The hook writes a failed refresh to stderr; its prompt output does not change. The statusline writes the snapshots from its stdin `rate_limits` (`harvestRateLimits`, `pfm/internal/statusline/render.go`): every window the harness sent, 0% included, under `windows`, beside the flat keys an older build's reader expects.

A blocked prompt returns `decision: block` with the original prompt suppressed (`pfm/internal/hookentry/prompt_block.go:23-28`).

## Codex

pfm owns seven Codex handlers: `resume-unkill` and the six of the [Herdr reporter](#herdr-reporter). `resume-unkill` is a `SessionStart` handler with matcher `resume` running `pfm internal resume-unkill`, the same command and matcher as its Claude row in `claudelaunch.HookTemplates`, from which the Codex writer takes it. Codex fires `SessionStart` with `source` `resume` and the resumed thread's id as `session_id` (codex-cli's `session-start.command.input` schema, `source` one of `startup`, `resume`, `clear`, `compact`, `fork`), so `codex resume`, the in-app `/resume`, pfm's resume of a Codex chat and a pfm Codex pane resuming inside all lift a standing kill through it; the entry resolves an indexed lineage member to its root (`kill.Manager.Unkill`). `pfm install` writes the handler into `{codex home}/hooks.json` for every Codex account, records it in the ownership ledger, and records its trust in that account's `config.toml` (`hooks.state."{key}"`, the key and hash read from Codex's own `codex app-server` `hooks/list`, with a receipt at `{codex home}/.professor-hook-trust.json` so uninstall removes exactly that trust; `pfm/internal/codexappendix/trust.go`). Without a configured Codex binary the install says the hook stays untrusted. The writer still removes pfm's retired hooks while keeping the operator's (`pfm/internal/installer/codex_hooks.go`). The fleet prompt reaches Codex through `config.toml`'s `developer_instructions`, never a hook. The six Herdr handlers run `pfm internal herdr-state --engine codex {start|working|blocked|idle|end}` on `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PermissionRequest`, `Stop` and `SessionEnd`; the installer writes, trusts, records and removes them exactly like `resume-unkill`. An unparsable file is skipped loudly unless owned hooks would be stranded.

## OpenCode

pfm ships no OpenCode hook. Its one OpenCode plugin is the [Herdr reporter](#herdr-reporter)'s bridge. OpenCode has no appendix hook; the staged prompt reaches it through the `instructions` config array (`pfm/internal/installer/opencode_instructions.go:12-17`). The generated mirrors are protected by a permission deny in `.opencode/opencode.jsonc` instead of a hook (the machine policy `templates/global/engine-sync/config.json` `opencode.permission`).

## Herdr reporter

**Purpose.** [Herdr](https://herdr.dev) detects an agent by the foreground process of a pane. A pfm chat pane runs `tmux attach`, so Herdr sees `tmux`, never the engine. pfm therefore reports itself through Herdr's reporter contract: `pane.report_agent` and `pane.release_agent` on `$HERDR_SOCKET_PATH`, under the stable source `pfm` (`herdr.Source`; a source never starts with `herdr:`, which is Herdr's own), with a strictly increasing `seq`. One implementation serves all three engines: `pfm internal herdr-state [--engine claude|codex|opencode] <start|working|blocked|idle|end|notification|title>` for engine events and `pfm internal herdr-state <sync|detach|name> --socket {tmux socket} --session {session} [--client {pid}]` for the chat tmux server's hooks (`pfm/internal/hookentry/herdr_state.go`, `herdr_clients.go`, `herdr_name.go`; the wire in `pfm/internal/herdr/`), reading the hook JSON on stdin.

**Event map.**

| Engine | Carrier | Events |
| --- | --- | --- |
| Claude | the seven launch rows of [the table above](#launch-time-claude-hooks-pfm-owned) | `SessionStart` → idle with the session and `resume_argv`; `UserPromptSubmit` and `PostToolUse` → working; `PermissionRequest` → blocked with `waiting for approval: {tool_name}`; `Notification` `permission_prompt` or `elicitation_dialog` → blocked with the message, never replacing a stored message that names the tool, `idle_prompt` → idle; `Stop` → idle; `SessionEnd` → release, except reason `clear` or `resume` (the session swaps in place) |
| Codex | six handlers in `{codex home}/hooks.json`, written by `pfm install` | `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PermissionRequest` (blocked, `waiting for approval: {tool_name}`), `Stop`, `SessionEnd` (release); Codex fires `SessionStart` at the first turn, not at launch, so the chat server's `attach` reports a pane with no stored state idle under the session's engine |
| OpenCode | the staged plugin, which pipes `{"session_id","message"}` to the same entry | the plugin maps the session's status and permission events onto the same working, idle and blocked states; a child session reports nothing |

A sub-agent event (a payload `agent_id`, or an OpenCode child session) never touches the pane. The agent label is the engine's own name (`claude`, `codex`, `opencode`).

**Pane identity.** A chat's own process environment keeps the `HERDR_*` variables of the shell that created its tmux server, which is the wrong pane for a chat attached later or from another pane. Inside a pfm chat tmux server (`$TMUX` set) the reporter never trusts its process environment, and it writes nothing to tmux or disk unless the host has Herdr (`HERDR_BIN_PATH` set or `herdr` on PATH). `config.ChatServerOptions` (`pfm/internal/config/tmux_titles.go`) sets `update-environment[20..23]` to `HERDR_ENV`, `HERDR_PANE_ID`, `HERDR_SOCKET_PATH` and `HERDR_BIN_PATH`, so tmux copies them from each attaching client into the session environment and removes them when the client lacks them. The server carries four hooks, all `set-hook -g {name}[50] run-shell -b "'{pfm}' internal herdr-state {event} --socket #{q:socket_path} --session #{q:session_name}[ --client #{q:client_pid}]"`: `client-attached` → `attach`, `client-resized` → `sync`, `client-detached` → `detach`, `window-renamed` → `name` (no `--client`). The command is quoted for both layers (the pfm path single-quoted for sh, tmux values through `#{q:…}`, the whole command in the spelling `show-hooks -g` prints), so a converged server is never rewritten. `attach` for a client not yet registered reads the session environment for the Herdr socket, then registers the Herdr pane whose `pane.process_info` foreground runs that client pid (the environment's pane asked first), never the environment's pane on its word alone: the session environment holds the variables of the last client that attached, so two clients attaching at once never take each other's pane. The client is registered in the session option `@pfm_herdr` (`clients`, keyed by client pid: pane, Herdr socket and terminal) and the stored state is re-reported to that pane; a client no Herdr pane runs registers nothing and is an error row. A client already registered is re-bound, as `sync` does. `sync` never registers: the session environment holds the variables of the LAST client that attached, so a client that attached earlier without Herdr and then resizes would otherwise take that client's pane. Every event stores `{engine, session_id, state, message, seq}` under a per-session `flock` (3 s deadline; a stored `seq` above the event's makes the event stale) and reports to every live registered client, so two panes attached to one chat both show it, and `detach` releases only the detaching client's pane (tmux 3.7c expands `client_pid` to empty on detach: a detach without a pid releases and forgets every registered client tmux no longer lists). Outside tmux (a Codex app-server seat, a direct run) the reporter uses its process environment.

**Pane moves.** Herdr's `pane.move` keeps the terminal and gives the pane a new public id; the id in the session environment is copied only at attach and so goes stale. The registry therefore records the pane's `terminal_id` (from `pane.list` at attach), and every send to a registered client first resolves the current pane id through `pane.list`: the pane holding that terminal receives the report, the release, the name and the title. A changed id re-binds the registry and re-sends state, session, name and title; no request names the vacated id, which Herdr may hand to another pane. Without a recorded terminal the recorded id is used if `pane.list` still holds it (its terminal is then bound), else the pane whose `pane.process_info` foreground processes hold the client pid. A terminal that is in no pane, or a failing `pane.list`, sends nothing and writes an error row. The `client-resized` hook runs `sync`, which re-binds a registered client only (a no-op for an unchanged pane; `attach` of a registered client does the same): a move usually resizes the pane, so the chat re-binds at once; a move that leaves the size alone re-binds at the next event. Flip the hook off by deleting `herdrResizedHook` in `config/tmux_titles.go`.

**Names.** `@pfm_chat_name` is a session option holding the chat's exact name; every writer sets it in the same tmux command as the rename and before it (a final `;` is escaped `\;`): `gather.RenameWindow` (name-sync's Codex half and the statusline's `convergeWindowName` for a Claude `/rename`), `renameChatWindow` (`pfm chat name`, the MCP name tool), `spawn.TmuxSpawner.NewSession` (`chat new --name`, `chat branch`). The `window-renamed` hook (it fires for `rename-window` from a command client, also for an unchanged name) runs `name`. `name` and the SessionStart events share one name sync: an unset `@pfm_chat_name` is an unnamed chat and Herdr keeps its default; a named one is slugged by `herdr.AgentName` (lowercase, `[a-z0-9_-]`, at most 32 characters, the shortest free `-2…-9` suffix against `agent.list`), sent with `agent.rename`, and the exact name goes to `pane.report_metadata` as the pane `title` (80 characters); the name is stored in `@pfm_herdr` once every pane carries it, so a rename that leaves it unchanged names only a pane just attached or moved, and a failed naming is tried again by the next rename. A release sends `clear_title`. OpenCode's plugin forwards a main-session title change (`session.updated`, no `parentID`, never the default `New session - {ISO time}` placeholder, once per changed title) as `pfm internal herdr-state --engine opencode title` with stdin `{"session_id","title"}`, which sets `@pfm_chat_name` (a final `;` escaped) and renames the window in one tmux command, so the same hook follows. Unnamed creation sets nothing.

**Only the pane's own engine reports.** A child engine a chat starts itself (`codex exec` from a Bash call) inherits `$TMUX` and the Herdr names. Two layers keep it silent. The doors we launch strip the names: headless `run`, `claudelaunch.ProbeEnv`, the usagehook version probe, the statusline and codexappendix `codex app-server` helpers and the launchers' non-interactive pass-through (Claude: arguments-decided pass-through only; Codex: every pass-through subcommand, `exec` and `review`, also `TMUX` and `TMUX_PANE`) drop `HERDR_*` (`herdr.StripPane`, `herdr.StripReporter`); `claudelaunch.Hygiene()` is unchanged, so interactive launches keep them. For doors nobody enumerated, an engine-fired event (not `attach`, `sync`, `detach`, `name`) walks up from the hook process, skips shells and pfm, and takes the first other process as the firing engine; above it, a command wrapper (`env`, `timeout`, `caffeinate`, …) is skipped, and a `node` launcher with no shell or pfm between it and the engine is the engine's own (npm's Codex runs its native binary under one). It reports only when no second engine sits between the firing engine and the pane pid; an unreadable process table or pane pid, or a hook that does not run under the pane, reports nothing and writes an error row.

**Errors.** Every reporter error goes to stderr and is appended to `{HerdrLockDir}/{session}.log` (`herdr.AppendError`, one RFC 3339 time, a tab and the message per line), because tmux `run-shell -b` discards stderr. `pfm doctor` prints the `herdr-reporter-errors` row: ok with none in the last 24 h, a WARN with the count, newest message, session and log path otherwise, a WARN with the read error for an unreadable log. Herdr's socket answers one request per connection and then closes it, so `herdr.Call` dials once per request line; a second line on one connection reads EOF or a broken pipe. A release or detach whose pane Herdr no longer lists, or answers `pane_not_found` for (Herdr 0.9.5's code; the socket-api docs spell it `not_found`, also honoured), is no error: the pane closed with its chat and has nothing left to release. A dial, `pane.list` or report failure stays an error row.

**Launch.** `attach` with nothing stored for the session reports the pane idle under the engine its socket names (`cc-` Claude, `cx-` Codex, `ox-` OpenCode) and stores that state, so a chat shows in Herdr from its first attach. Codex fires `SessionStart` only at its first turn; a later `SessionStart` reports the same idle with the session.

**Shells.** A plain shell or server pane reports a long command when it finishes, as its pane title. Output never counts. The shim (`pfm/internal/installer/assets/shim/pfm.zsh`) adds a zsh `preexec`/`precmd` pair only in an interactive shell with `HERDR_ENV=1` and no `$TMUX`, so a pfm chat's own tmux pane keeps its chat reporter. A command that ran at least `PFM_HERDR_LONG_COMMAND_SECS` whole seconds (default 10, also when the value is no number) runs `pfm internal herdr-shell done --pid {shell pid} --at {$EPOCHREALTIME} --command {line} --exit {status} --seconds {n}` in the background; the next command, or the shell's `zshexit` (a nested zsh left by Ctrl-D runs no `preexec`), runs `pfm internal herdr-shell release --pid {shell pid} --at {$EPOCHREALTIME}`. `PFM_HERDR_SHELL_REPORT=0` turns it off. The entry (`pfm/internal/hookentry/herdr_shell.go`) finds the pane whose `pane.process_info` `shell_pid`, or one of whose foreground processes, is that pid: the pane the shell was born in first, then every `pane.list` pane, because a move gives the pane a new id. Both runs of one shell hold its lock (`{HerdrLockDir}/pfm-shell-{pid}.lock`); a release records its `--at` in `pfm-shell-{pid}.released`, and a done whose `--at` is older reports nothing, so a done the next command overtook never leaves a stale done. It reports `working`, then `idle` with `{command} exit {status} · {n}s`, the command cut to fit Herdr's 240-rune message and never the status and duration, under the source `pfm-shell` and the agent `shell`, because a lone `idle` on a pane with no agent shows nothing; Herdr drops any agent report within a second once the bare shell holds the foreground again, so the same text, cut to Herdr's 80-rune title and never the status and duration, is also the pane's title (`pane.report_metadata`, source `pfm-shell`), which Herdr keeps on a bare shell. The next command's release sends `pane.release_agent` and `clear_title`, restoring the terminal's own title. Every failure, a done that finds no pane running the shell included, is a line in `{HerdrLockDir}/pfm-shell.log` that names each Herdr request by its method, id and pane, never the command it carried, which the `herdr-reporter-errors` row reads. A shell found among a pane's foreground processes is a nested shell (a `zsh` started inside the pane's own shell): its done also records that pane's terminal in `pfm-shell-{pid}.pane`, because the next command takes the foreground from it; a release that finds the shell in no pane goes to the pane now holding that terminal and drops the record. A release with neither a pane running the shell nor a recorded terminal in a pane has nothing left to release.

**Presence.** `pfm chat ls` and the chat MCP's `ls` show each chat's Herdr presence, both from `pfmchat.List` (`ListResult.Herdr`, `pfm/internal/herdr/presence.go`): `{pane} {workspace} {agent status} {agent name}` for each registered client, resolved through its terminal id so a moved pane reads right (`{pane} {workspace} no-agent` when Herdr lists no agent on that pane); `not in herdr` for a chat no Herdr pane shows; `herdr error: {cause}` for a failed lookup; `—` on a host without Herdr (no `HERDR_BIN_PATH`, no `herdr` on PATH), with no socket call. One `pane.list`, `agent.list` and `workspace.list` per Herdr socket serves a whole listing.

**Resume.** The session start reports `resume_argv ["pfm","chat","open",<session id>]`. After a Herdr server restart Herdr runs it in the restored pane, and `pfm chat open` attaches the live socket or resumes the chat on the account that owns it. A session id Herdr's rules refuse (empty, an apostrophe, a control character, more than 64 words or 8 KiB) omits `resume_argv` and writes one stderr line. Herdr's own `[session] resume_agents_on_restore = false` opts a host out.

**Contract.**

- `seq` is the UnixNano of the process start, so concurrent events from separate processes order by start time.
- The entry is fail-open and always exits 0: a hook exit 2 would block Claude. A socket that is missing, refused or slow (500 ms dial, 1 s I/O) writes one stderr line with its full context.
- Outside a Herdr pane (`HERDR_ENV` unset in the process or the session environment, or no Herdr on the host) it is inert: no stdout, no stderr, no socket, no tmux write. The lane beat `O2.05-internal-plumbing` proves this against the built binary; the socket path is unit-tested.
- A message is capped at 240 runes.

**Doctor.** Herdr ships its own bundled integrations for Claude, Codex and OpenCode, which report the same panes under the source `herdr:{engine}` and would compete with pfm's. `pfm doctor` runs `herdr integration status` per engine and prints a FAIL row for each one installed, with the fix `herdr integration uninstall {engine}`; with `herdr` absent the row is ok and not applicable; an unreadable status is a warning row, never ok (`pfm/internal/doctor/herdr_check.go`).

**Recorded forks.** The agent label is the engine name; no Herdr behaviour is known to bypass pfm for a label, and only the source decides authority (recorded, unverified live). `HERDR_AGENT` is deliberately not set on the attach lines: it is a per-process screen-manifest hint on `tmux`, would mislabel codex and opencode at the engine-blind attach sites, and is a second authority beside the reporter. To flip it, add `HERDR_AGENT={engine}` in `action.attachLine` and in `chat_new`'s `attachRunResult`.

**Known limits.** An Esc interrupt fires no `Stop`: the `idle_prompt` notification is the net. A denied permission stays blocked until the next tool call or `Stop`.

## Agent-attached hooks (not machine-global)

A hook can also be wired only into one agent's own frontmatter instead of every launch's payload — it is never in `claudelaunch.HookTemplates`, never in spawn-audit's expected set, and pfm install/doctor never mention it. `orchestrator-wait` is the one: a `PreToolUse` hook on `Bash` that denies a call whose whole command only waits (`echo`/`printf` with plain literal arguments, `true`, `:`, or `sleep N` — matched as a whole string; `pfm/internal/hookentry/orchestrator_wait.go:55-94`) and a call that loops on a file's existence under a `returns/` path (`until [ -s … ]`, `while [ ! -f … ]`), so a wait-looping orchestrator ends its message instead of spending a call proving nothing changed or placing a watcher on a sub-agent, whose completion notice wakes it. It is fail-open the same way every pfm hook is: a read or decode failure logs to stderr and returns 0 (`orchestrator_wait.go:41-54`). It is registered as an internal verb exactly like `explore-deny` (`pfm/cmd/pfm/main.go`'s `internalSubcommands` list and its `runInternal` dispatch) so `pfm internal orchestrator-wait` runs and the subcommand is never mistaken for unknown residue, but it is deliberately absent from `claudelaunch.HookTemplates` — it is attached only through the frontmatter of `flights-foreman` (carried into its rendered twins) and of this repo's `releaser`, the agents that spend calls waiting on their spawned children, and never runs for any other agent. The frontmatter names bare `pfm`, never a machine path, since the agents ship; the Codex compile drops an agent's hooks, so the hook is Claude-only.

`call-cap` is the second: `pfm internal call-cap`, a `PreToolUse` hook on every tool (matcher `*`) of an agent whose manual caps its model requests. The cap is the one the flight report judges a run by, `transcript.CallCap` of the payload's `agent_type` (a foreman 250, a lander 200, any other agent 150; `pfm/internal/transcript/records.go`), so the frontmatter only attaches the hook and carries no number. An agent's own count of its calls lives in its context and is summarized away at every compaction; this one is read from its transcript at each tool call (`pfm/internal/hookentry/call_cap.go`), resumed from a tally the previous call saved under `~/.local/state/pfm/call-cap/` (`paths.CallCapTallyDir`, one file per transcript path), so a call reads only what the agent appended since; a transcript shorter than its tally or rewritten under its first 4 KiB, or a tally with a negative offset or line count, is counted from the start, a tally that cannot be read or saved costs a full read, logged to stderr, never the count, a call that read no new complete line leaves its tally file as it was, and a new tally prunes the tallies a week old. The transcript is the payload's `transcript_path`, or, when the payload names an `agent_id`, the sub-agent's own `agent-{id}.jsonl` in that session's `subagents/` directory (one file across all of its compactions). The count is `transcript.RequestTally`'s, the fold `transcript.RequestCount` runs from the start (`pfm/internal/transcript/records.go`): the distinct response keys of the assistant records that bill a request, by the same `transcript.NotARequest` rule and response key `pfm tokens` collects a call with. It is never below the calls the flight report judges against the cap: the report also drops a record with no timestamp, a call copied from another transcript, a response only an advisor billed and a call before the flight's window, so the hook stops an agent no later than its report flags it over the cap. Below four fifths of the cap it prints nothing; from there it injects the count as `additionalContext`; at or past the cap the context orders the stop and the cap return of the agent's role (`transcript.CallCapRole`), as its manual words it: a foreman's `FAILED {flight}: cap` with its handoff, a lander's `FAIL {flight}: cap` with its ledger, any other agent's `FAILED {id}: cap`. It never denies a tool, since the handoff needs them. A payload, transcript or agent id it cannot read is injected as an unknown count with its error, and a payload naming no `agent_type` as the count with an unknown cap, never as silence; any argument exits 1 with the usage on stderr. It is registered as an internal verb like `orchestrator-wait` and, like it, absent from `claudelaunch.HookTemplates`.

`cutgate` is the third, and the one that is not pfm's: `python3 $HOME/.claude/skills/tracetree/tracetree.py cutgate`, a `PreToolUse` hook on `Bash|Edit|Write|MultiEdit|NotebookEdit` in `flights-foreman`'s frontmatter, carried into its rendered twins. It denies the foreman's code edits, a Bash write into the tree or a tree Bash left dirty included, until the agent's own transcript, resolved as `call-cap` resolves it, holds its run of the tracetree kit's `segment` with a verdict other than `EMPTY`; writes under the flight's state directory or `/tmp`, and a segment or `DEPTH 3` child whose parent already cut, stay open. What it cannot read allows the edit and says so in `additionalContext` and on stderr. Its law is in [tracetree.md](../tracing/tracetree.md#cutgate).

## The ownership rule

- **pfm owns** exactly the hooks in `claudelaunch.HookTemplates`, which live only in the launch payload, the Codex `resume-unkill` handler it writes into each `hooks.json`, and the retired shapes above. In a Codex `hooks.json` its record is the ownership ledger, and pfm removes exactly what the ledger records. In an account `settings.json` left by an older install, ledger-recorded commands count only when their first space-separated field is `~/.local/bin/pfm`; every hook whose command is a `claudelaunch.HookTemplates` command or a retired shape also counts. Doctor names these leftovers for the operator to remove.
- **The operator owns** every other hook in a settings file: a notification script, a memory sync, anything hand-wired. pfm never rewrites, reorders or removes one, and doctor never reports one. The Codex writer's contract says the same (`pfm/internal/installer/codex_hooks.go:85`).
- **An operator's hook that calls pfm stays the operator's.** A hook naming a subcommand this binary implements, such as `pfm doctor`, is never treated as residue (`pfm/internal/installer/settings.go:170-175`, `:209-211`). Only an unknown subcommand in pfm's own shape is.
- **Project-tier hooks are the adopter's.** pfm scaffolds them once; later changes flow through `pfm doctor --project-updates` and an upstream diff the project ports by judgment, never a rewrite.

## The pfm doctor checks

Five checks prove pfm's hooks. The launch hooks are proven per live chat, because that is the only place they exist; the one launch hook that runs something besides pfm, `tracer-intake`, is also proven on the host, since a chat only reveals its failure as a non-blocking error; account files are checked for leftovers that would double-fire beside the launch; Codex homes are checked for the `resume-unkill` handler, its recorded trust and retired residue; the Herdr bundled integrations that would compete with the reporter are checked on the host ([Herdr reporter](#herdr-reporter)). Doctor checks only pfm's own hooks and prints nothing about the operator's — no count line either. The project tier has no doctor coverage.

### Launch hooks: spawn-audit

`pfm doctor` spawn-audit reads each live `cc-` chat's Claude argv from `/proc` and decodes it with `claudelaunch.Parse`, the inverse of `Render` ([claude-launch.md](../engines/claude-launch.md#pfm-doctor-spawn-audit)). A chat is `INJECTED` only when its `--settings` payload carries the registry's hook set: every `claudelaunch.HookTemplates` registration present exactly once, under its own event and matcher, with the exact command. No current template sets `async`; the renderer keeps the field only as `Parse`'s round-trip twin.

| Verdict | Hook meaning | Reports |
| --- | --- | --- |
| `INJECTED` | the payload's `hooks` equals the registry's set | the chat's row, no finding |
| `VIOLATION` | a fresh launch with no registry payload — a spawn site bypassed `Render`, so the chat runs no pfm hook | failure, naming the chat and pid |
| `PREDATES-LAYER` | the payload's hook set differs from the current registry: the process started before it changed | warning, naming the chat; `pfm chat reload` carries the new set |

A probe that cannot read `/proc` or decode an argv reports `CHECK FAILED to run … — live chats unaudited`, never "no chats". Hook values are read from argv, never from `/proc/{pid}/environ`.

The same check stats the first word of every template command, following a symlink, and reports `DRIFT what=executable want=$HOME/.local/bin/pfm got={absent|not-executable|not-regular-file|stat-failed(…)} — run pfm install` (`executableVerdict`, `pfm/internal/installer/hook_probe.go:308`), since every rendered hook would fail to start.

### Account files: pfm-settings

`pfm-settings` reads each physical `settings.json` in the store and configured account dirs once, against the ownership ledger and pfm command shapes. Its items are distinct `hook "{command}"` entries sorted by command, then `statusLine`, then `subagentStatusLine`, joined with `, `. Doctor prints `host-check: BLOCK pfm-settings {file} — carries pfm's {items} — pfm supplies its own hooks and status lines through --settings at launch, so these entries are leftovers of an earlier install`, followed by `host-check:   fix: remove {items} from {file} (each hook entry running that command and each named key; keep every other entry)`. Install refuses until the operator fixes the file.

An absent file or a file without pfm-owned keys produces no row. An unreadable file or ownership ledger produces a BLOCK `UNREADABLE` row with its cause and remedy; failed inspection is never clean. A custom status line and unrelated hook commands remain the operator's settings.

### Codex hooks.json

The Codex probe (`probeCodexHooks`, `pfm/internal/installer/hook_probe.go`) opens every configured Codex home's `hooks.json`, drawn from the machine config's Codex accounts, named `codex[{id}]`, de-duplicated by physical path. Each row keeps the prefix `doctor: hook {target} {file} {event} {name}`. It expects all seven pfm-owned handlers per Codex home (`resume-unkill` on `SessionStart` with matcher `resume`, plus the six `herdr-*` handlers), each trusted, and validates the source file before querying native `hooks/list` through Codex app-server. This read-only query starts no model turn and writes no configuration. A matching receipt alone cannot prove current trust. It prints these states:

| State | When | Prints | Tally |
| --- | --- | --- | --- |
| MISSING | `hooks.json` is absent, or holds no `resume-unkill` handler under a `SessionStart` entry with matcher `resume`, or lacks one of the six Herdr reporter handlers (`SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PermissionRequest`, `Stop`, `SessionEnd`) | `… MISSING — run pfm install --yes` | failure |
| UNTRUSTED | Missing receipt, changed fingerprint, or native trust not trusted, for any of the seven pfm-owned handlers | `… UNTRUSTED {cause} — run pfm install --yes` | failure |
| NATIVE-TRUST-UNKNOWN | Native `hooks/list` could not run | `… NATIVE-TRUST-UNKNOWN {cause}` | warning |
| STALE | A retired or unknown pfm hook is registered; the Codex-only retired shapes (the old `clear-kill` `SessionStart` hook and the retired appendix hook) are flagged only under `SessionStart` | `… STALE {name} — run pfm install` | failure |
| UNREADABLE | The file or the ownership ledger exists but cannot be read or parsed, is a dangling symlink, or its `hooks` value has the wrong shape (a non-object `hooks`, a non-array event, a non-object entry, a non-string `matcher`, a non-array `hooks` list, a non-object hook, a missing or empty `command`) | one line per file, no per-hook rows: `doctor: hook {target} {file} UNREADABLE error={cause}`; for the ledger, target `ownership` | failure |
| DRIFT (ledger) | The ledger owns an entry the file lacks, or one the installer no longer expects | `… DRIFT ledger ownership={n} file={m}`, `m` also `absent` or `not-expected` | warning |
| (unknown) | An internal state this printer does not recognize | `… UNKNOWN-STATE state=…` | failure |

UNREADABLE is an error, never absence: it carries no rows for that file's hooks, because nothing was proven. An unreadable ledger prints its own UNREADABLE row and every file's STALE and UNREADABLE rows still print, without the ledger comparison. OpenCode prints nothing.

### Launch hook: tracer-intake

`pfm doctor` proves the `tracer-intake` hook can work on this host (`printTracerIntakeDoctor`, `pfm/internal/doctor/tracer_intake_check.go`). The hook fails open by design, so a missing `python3` or kit would otherwise show only as one non-blocking stderr line in a chat. The check takes the rendered command and the kit path from `claudelaunch.TracerIntakeHook`, which reads the `tracer-intake` row of `HookTemplates`; when the row changes, the check follows with no edit. Every row starts `doctor: tracer-intake:`.

| Need | Checked | Broken state reports |
| --- | --- | --- |
| `python3` | the `python3` row of `deps.Registry`, through the same `deps.Probe` as `doctor: dep python3` (resolved on doctor's PATH, answers `--version`) under the check's own 20 s bound, where the dep row has the probe's default | `FAIL need=python3` with `python3 not found on doctor's PATH`, or the probe's state and error (`broken: …`, `timeout: …`), and the fix pointing at the `doctor: dep python3` row |
| the kit | the kit file the command names is a readable regular file | `FAIL need=kit` with the stat or open error |
| pass-through smoke | the command, run through `/bin/sh -c` with a non-tracer `PreToolUse` payload on stdin, exits 0 with empty stdout; this proves the interpreter, the kit and its imports | `FAIL need=smoke-passthrough` with the first stderr line |
| tracer smoke | the same command with a tracer-spawn payload whose `Repo root:` is a temporary directory doctor creates returns JSON whose `updatedInput` prompt carries a `RUN:` line; this proves the run directory is writable | `FAIL need=smoke-tracer` with the first stderr line or the missing `RUN:` line |

Each FAIL row names the need, the path or command checked, the first line of the captured stderr (or the error that stopped the check; for `need=python3`, the dependency probe's result), and the fix: install python3 as the `doctor: dep python3` row says, or run `pfm install --yes` to relink the kit. Every FAIL is a failure in the doctor tally. A check that could not run (no `/bin/sh`, a temporary directory it could not create, a run past the 20 s bound) is a FAIL with that reason, and when python3 or the kit fails, one `need=smoke` FAIL says the smokes were not run, never silence. The smokes create `/tmp/{project}/tracer/{run}` for a temporary root named `pfm-doctor-tracer-*`, made under the temporary directory, or under `/tmp` when that path is relative or holds a character outside `A-Za-z0-9/._+@%=~-` (the kit's `Repo root:` parser stops at Unicode whitespace, a quote, a bracket, a comma or a semicolon); the smokes run without the inherited git repository variables and with `GIT_CEILING_DIRECTORIES` at the root's parent, so no checkout around the root names the run's `/tmp/{project}`; doctor removes the run, that `/tmp/{project}` and the root, so `tt book` never lists a doctor run, and a removal that fails is `need=cleanup`. On a healthy host one row replaces them: `doctor: tracer-intake: ok python3={path} version={version} kit={path} smoke passed`.

The launch hands its hooks the PATH of the process that launched Claude (`hookentry.Launch` passes `os.Environ()`; pfm sets none), which doctor cannot see, so python3 is judged on doctor's own PATH and the row says so. The check resolves python3 through the registry row and keeps no lookup of its own.

**Before the install has placed the kit.** The kit is linked by `pfm install --yes`, so a host that has not run it, or whose install predates the link, is not broken. When the kit's skill directory (`{home}/.claude/skills/tracetree`) is absent, doctor prints `doctor: tracer-intake: kit not installed yet — run pfm install --yes` and counts nothing; the kit and smoke checks are skipped. The installer records no individual skill link (`~/.local/share/pfm/install/skill-links.json` names only the directories it links source-fetched skills into, never the clone's tracetree link), so "placed" is read from the link at the hook's path: absent is not installed yet, unless the record shows more. If `skill-links.json` is absent, no install has run and the row stays pending. If it is present but unreadable or invalid, the row is a FAIL (`need=kit`) naming the file and the parse error. If a directory it lists holds a `tracetree` link while the hook's own path does not, the row is a FAIL naming both paths: the install linked the kit where the tracer's hook does not read (`pfm install --config-dir` links under that directory, the hook reads the default one), and `pfm install --yes` will not move it. A kit linked nowhere stays pending. A link at the hook's path with the kit file missing, dangling or unreadable is a FAIL. python3 is not part of that wait: it is a required dependency row, so a host without it fails `pfm install --check` and the install preflight (naming python3 with its install hint), and the tracer-intake python3 row runs in every state as the consequence. The kit and smoke checks live in doctor alone: `pfm install --check` and the install preflight never run them, so a fresh machine and an update that brings the kit install cleanly once python3 is there.

### Exit

Each check returns its warnings and failures to the doctor tally (`pfm/internal/doctor/doctor.go:252-254`). `pfm doctor` exits 3 on any failure, 1 on warnings only, 0 when clean (`pfm/internal/doctor/doctor.go:398-410`). A deterministic stub stays available through `HookProbeOverride` (`pfm/internal/installer/hook_probe.go:490`).

### What the checks' own broken state reports

- Spawn-audit that cannot run: `CHECK FAILED to run … — live chats unaudited`, never "no chats".
- An unreadable ownership ledger: its own UNREADABLE row; ledger-recorded entries read as unjudged, never clean, while command-shape leftovers still report.
- An empty machine config (no accounts): one line saying no Claude config dir is configured, never a silent pass.
- A tracer-intake check that cannot run (no `/bin/sh`, no temporary directory, a timeout): its own `FAIL` row naming the reason, never ok and never skipped.
- A probe that cannot resolve `$HOME`: doctor stops before the checks.

## Discrepancies

1. **The Codex adapter says "Codex has NO hook layer"** (`.claude/engine-sync.json` `codex.rootAdapter`). Codex has one, and pfm reads and writes `{codex home}/hooks.json`. The adapter's conclusion (generated files are read-only) holds, because pfm installs no Codex project hook.
