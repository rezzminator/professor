# Orchestrate, nested — run a flight in a sub-agent

The `flights-orchestrator` agent is the manual; you run it once and read its return. Input: $ARGUMENTS.

1. Resolve the directory: the argument, else the newest under `$HOME/.local/state/pfm/flights/{project}/`. It must hold `index.md`; a `run.md` with `DONE` lines means a resume, and you say so.
2. Assemble the brief, and nothing more: the directory; the standing rules — what the project contract does not carry: the worktree, the fenced command that runs one package's affected tests (the full suite is the gate's, never an executor's), anything the user adds; never a `CLAUDE.md`, pasted or named, since the harness hands it to every executor; each project the index's `files` touch with the path of its testing manual (as `speccer-manual.md` beside the directory records it, else `.claude/commands/{project}-testing-manual.md` or `testing-manual.md`; a project without one is named as such); the worktree when given, with the integration branch it was cut from; the cap when given; the landing: the checks the user names, by command, `commit` when asked, the user's own order for a gate review above `medium` when the user gave one; `revised {ids}` and `applied {ids}` when given.
3. Spawn `Agent(subagent_type: "flights-orchestrator")` with the brief. End your message with one line and no tool call; the return arrives on its own. Never poll, never read `run.md` while it runs. A lander's return that reaches this chat is the orchestrator's: ignore it; its watch reads the same file.
4. On the return: present it verbatim, then one line of your own on what the user owes (a `BLOCKED` question, a commit not made, a missing return). A `LANDED` row: the next flight you start branches from that tip; once the last flight you are running has landed, run the integration branch's gate once (the testing manuals' gate rows), skipped when every landing was a `gated tree`, since the lander gated that exact tree. A `NOT LANDED` conflict or refusal, or a red at that gate, goes to one `general-foreman`, which resolves it and lands the flight through the repository's git writer; nothing else in a landing gets one. `NOT LANDED · unfinished` follows the roads below; the re-run that finishes the flight lands it. A `BLOCKED` question: put it to the user, send the ruling to `Agent(subagent_type: "flights-speccer", model: "opus")` — every revising round runs on opus — as a revising call with the directory, the ruling and the completed ids from `run.md`, then run this command again on the same directory with `revised {the ids of its REVISED line}`: the orchestrator resumes from `run.md` and dispatches the revised tasks. A missing return: run this command again; the orchestrator treats the `CLAIMED` task as not started. A `MAIN-CHAT` row: apply its task file in this chat under `/pcm`, inside the worktree when the flight has one, then run this command again on the same directory with `applied {those ids}`.
