# hooks

Professor reaches a chat through hooks at two tiers. pfm's twenty-three machine-global Claude hooks, one registration each, ride every Claude launch: `claudelaunch.Render` renders them into the `hooks` key of the single `--settings` JSON the chat starts with. `pfm init` scaffolds a project's `.claude/settings.json` from the template, with one hook over the project's own scripts, `format-md.sh`. Claude merges hooks across its settings layers, so the project's hooks run beside the launch's. Codex carries eight pfm handlers, `resume-unkill` and the seven of the [Herdr reporter](#herdr-reporter), which `pfm install` writes into each Codex home's `hooks.json` and trusts; OpenCode carries the Herdr reporter's one staged plugin and no hook. This file holds the inventory, the ownership rule, and the design of the `pfm doctor` checks that prove each pfm hook is in place. The Bash guard over shared git state is designed in [git-guard.md](git-guard.md).

A change lands in this design doc first, then in the code or template, then in every surface listed under [Surfaces that stay in sync](#surfaces-that-stay-in-sync).

Every claim cites the file that proves it. `{claude config dir}` is one account's `configDir` from the pfm machine config; `{codex home}` is one Codex account's home.

## Decisions

- **One list is the truth for pfm's hooks.** `claudelaunch.HookTemplates` (`pfm/internal/claudelaunch/hooks.go`) names all twenty-three hooks, one registration each. `claudelaunch.Render` renders it into every launch's `--settings` payload, and spawn-audit compares each live chat's decoded payload against it. A new pfm hook is a new row there, never a second list.
- **Hooks ride the launch, never a file.** `pfm install` writes no key into any account `settings.json`: no `hooks`, no `statusLine`, no `subagentStatusLine`. A chat carries the hook set it was launched with; a changed set reaches a running chat at its next reload (`pfm chat reload`) or relaunch.
- **pfm never writes a project's `.claude/settings.json`.** The project tier is scaffolded once by `pfm init` (`pfm/internal/professor/scaffold.go:29`) and is the adopter's file from then on. Its hooks merge with the launch's; neither layer replaces the other.
- **Every pfm hook command is the installed binary.** Each command is `$HOME/.local/bin/pfm` plus a subcommand (`pfm/internal/claudelaunch/hooks.go`). No pfm hook runs a shell script or an interpreter.
- **An ownership ledger records hooks pfm wrote into a file.** `$HOME/.local/share/pfm/install/settings-hook-ownership.json` is keyed by physical file, event, matcher and command (`pfm/internal/installer/settings_ownership.go`). Its readers are the Codex `hooks.json` writer and the `pfm-settings` host check. That check combines ledger entries with pfm command shapes to name hooks and status lines an old install left in `settings.json`. It returns BLOCK rows with edits for the operator; it never strips the file.
- **A retired hook is removed by the installer and reported by doctor.** One table names the retired subcommands (`pfm/internal/installer/settings.go:47-59`), with legacy shim hints at `:69-71`; the Codex writer strips them from every `hooks.json` event, and doctor flags any left behind as STALE.
- **pfm hooks fail open.** A pfm hook that cannot do its job writes one stderr line and lets the chat continue. Only the two intercepts exit 2, and only for the prompt they were built to stop; `git-guard` alone also denies a git command it cannot read ([git-guard.md](git-guard.md#how-it-fails)).

## Launch-time Claude hooks (pfm-owned)

`claudelaunch.Render` (`pfm/internal/claudelaunch/render.go`) turns `claudelaunch.HookTemplates` into the `hooks` object of the launch `--settings` JSON: one entry per (event, matcher) pair, each registration once. Every interactive door renders it — `pfm chat new`, the picker and `pfm chat open`, `pfm chat branch`, `pfm chat reload`, `pfm internal agent-open`, a `claude` typed at a shell through the managed launcher ([claude-launch.md](../engines/claude-launch.md#doors)). Three runs carry no pfm hook: a launcher passthrough (`-p`, `--version`, the Claude subcommands, `PFM_LAUNCH_PASSTHROUGH=1`), which execs the real binary untouched; the `claude agents --json` query; and `pfm headless exec`, which is config-free by design. Each command below is `$HOME/.local/bin/pfm …`.

Placement holds by construction: the renderer emits each registration once under its own pair, so a launch cannot carry a duplicate, a moved or a mis-typed pfm hook. The only place such a copy can still sit is an account `settings.json` an older install wrote, which the [pfm-settings row](#account-files-pfm-settings) names for the operator to fix.

The usage hook and the `pfm ls` Limits tab reach `GET https://api.anthropic.com/api/oauth/usage` only through `usagehook.Fetch` (`pfm/internal/usagehook/fetch.go`), which answers in this order:

1. A `cc-rate-limits` statusline snapshot of the seat (`ReadStatuslineSnapshot`): the same config dir, younger than the caller's TTL, its five-hour reset still ahead. No request.
2. The shared cache record `acct-<id>.json` fresh within the caller's TTL: the hook's 180 seconds (`CC_USAGE_TTL`), the Limits tab's 60 (`LiveLimitsTTL`).
3. An active shared backoff: the cached usage with the backoff's error. No request.
4. The `O_EXCL` refresh lock `acct-<id>.lock` beside the cache (`RefreshLockPath`). A lock older than 30 seconds (`lockStaleAfter`) is stale and taken over; a caller that cannot take the lock sends no request and answers from the cache; the holder re-reads the cache and answers if a peer refreshed or backed off meanwhile, and releases the lock on every path.
5. The request, sent with `User-Agent: pfm/{version}`. Success writes the record. A 429 writes the shared backoff (`BackoffFor`): `Retry-After` honored with a ten-minute floor, message `rate-limited — retry HH:MM (429 Too Many Requests)`. Any other failure backs off one minute.

The hook writes a failed refresh to stderr; its prompt output does not change. The statusline writes the snapshots from its stdin `rate_limits` (`recordRateLimits`, `pfm/internal/statusline/render.go`): every window the harness sent, 0% included, under `windows`, beside the flat keys an older build's reader expects.

A blocked prompt returns `decision: block` with the original prompt suppressed (`pfm/internal/hookentry/prompt_block.go:23-28`).

## Project-tier Claude hooks (template)

Source `templates/project/settings.json`, scaffolded to `.claude/settings.json` with the scripts in `templates/project/scripts/` copied to `.claude/scripts/` (`pfm/internal/professor/scaffold.go:29`, `pfm/internal/professor/scaffold.go:33`). pfm never rewrites them after init. Every command runs `$CLAUDE_PROJECT_DIR/.claude/scripts/…`; the `format-md.sh` command first points `CLAUDE_PROJECT_DIR` at the session's current repository when that repository holds the same script and shares the project's git common dir, so a session inside one of the project's worktrees runs that worktree's own copy, and a plugin submodule, a foreign repository (its own copy included) or a directory outside any repository runs the project's. Lane A.11 and the demo's express-hooks beat read that command in its plain form (`infra/fence/lanes/hook-command.sh`). Claude runs them beside the launch's hooks, since hooks merge across settings layers.

The Codex and OpenCode mirror hooks come from the engine-sync Claude plugin, never from a project script (`plugins/engine-sync/hooks/hooks.json`): `PostToolUse` matcher `Write|Edit` runs `engine-sync hook claude mark`, which marks the project's Codex and OpenCode mirrors dirty; `Stop` runs `engine-sync hook claude stop`, which builds and checks both mirrors when dirty and reports a failure as a `systemMessage`; `SessionStart` (async) runs `engine-sync hook claude start`, which rebuilds a stale project and runs `global` when targets exist. pfm's default `claude.plugins` lists `engine-sync`, and `pfm doctor` warns `claude.plugins omits engine-sync` when a set list leaves it out. This repo's own `.claude/settings.json` carries `format-md.sh` only (`PostToolUse`). A long-turn notification is the operator's own hook, never a template one.

## Codex

pfm owns eight Codex handlers: `resume-unkill` and the seven of the [Herdr reporter](#herdr-reporter). `resume-unkill` is a `SessionStart` handler with matcher `resume` running `pfm internal resume-unkill`, the same command and matcher as its Claude row in `claudelaunch.HookTemplates`, from which the Codex writer takes it. Codex fires `SessionStart` with `source` `resume` and the resumed thread's id as `session_id` (codex-cli's `session-start.command.input` schema, `source` one of `startup`, `resume`, `clear`, `compact`, `fork`), so `codex resume`, the in-app `/resume`, pfm's resume of a Codex chat and a pfm Codex pane resuming inside all lift a standing kill through it; the entry resolves an indexed lineage member to its root (`kill.Manager.Unkill`). `pfm install` writes the handler into `{codex home}/hooks.json` for every Codex account, records it in the ownership ledger, and records its trust in that account's `config.toml` (`hooks.state."{key}"`, the key and hash read from Codex's own `codex app-server` `hooks/list`, with a receipt at `{codex home}/.professor-hook-trust.json` so uninstall removes exactly that trust; `pfm/internal/codexappendix/trust.go`). Without a configured Codex binary the install says the hook stays untrusted. The writer still removes pfm's retired hooks while keeping the operator's (`pfm/internal/installer/codex_hooks.go`). The fleet prompt reaches Codex through `config.toml`'s `developer_instructions`, never a hook. The seven Herdr handlers run `pfm internal herdr-state --engine codex {start|working|blocked|idle|end}` on `SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PermissionRequest`, `Stop`, `Interrupt` and `SessionEnd`, each with a 5 s timeout (`herdr.EngineKillTimeout`) except `Interrupt` and `SessionEnd`, which take 3 s, the most Codex allows them (codex-rs `SESSION_END_MAX_TIMEOUT_SEC`; over it Codex warns at load, which `pfm doctor` reads as `UNREADABLE`), and an install rewrites an owned handler whose timeout differs (`pfm/internal/installer/codex_hooks_herdr.go`); the installer writes, trusts, records and removes them exactly like `resume-unkill`. An unparsable file is skipped loudly unless owned hooks would be stranded.

## OpenCode

pfm ships no OpenCode hook. Its one OpenCode plugin is the [Herdr reporter](#herdr-reporter)'s bridge. OpenCode has no appendix hook; the staged prompt reaches it through the `instructions` config array (`pfm/internal/installer/opencode_instructions.go:12-17`). The generated mirrors are protected by a permission deny in `.opencode/opencode.jsonc` instead of a hook (the machine policy `templates/global/engine-sync.json` `opencode.permission`).

## Herdr reporter

**Purpose.** [Herdr](https://herdr.dev) detects an agent by the foreground process of a pane. A tmux-backed pfm chat pane runs `tmux attach`, so Herdr sees `tmux`, never the engine. That bridge reports through `pane.report_agent` and `pane.release_agent` on `$HERDR_SOCKET_PATH`, under the stable source `pfm` (`herdr.Source`), with a strictly increasing `seq`. Native non-tmux Claude instead leaves lifecycle state to Herdr's own detection: no `pane.report_agent`, including on sub-agent events. The event map and sub-agent set below describe the tmux Claude bridge; Codex and OpenCode reporting remain unchanged. One implementation serves all three engines: `pfm internal herdr-state [--engine claude|codex|opencode] <start|working|blocked|idle|end|notification|title>` for engine events (Claude also `agent-start|agent-stop`) and `pfm internal herdr-state <sync|detach|name> --socket {tmux socket} --session {session} [--client {pid}]` for the chat tmux server's hooks (`pfm/internal/hookentry/herdr_state.go`, `herdr_clients.go`, `herdr_name.go`; the wire in `pfm/internal/herdr/`), reading the hook JSON on stdin.

### deferNativeClaude

`nativeSeat` (`pfm/internal/hookentry/herdr_seat.go`) proves the durable native owner before `deferNativeClaude` (`pfm/internal/hookentry/herdr_native.go`) releases old `pfm` ownership at a newer `seq` and publishes state-free session metadata. `sessionOnly` sends `pane.report_agent_session` under `herdr:claude`, carrying the session and custom `resume_argv` `[pfm, chat, open, --restored, {SID}]`; the `pfm` source cannot persist this state-free restore record. A `resume_not_accepted` before Herdr's native process detection retries every 100 ms within the existing 3 s hook deadline, retaining the argv. Failure stays visible and retryable; completion is stored only after both release and publication succeed. A later `SessionStart` refreshes the metadata. The `nativeClaude` guard in `apply` (`herdr_state.go`) prevents an unproved bare native launch from falling back to state reporting. Naming, durable seat bookkeeping and other non-state integration remain in place; the twenty-three launch hooks are unchanged.

### retireNativeTargets

`runActivity` and `expireAgents` (`pfm/internal/hookentry/herdr_activity.go`) call `retireNativeTargets` under the shared activity lock. It persists removal of native replay targets from legacy `Targets` before releasing ownership; pending releases live separately in `RetiredTargets`. An old worker takes the same lock and rereads `Targets`, so an in-flight old send finishes before retirement and cannot replay a removed target afterward. A failed release remains retryable. Positive tmux proof keeps a target: the complete socket/session/numeric-client tuple plus terminal identity, not merely an absent native flag. Tmux agent membership and its watchdog remain active; native Claude `agent-start` and `agent-stop` return without touching the pane.

**Payload bounds.** `readHerdrPayload` (`pfm/internal/hookentry/herdr_origin.go`) decodes selected top-level fields and skips unknown values with a JSON token stream, rather than truncating the object at 1 MiB. Large `tool_response` and prompt fields still report working; `agent_id` and explicit null `transcript_path` are read even when they follow the large value. The full stream is validated before any state change. Reads, decoder tokens and retained fields are bounded by a 64 MiB input budget (plus one overflow-detection byte), nesting by 1000 levels. Overflow is named as `hook payload exceeds … bytes (skipped)`, not malformed JSON; decode diagnostics name the engine. Invalid or over-budget input reports nothing because its child identity cannot be proved.

A sub-agent event (a payload `agent_id`, or an OpenCode child session) never touches the pane, except tmux-backed Claude's `SubagentStart` and `SubagentStop`, which keep the sub-agent set below. Native non-tmux Claude sub-agent events have no exception and never touch the pane. Nor does a Codex thread that keeps no rollout (`transcript_path` JSON `null`: the memory consolidation thread Codex runs inside the chat's own process; `threadWithoutRollout`, `pfm/internal/hookentry/herdr_origin.go`); the chat's own thread names its rollout in every event, and an absent key still reports. A release also clears the pane's metadata title (`pane.report_metadata` `clear_title`), and an end event inside a pfm chat server empties that server's `set-titles-string` first: the terminal title Herdr shows is the outer title tmux writes under `set-titles on`, whose last write after the engine's own title empties would leave `⬢ `; blanked, tmux writes the empty title and nothing after it. An engine in the user's own tmux leaves that server's titles alone, and so does a reload's `/exit`, whose engine respawns on the same server: the end event asks `reload.InFlight` for its socket and pane, as `exit-close` does; an end whose server keeps another pane (a pane the user split beside the chat) leaves the title too, and a reload probe or pane list that fails leaves it as it is, with a warning. The agent label is the engine's own name (`claude`, `codex`, `opencode`).

**Sub-agent set.** For tmux-backed Claude the reporter keeps a set of `agent_id`s per `session_id`; `agent-start` adds, `agent-stop` removes, idempotently. While it is not empty, `Stop` and `idle_prompt` report working `N agents running` (`1 agent running` at one); the last `agent-stop` is idle only while the main turn remains stopped, else working. `UserPromptSubmit` starts the main turn; an accepted main-thread working tool event also clears `MainStoppedAt`, even with other agents running, so an automatic resume stays working after the last agent stops. Old-sequence main-thread hooks are still rejected. `SessionStart` `startup`, `clear` or `resume` resets the set, `compact` keeps it. A permission request stays blocked. Tracked transports share a session lock and private persisted state (`herdr_activity.go`). When `runActivity` bypasses durable membership, including a tmux host without Herdr, `agent-start` and `agent-stop` are ignored rather than mapped to main-thread working; main working and Stop theme behaviour stays unchanged. A lost `SubagentStop` is bounded by a one-hour lease (detached watchdog) that starts at the main `Stop` leaving agents tracked: at the deadline the residual agents expire and the pane reports idle, or stays blocked on an open permission request. A new main-turn working event cancels the stopped-turn lease, its later `Stop` starting a fresh hour; `idle_prompt` and agent events never extend a running deadline. The watchdog logs transient errors and retries; an ended session removes its activity file.

**Pane identity.** A chat's own process environment keeps the `HERDR_*` variables of the shell that created its tmux server, the wrong pane for a chat attached later or from another pane. Inside a pfm chat tmux server (`$TMUX` set) the reporter therefore never trusts its process environment. With neither Herdr (`HERDR_BIN_PATH` set or `herdr` on PATH) nor theme sync it writes nothing to tmux or disk; with theme sync alone main working and Stop events still paint tmux state without making Herdr calls, while agent lifecycle events are ignored. One rule, `herdr.Resolver` (`pfm/internal/herdr/resolve.go`), answers "which Herdr pane runs this tmux client" for the reporter and for presence (below): it reads the client's own environ (`HERDR_ENV`, then `HERDR_SOCKET_PATH`), asks the pane `HERDR_PANE_ID` names first, then walks every `pane.list` pane, and takes the pane whose `pane.process_info` foreground holds the client pid. `HERDR_PANE_ID` is only the pane asked first, never trusted on its word: it goes stale after a Herdr restart or a re-attach. A client whose environ lacks `HERDR_ENV=1` runs outside Herdr and is silent: no Herdr call, no error row. A client inside Herdr that no pane holds is an error row naming the pid and the socket, and is never sent to.

The server carries four hooks, all `set-hook -g {name}[50] run-shell -b "'{pfm}' internal herdr-state {event} --socket #{q:socket_path} --session #{q:session_name}[ --client #{q:client_pid}]"`: `client-attached` → `attach`, `client-resized` → `sync`, `client-detached` → `detach`, `window-renamed` → `name` (no `--client`). The command is quoted for both layers (the pfm path single-quoted for sh, tmux values through `#{q:…}`, the whole command in the spelling `show-hooks -g` prints), so a converged server is never rewritten. `config.ChatServerOptions` (`pfm/internal/config/tmux_titles.go`) also sets `update-environment[20..23]` to the four `HERDR_*` names.

**Adoption.** Every reporter run except a release adopts: `liveClients` lists the session's tmux clients (`list-clients -t {session}`, the call a registry with clients makes anyway), and each live client missing from the registry is resolved by `herdr.Resolver` and registered, so a record born before the hooks, across a Herdr outage or after a Herdr restart heals on the next engine event, `attach`, `sync` or `name` (`reconcile` is the one client pass of the three tmux-fired verbs). `end`/release events, the sweep and `detach` never adopt: adopting there would resurrect the client they release. The registry is the session option `@pfm_herdr` (`clients`, keyed by client pid: pane, Herdr socket and terminal); a new or moved pane is sent the stored state again. A tmux client that vanished without a `detach` hook is released at the next run without a process walk. Every event stores `{engine, session_id, state, message, seq}` under a per-session `flock` (3 s deadline; a stored `seq` above the event's makes the event stale) and reports to every live registered client, so two panes attached to one chat both show it, and `detach` releases only the detaching client's pane (tmux 3.7c expands `client_pid` to empty on detach: a detach without a pid releases and forgets every registered client tmux no longer lists). Outside tmux (a direct run) the reporter addresses the pane of the chat's durable seat, the one whose supervisor is in the hook's ancestry (`gather.HerdrChatSeat`), never the inherited `HERDR_PANE_ID`, which a pane move leaves dead; a Codex event uses the [Codex pane registry](#herdr-reporter) instead.

**Re-announce.** `pfm name-sync --apply` calls `hookentry.HerdrReannounce(ctx, socket)` for every live chat server, right after the tmux options converge. Per session, under the session lock, it adopts the live clients, re-binds the registered ones, releases the vanished, stores `unknown` (the engine named by the socket prefix, `seq` untouched) when no engine event ever stored a state and a live client sits in a Herdr pane, and reports the stored state and the name to every live client. It prints `herdr re-announce {socket name}: {n} client(s) {pane ids}`; an error goes to stderr as `pfm name-sync: {err}` and counts in `tmux options unverified` (exit 1). A host without Herdr reaches nothing and says nothing. A chat whose engine carries no herdr hooks (launched before them) is therefore adopted with its name and shown as `unknown`, Herdr's own "not known" rather than a guessed idle, and presence (below) adds `launched without Herdr hooks: pfm chat reload {name}`; any later engine event outranks the `unknown` by `seq`.

**Codex pane registry.** A Codex hook never takes its pane from its own environment (`runCodex`, `pfm/internal/hookentry/herdr_codex.go`). A bare `codex` TUI hands its thread to the shared app-server daemon, whose hooks run with the daemon's environment: the `TMUX` and `TMUX_PANE` of whichever chat started the daemon, no Herdr pane; the session id never reaches the TUI's side (codex-cli 0.162.1, daemon 0.163.0, probed live). A `SessionStart` whose hook runs under an interactive Codex process (the first process above the hook that is no shell, pfm or command wrapper, its command or `argv[0]` named `codex`, its command line passing `codexRunsAsInteractiveChat`) registers that session's pane in `{state}/pfm/herdr/codex-{session_id}.pane`: the process's pid and command, and the pane its own environment names, set by the pane that started it: tmux's `TMUX` and `TMUX_PANE`, else Herdr's `HERDR_ENV`, `HERDR_PANE_ID` and `HERDR_SOCKET_PATH`, else none (a plain terminal; `codex exec` and `review` register no pane either), so its events stay silent. A registration drops every other record of the same process and every record whose process is gone: one pane, one session; a record whose process cannot be read is kept, and a sweep that fails is an error row that still lets the session report. A host with neither Herdr nor the theme sync registers nothing. Every other Codex event reports to its session's record, through the tmux path when the record names a tmux pane, and to a recorded Herdr pane through `gather.HerdrChatPane`, so a moved native seat's events reach its seat's pane rather than the TUI's birth id; a `SessionEnd` releases the pane, clears its title and removes the record, except reason `clear` or `resume`. An event with no record (the daemon's own `SessionStart`, whose process is `codex app-server`, or a hook under no Codex process; any thread that is not the pane's registered session), a session id that is not a plain name, a record whose process is gone or now runs another command (the record removed), or one whose process cannot be read (the record kept) reports nothing and writes one error row, on a host with Herdr only. A Codex session on the shared daemon is therefore unmapped by design: no pane reaches its hooks, so it reports nothing through pfm and its pane state is Herdr's own title detection; a bare `command codex` (the shell function bypassed) stays that way, each of its hooks writing the unmapped error row that holds `pfm doctor`'s Herdr reporter row at WARN. The cure is the in-process run: every Codex TUI pfm starts passes `--no-daemon` right after the binary word (`CodexTransportArgs`, `pfm/internal/hookentry/codex_launch.go`), so its hooks run under the TUI and the registration above finds its pane. The doors are the shell's `codex` function, which asks `pfm internal codex-transport` about its arguments (`pfm/internal/installer/assets/shim/pfm.zsh`); `cx` and the picker's fresh chat (`pfm internal codex-launch`); and `chat new`, the MCP `new` tool, `chat open` (every resume: picker, FleetView, Herdr's `agent_resume`), `chat branch` and `chat reload` (`action.codexCommandWithAccount`, `reload.codexRun`), whose arguments pfm builds itself. A call that opens no TUI gets nothing: help, version, every subcommand but `resume` and `fork` (`agents` browses the daemon itself). The user's own transport is respected: a launch whose arguments before any `--` already carry `--no-daemon`, `--remote[=ADDR]` or `--remote-auth-token-env[=ENV]` reaches Codex exactly as typed (codex-cli 0.162.1 refuses `--no-daemon` beside `--remote`, and a repeated `--no-daemon`). A shell `codex` whose `pfm internal codex-transport` fails says so on stderr and starts Codex on its default transport. Every other engine believes `$TMUX` (`socket,server pid,session`) and `$TMUX_PANE` as they stand (`tmuxOrigin`, `pfm/internal/hookentry/herdr_origin.go`).

**Pane moves.** Herdr's `pane.move` keeps the terminal and gives the pane a new public id; the id a client's environment holds was set when its shell started and so goes stale. The registry therefore records the pane's `terminal_id` (from `pane.list` at attach), and every send to a registered client first resolves the current pane id through `pane.list`: the pane holding that terminal receives the report, the release, the name and the title. A changed id re-binds the registry and re-sends state, session, name and title; no request names the vacated id, which Herdr may hand to another pane. Without a recorded terminal the recorded id is used if `pane.list` still holds it (its terminal is then bound). A terminal in no pane, or a recorded id `pane.list` no longer holds, falls through to `Resolver.PaneRunning` (the pane whose `pane.process_info` foreground holds the client pid) before any error; none holds it, or a failing `pane.list`, sends nothing and writes an error row. The `client-resized` hook runs `sync`, which adopts a live client and re-binds the registered ones (a no-op for an unchanged pane; `attach` does the same): a move usually resizes the pane, so the chat re-binds at once; a move that leaves the size alone re-binds at the next event. Flip the hook off by deleting `herdrResizedHook` in `config/tmux_titles.go`.

**Names.** `@pfm_chat_name` is a session option holding the chat's exact name; every writer sets it in the same tmux command as the rename and before it (a final `;` is escaped `\;`): `gather.RenameWindow` (name-sync's Codex half and the statusline's `convergeWindowName` for a Claude `/rename`), `renameChatWindow` (`pfm chat name`, the MCP name tool), `spawn.TmuxSpawner.NewSession` (`chat new`, `chat branch`). A writer of a name no user chose (name-sync's Codex half for a thread named only by its first prompt, the OpenCode title below, `chat new`'s pool name when no `--name` is given, `chat branch`'s default `{parent}-branch` name, `SessionSpec.ChatNameAutomatic`) also sets `@pfm_chat_name_auto` to it in the same command (`gather.AutomaticChatNameCommand`); a user's writer leaves it as it was. The `window-renamed` hook (it fires for `rename-window` from a command client, also for an unchanged name) runs `name`. `name` and the SessionStart events share one name sync: an unset `@pfm_chat_name` is an unnamed chat and Herdr keeps its default; a named one is slugged by `herdr.AgentName` (lowercase, `[a-z0-9_-]`, at most 32 characters, the shortest free `-2…-9` suffix against `agent.list`), sent with `agent.rename`, and the exact name goes to `pane.report_metadata` as the pane `title` (80 characters) and, when the agent sits alone in its tab (`tab.get` `pane_count` 1, the `tab_id` its `agent.list` entry names), to `tab.rename` as the tab's `label` (a changed name equal to `@pfm_chat_name_auto` is re-announced through `herdr.ReannounceSoleTab`, so a label the user set in Herdr stays; any other changed name goes through `herdr.LabelSoleTab`; a user who picks a name equal to the stale mark is read as automatic once), the text Herdr's tab bar and its sidebar `tab` token show; a tab holding other panes, or already carrying the name, keeps its label, and a tab Herdr will not read or relabel is written to stderr and the error log without holding the name back (the next name change or re-announce tries it again); the name is stored in `@pfm_herdr` once every pane carries it, so a rename that leaves it unchanged names only a pane just attached or moved, and a failed naming is tried again by the next rename. A release sends `clear_title`. OpenCode's plugin forwards a main-session title change (`session.updated`, no `parentID`, never the default `New session - {ISO time}` placeholder, once per changed title) as `pfm internal herdr-state --engine opencode title` with stdin `{"session_id","title"}`, which sets `@pfm_chat_name` and `@pfm_chat_name_auto` (a final `;` escaped) and renames the window in one tmux command, so the same hook follows. Unnamed creation sets nothing.

**Clear successor name.** A Claude `/clear` hands the conversation to a new session id; the pre-clear session keeps its title, and `clear-kill` hides it from the picker behind a prompt baseline until a resume or a new prompt brings it back. `naming.ClearSuccessorName(original, sessionID, occupied ...string)` (`pfm/internal/naming/clear.go`) owns the naming scheme: a named chat's successor is `{base} #{N}`, N the smallest free integer >= 2. `base` is the inherited name with one trailing space-then-`#N` suffix stripped, so clearing `INTEGRATION` names `INTEGRATION #2` and clearing that names `INTEGRATION #3` while `INTEGRATION #2` is occupied, never `INTEGRATION #2 #2`. The original name counts as occupied even when its predecessor is not indexed, and so does every name in `occupied`. An unnamed chat's successor stays unnamed (empty input creates no name), and a session id that is no UUID or an original name that is not one line is an error. `pfm internal clear-name` (the `clear-name-start` and `clear-name-prompt` rows) decides, in order:

- **`SessionStart` with source `clear`** (`clearNameEvent`, `pfm/internal/hookentry/clear_name.go`), under the successor's seat lock: it reads the original title from the payload's `session_title`, else the transcript (`transcript.FileTitle`), and persists `naming.ClearName` (`inherited`, `name`, `emitted`, `confirmed`) in the shared fleetdb meta key `clear-name:{UUID}`. `ClearName` runs the whole event, database and seat-lock work included, under `context.WithTimeout(promptHookDeadline)` (5 s), so a stuck lock or database fails open instead of holding Claude. The name is reserved, never recomputed: `store.Store.ReserveClearName(ctx, id, original)` delegates to `fleetdb.Store.ReserveClearName(ctx, id, original, cachePath, at)` (`pfm/internal/store/clearname.go`, `pfm/internal/fleetdb/clearname.go`), which receives the derived cache that `clearNameEvent` first opened and initialized through `store.OpenContext`, then on the shared-state connection ATTACHes that cache and takes `BEGIN IMMEDIATE`, locking both databases. Inside that lock it reads every occupied name: the stored transcript names (custom title, AI title or first prompt per `naming.DisplayName`, with the durable clear overlays applied), Codex `cx_names`, durable seat names, fleet chat labels and the existing clear decisions excluding the successor's own. It computes `naming.ClearSuccessorName(original, id, occupied...)`, writes the decision with `PutClearName`'s record shape in the same SQLite transaction and commits, so two concurrent clears of one name never take the same number. A lookup that fails is a visible error and reserves no guessed name; an empty original reserves nothing. A stored record is read back through `naming.ClearName.Validate(id)`, which checks the numbered shape (`name` is `{base} #{N}` with N >= 2 and `base` the inherited name stripped of a trailing space-then-`#N` suffix), not a recomputation, because the choice depends on the occupied names of the moment it was made. It seeds the derived store cache with the successor's row when none exists, never Claude's transcript (`store.Store.SeedClearTranscript` is `INSERT … ON CONFLICT(uuid) DO NOTHING`, so a row a concurrent index pass already wrote is never clobbered), then re-runs `HerdrState start` on the same payload: hooks run concurrently, and an earlier `herdr-start` would otherwise leave the pane with the inherited name.
- **`UserPromptSubmit`**: for a pending record whose `emitted` is false, it prints `{"hookSpecificOutput":{"hookEventName":"UserPromptSubmit","sessionTitle":"{fresh name}"}}` once and stores `emitted`. It prechecks the decision before the seat lock (`state.ClearName`: missing, `emitted` or `confirmed` returns at once, so an ordinary prompt never contends for the lock) and rereads it under the lock before it emits. A failure there reports `session {id} pending title check failed (fail-open)`, the `SessionStart` failure keeps `successor {id} NOT named/titled (fail-open)`. Claude's documented `SessionStart` `sessionTitle` output covers `startup`, `resume` and `fork` and excludes `clear` (<https://code.claude.com/docs/en/hooks.md>), so Claude's own title is applied at the first prompt, while pfm and Herdr carry the name from the `/clear`. The hook injects no terminal `/rename` and writes no transcript. A user rename between the `/clear` and the first prompt, or a `confirmed` record, emits nothing: the user's name stands.
- **Overlay.** `naming.ClearName.Title(current)` returns pfm's name only while the engine's title is empty or still the inherited one and `confirmed` is false. `store.clearNames` (`pfm/internal/store/clearname.go`) applies it to every transcript a list returns from one shared-state read of every decision (`ClearNames`), never one `Meta` query per transcript, and persists `naming.ClearName.ObserveTitle(current)`, which sets `confirmed` once the engine's title is non-empty and differs from `inherited` (pfm's fresh title or a deliberate user rename), so a later rename, one back to the original name included, wins. `fleetdb.Store.PutClearName` writes one SQL upsert that OR-merges the `emitted` and `confirmed` flags with the stored ones, so a stale observer and the prompt hook, each holding an older snapshot, never undo each other. A store opened by `store.OpenWithoutMigrating` (`pfm doctor`, `readOnly`) applies the overlay without persisting an observation, `SharedDegraded` stays visible separately, and the raw cache read stays available when the shared half is degraded. The Herdr reporter's `engineName` persists the same observation, and the first-prompt hook observes it before it decides to emit.
- **Herdr and tmux.** The Herdr reporter's `engineName` (`pfm/internal/hookentry/herdr_engine_name.go`) reads the transcript title through the same `Title` rule, except that a `working` report from any hook but `UserPromptSubmit` (`PostToolUse`, `PostToolUseFailure`) skips it, so the per-tool hot path never scans a transcript; lifecycle, `Stop` and prompt events still converge a rename. A tmux chat syncs it to `@pfm_chat_name` on each engine event but the end (`syncTmuxEngineName`, run while the report lock is held); a native Herdr seat goes through `chat.RenameHerdrOwned` (`pfm/internal/chat/herdr_name.go`), the path `DeliverName` uses, which records `seat.Name` only after the pane, agent and sole-tab writes all succeed, so a failed one is retried at the next event.
- **Native `/rename`.** An in-engine `/rename` fires no hook: its name is read from the transcript at the lifecycle events above and by `pfm name-sync --apply`, which calls `chat.ConvergeHerdrNames` (`pfm/internal/chat/herdr_name_sync.go`) for proved native seats.

Every failure is a stderr line and exit 0 (fail-open); a successor that could not be named is never reported as named.

**Only the pane's own engine reports.** A child engine a chat starts itself (`codex exec` from a Bash call) inherits `$TMUX` and the Herdr names. Two layers keep it silent. The doors we launch strip the names: headless `run`, `claudelaunch.ProbeEnv`, the usagehook version probe, the statusline and codexappendix `codex app-server` helpers and the launchers' non-interactive pass-through (Claude: arguments-decided pass-through only; Codex: every pass-through subcommand, `exec` and `review`, also `TMUX` and `TMUX_PANE`) drop `HERDR_*` (`herdr.StripPane`, `herdr.StripReporter`); `claudelaunch.Hygiene()` is unchanged, so interactive launches keep them. For doors nobody enumerated, an engine-fired event (not `attach`, `sync`, `detach`, `name`) walks up from the hook process, skips shells and pfm, and takes the first other process as the firing engine; above it, a command wrapper (`env`, `timeout`, `caffeinate`, …) is skipped, and a `node` launcher with no shell or pfm between it and the engine is the engine's own (npm's Codex runs its native binary under one). It reports only when no second engine sits between the firing engine and the pane pid; an unreadable process table or pane pid, or a hook that does not run under the pane, reports nothing and writes an error row.

**Errors.** Every reporter error goes to stderr and is appended to `{HerdrLockDir}/{session}.log` (`herdr.AppendError`, one RFC 3339 time, a tab and the message per line; `AppendInfo` inserts an `INFO` column for expected lifecycle outcomes, which `RecentErrors` excludes; legacy unlevelled records remain errors), because tmux `run-shell -b` discards stderr.

**Retention.** `RecentErrors` (`pfm/internal/herdr/errlog.go`) reads both `{session}.log` and `{session}.log.1` under a shared directory flock; writers hold the exclusive flock through rotation and append. Storage stays bounded to two log generations plus a fixed-size `{session}.log.lost` watermark. Before replacing `.log.1`, the writer atomically records the newest discarded error timestamp, preserving any later timestamp already recorded; discarding only INFO records does not advance the watermark. `RecentErrors` returns retained errors at or after the requested cutoff, newest first, together with `ErrorLogIncompleteError` when a watermark is at or after that cutoff. Historical loss predating the watermarks cannot be reconstructed. Corrupt or unreadable retained files, including a malformed watermark, return contextual errors, never an empty success.

**Reporter diagnostics.** `printHerdrReporterErrors` (`pfm/internal/doctor/herdr_check.go`) prints the `herdr-reporter-errors` row: ok with no errors retained in the last 24 h and no overlapping loss watermark; otherwise WARN with the count, newest message, session and the actual `ErrorRecord.LogPath`, which may name `.log.1`. An incomplete window produces WARN with the retention error and retained count, followed by every retained error's session, timestamp, message and actual log path, even when the retained count is zero; it never claims a clean 24 h window. A corrupt or unreadable log produces WARN with the contextual read error.

Herdr's socket answers one request per connection and then closes it, so `herdr.Call` dials once per request line; a second line on one connection reads EOF or a broken pipe. A release or detach whose pane Herdr no longer lists, or answers `pane_not_found` for (Herdr 0.9.5's code; the socket-api docs spell it `not_found`, also honoured), is no error: the pane closed with its chat and has nothing left to release. A dial, `pane.list` or report failure stays an error row. An engine `end` that cannot read a pfm chat server whose socket is confirmed missing records `INFO`, not an error: ending the server disconnects all its tmux clients, and Herdr clears its agent when that foreground client exits (the bare-shell observation below). There is no surviving session option to release from; inherited Herdr pane variables are stale and must not be used to guess a release target. A missing server during a live event, a server that still has a socket, an unreadable socket path, and every durable-seat cleanup failure remain errors.

**Launch.** Whichever tmux verb (`attach`, `sync`, `name`) adopts a client of a session with nothing stored reports the pane under the engine its socket names (`cc-` Claude, `cx-` Codex, `ox-` OpenCode) and stores that state, `seq` untouched, so a chat shows in Herdr from its first attach: Codex and OpenCode `idle`, as Codex fires `SessionStart` only at its first turn and a later `SessionStart` reports the same idle with the session; Claude `unknown`, as a hooked Claude chat stores its state at `SessionStart`, so one with nothing stored was launched without the herdr hooks (its first `SessionStart` outranks the `unknown`).

**Shells.** A plain shell or server pane reports a long command when it finishes, as its pane title. Output never counts. The shim (`pfm/internal/installer/assets/shim/pfm.zsh`) adds a zsh `preexec`/`precmd` pair only in an interactive shell with `HERDR_ENV=1` and no `$TMUX`, so a pfm chat's own tmux pane keeps its chat reporter. A command that ran at least `PFM_HERDR_LONG_COMMAND_SECS` whole seconds (default 10, also when the value is no number) runs `pfm internal herdr-shell done --pid {shell pid} --at {$EPOCHREALTIME} --command {line} --exit {status} --seconds {n}` in the background; the next command, or the shell's `zshexit` (a nested zsh left by Ctrl-D runs no `preexec`), runs `pfm internal herdr-shell release --pid {shell pid} --at {$EPOCHREALTIME}`. `PFM_HERDR_SHELL_REPORT=0` turns it off. The entry (`pfm/internal/hookentry/herdr_shell.go`) finds the pane whose `pane.process_info` `shell_pid`, or one of whose foreground processes, is that pid: the pane the shell was born in first, then every `pane.list` pane, because a move gives the pane a new id. Both runs of one shell hold its lock (`{HerdrLockDir}/pfm-shell-{pid}.lock`); a release records its `--at` in `pfm-shell-{pid}.released`, and a done whose `--at` is older reports nothing, so a done the next command overtook never leaves a stale done. The shells reporting to one pane (a nested shell and its parent hold different shell locks) also share the pane's lock (`pfm-shell-pane-{pane}.lock`), because a title carries no seq and the last one Herdr gets is the one the pane shows: a done records its `--at` in `pfm-shell-pane-{pane}.title` before it sends the title and keeps it when the send errors (a timed-out send may have reached Herdr), a release started before that done sends no `clear_title`, and an older done reports nothing over it, so a nested shell left by Ctrl-D never clears the title of its parent's later done. A record holding no shell clock is an error row and is dropped, so it never stops the pane's reports. It reports `working`, then `idle` with `{command} exit {status} · {n}s`, the command cut to fit Herdr's 240-rune message and never the status and duration, under the source `pfm-shell` and the agent `shell`, because a lone `idle` on a pane with no agent shows nothing; Herdr drops any agent report within a second once the bare shell holds the foreground again, so the same text, cut to Herdr's 80-rune title and never the status and duration, is also the pane's title (`pane.report_metadata`, source `pfm-shell`), which Herdr keeps on a bare shell. The next command's release sends `pane.release_agent` and `clear_title`, restoring the terminal's own title. Every failure, a done that finds no pane running the shell included, is a line in `{HerdrLockDir}/pfm-shell.log` that names each Herdr request by its method, id and pane, never the command it carried, which the `herdr-reporter-errors` row reads. A shell found among a pane's foreground processes is a nested shell (a `zsh` started inside the pane's own shell): its done also records that pane's terminal in `pfm-shell-{pid}.pane`, because the next command takes the foreground from it; a release that finds the shell in no pane goes to the pane now holding that terminal and drops the record. A release with neither a pane running the shell nor a recorded terminal in a pane has nothing left to release.

**Presence.** `pfm chat ls` and the chat MCP's `ls` show each chat's Herdr presence, both from `pfmchat.List` (`ListResult.Herdr`, `pfm/internal/herdr/presence.go`), live and read-only: the registered clients plus every live tmux client of the session (`list-clients -t {session}`), by pid. A registered client is placed by its terminal id, so a moved pane reads right; an unregistered live client by `herdr.Resolver`, so presence is right before the reporter has run. One client reads `{pane} {workspace} {agent status} {agent name}` (`{pane} {workspace} no-agent` when Herdr lists no agent on that pane). A pane whose agent Herdr reports `unknown` for a chat launched without the Herdr reporter hooks gains `· launched without Herdr hooks: pfm chat reload {name}`; hookless is read from the chat's Claude process argv, the way spawn-audit parses it (`claudelaunch.Parse`): no `herdr-*` hook in the `--settings` payload. An argv that cannot be read or parsed adds no hint and is a warning line (stderr for `pfm chat ls`). A live client Herdr cannot place, beside one it can, follows the panes shown as `herdr error: {cause}`. A chat shown nowhere says why: `not in herdr` (no client, or no pane found), `attached outside Herdr` (every live client runs outside Herdr), `herdr unreachable: {err}` (the socket dial, `pane.list`, `agent.list` or `workspace.list` failed) or `herdr error: {cause}` (any other failed lookup); `—` on a host without Herdr (no `HERDR_BIN_PATH`, no `herdr` on PATH), with no socket call. One `pane.list`, `agent.list` and `workspace.list` per Herdr socket serves a whole listing. `parsePresencePanes` and `ParseWorkspaceList` (`pfm/internal/herdr/presence.go`) require non-null `panes` and `workspaces` arrays, respectively, as `ParseAgentList` (`pfm/internal/herdr/wire.go`) requires `agents`: a missing or null required array is a contextual lookup error, while explicit `[]` is a valid empty result. Failed lookups remain unknown/error, never proof of an absent pane, agent or workspace.

**Resume.** The tmux bridge's session start reports `resume_argv ["pfm","chat","open",<session id>]`; native Claude's state-free session publication carries `["pfm","chat","open","--restored",<session id>]` under `herdr:claude`. After a Herdr server restart Herdr runs it in the restored pane, and `pfm chat open` attaches the live socket or resumes the chat on the account that owns it. A session id Herdr's rules refuse (empty, an apostrophe, a control character, more than 64 words or 8 KiB) omits `resume_argv` and writes one stderr line. Herdr's own `[session] resume_agents_on_restore = false` opts a host out.

**Transcript watch.** A Claude blocked event inside a pfm chat server, whose session names are unique (the user's own tmux keeps no watch) (`herdrReporter.watch`, `pfm/internal/hookentry/herdr_watch.go`) writes `{HerdrLockDir}/{session}.watch` under the session lock, holding the blocked event's `seq`, and starts `pfm internal herdr-state watch --socket {tmux socket} --session {session} --seq {seq} --transcript {transcript_path} --offset {bytes}` detached (its own session, stdio `/dev/null`). The transcript is the payload's `transcript_path` (absolute, `.jsonl`, a regular file, opened without blocking so a FIFO in its place is an error), read only past the size it had at the block, so an earlier turn's entry never matches. Every 250 ms the watch reads the new complete lines; a `type` `user`, non-sidechain entry whose whole content (a string or one text block) is `[Request interrupted by user for tool use]` ends the turn: Claude Code 2.1.301 writes it 1-2 ms after the `tool_result` rejection (`The user doesn't want to proceed with this tool use. The tool use was rejected …`, `toolUseResult` `User rejected tool use`) for Esc and No alike. The rejection alone is no trigger: a rejection with feedback continues the turn. On the entry the watch takes the shared activity lock, then the session lock, and settles the interrupted main turn only while the stored state is still blocked at its `seq`: working `N agents running` while sub-agents remain, else idle, stored at `seq + 1`, so any event started after the block outranks it and a newer state is never overwritten. Every later stored state of the session, a release included, removes the record, and a second blocked event rewrites it; the watch exits at its next poll when the record is gone or names another `seq`, so one session runs one live watch and no process is ever signalled. It also exits after 30 minutes, which bounds a forgotten dialog's sleeping process; the `idle_prompt` notification covers what follows. A watch failure (an unreadable or missing transcript, a failed start, a lock timeout) is an error row in `{HerdrLockDir}/{session}.log` and never changes the event's own report.

**Contract.**

- `seq` is the UnixNano of the process start, so concurrent events from separate processes order by start time.
- The entry is fail-open and always exits 0: a hook exit 2 would block Claude. A socket that is missing, refused or slow (500 ms dial, 1 s I/O) writes one stderr line with its full context.
- Outside Herdr it makes no Herdr socket call. With theme sync on, a pfm chat tmux server still paints main working and Stop state, but agent lifecycle events bypassing durable membership are ignored; without either surface it is inert: no stdout, no stderr, no socket, no tmux write. The lane beat `O2.05-internal-plumbing` proves the inert path against the built binary; the socket path is unit-tested.
- A message is capped at 240 runes.

**Doctor.** Herdr ships its own bundled integrations for Claude, Codex and OpenCode, which report the same panes under the source `herdr:{engine}` and would compete with pfm's. `pfm doctor` runs `herdr integration status` per engine and prints a FAIL row for each one installed, with the fix `herdr integration uninstall {engine}`; with `herdr` absent the row is ok and not applicable; an unreadable status is a warning row, never ok (`pfm/internal/doctor/herdr_check.go`).

**Recorded forks.** The agent label is the engine name; no Herdr behaviour is known to bypass pfm for a label, and only the source decides authority (recorded, unverified live). `HERDR_AGENT` is deliberately not set on the attach lines: it is a per-process screen-manifest hint on `tmux`, would mislabel codex and opencode at the engine-blind attach sites, and is a second authority beside the reporter. To flip it, add `HERDR_AGENT={engine}` in `action.attachLine` and in `chat_new`'s `attachRunResult`.

**Known limits.** In Claude Code an Esc interrupt during a turn fires no `Stop`: the `idle_prompt` notification is the net, so the pane stays working until it or the next prompt (with agents tracked, until their stops or the lease). A denial the transcript watch misses (a dialog left open past 30 minutes, a rejection whose feedback continues the turn, which writes no interrupt entry) falls back to the same net. A `plugin_notification` block names no tool call, so a main-thread tool's working report leaves it, a sibling of the same batch finishing included, while the plugin's picker still waits (sub-agent payloads never reach the reporter). A chat that dies without `SessionEnd` (a crash, a kill) keeps its last terminal title. An end whose engine process lives on outside a reload (Claude's `/logout`, an OpenCode instance disposed without exiting) leaves its chat server's title blank until `pfm name-sync` converges `set-titles-string` again.

- Ordering without tmux is by `seq` alone for Codex and OpenCode: Herdr keeps the newest `seq`, and no pane-keyed store exists.
- No state mapping is platform-specific; Herdr's bundled integrations, screen detection, source precedence and version or hook differences can vary. No macOS proof.
- Each hook event is a fresh pfm process, one per tool call; a resident daemon is rejected. Measured 2026-10-16 on this host's flight build, 21 runs each: the inert path (`HERDR_*` and `TMUX` unset, empty payload) median 9.9 ms (min 9.6, max 10.5); a live report to a scratch Herdr pane, alternating `working` and `idle`, median 10.8 ms (min 10.1, max 17.8). The adoption itself, one `list-clients` and one environ read, measures a median of 836 us in the fence. Every run on a chat server lists its tmux clients even with an empty registry, and a failing adoption (`HERDR_ENV=1` without a socket, a client in no pane) writes an error row on every run.
- A tool call the permission hold cannot pair stays blocked until a non-tool event (`Stop`). Claude Code 2.1.301's `PermissionRequest` input carries no `tool_use_id` (only `PostToolUse` and `PostToolUseFailure` do), so `callFingerprint` names the request by tool and a digest of its input, and two identical calls of one batch share a hold until one finishes. When a Claude release adds the id to `PermissionRequest`, the hold can match on it.
- Lock files are not reaped. `{HerdrLockDir}` (`~/.local/state/pfm/herdr/`) keeps one empty `{session}.lock` per chat session ever reported. Unlinking a flock file races its holders, so no sweep removes them.

**Herdr behaviour found live.** Probed on a throwaway Herdr 0.9.5 server (own socket and config, six panes, `capture-pane -e`):

- `agent_panel_sort = "priority"` orders the sidebar blocked, done, working, idle, unknown.
- `done` is `idle` reached from `working` while the pane is unseen; a visible pane reads `idle`.
- A `pane.report_agent` from a source Herdr does not know is acknowledged `ok` and ignored.
- A reported agent on a bare-shell pane is cleared within about 1 s: Herdr needs a foreground process.

**Sidebar indicators.** Herdr's own `state_icon` cannot blink and cannot hide its idle glyph, so the sidebar's state marks are pfm's: a Herdr plugin (`professor.indicators`, manifest `~/.config/herdr/pfm-indicators/herdr-plugin.toml`, written and linked by the theme sync's Herdr surface, [theme-sync](../engines/theme-sync.md)) runs `pfm internal herdr-indicators` at Herdr's server start and on the state, creation, focus and topology events returned by `herdr.IndicatorEvents()`. The entry (`herdr.IndicatorsEntry`, `pfm/internal/herdr/indicators_entry.go`, over `chat.PaintHerdrIndicators` and `herdr.PaintIndicatorsWithTabs`) reads every pane's and workspace's Herdr `agent_status` from `$HERDR_SOCKET_PATH`, which Herdr sets for a plugin command, and reports at most one custom token per pane and workspace under the source `pfm-indicators`: idle none, working `$pfm_working` `●`, blocked `$pfm_blocked` `●` in the on-half of a 1 Hz blink, done `$pfm_done` `✓`, unknown (a plain shell or a program Herdr does not recognize) `$pfm_unknown` `○`, never a `·`, which Herdr already puts between row tokens. The sidebar rows name these tokens; the theme sync paints each one's `fg` with the Claude theme's hue. A run that wrote lists and paints again, up to three more rounds, so a write that crossed a newer state change is repainted from it. Every run records its socket in `{HerdrLockDir}/indicators-{8 hex}.socket`; a blocked or unseen done agent, or an eligible chat tab, keeps one painter alive per Herdr socket (lock `indicators-{8 hex}.lock`) until none remains, or until its record is gone or its stop marker (`indicators-{8 hex}.stop`) is there, when it clears the tokens and exits; a paint that began before the theme off writes nothing more, a tab status rename included (`pfm/internal/herdr/indicators_stop.go`). `pfm theme off` unlinks the plugin, then clears the four tokens on every recorded socket and removes each record (`herdr.ClearIndicators`; a socket nobody listens on is forgotten, its tokens gone with its server), since a token carries no ttl and would stay until its pane closes. A failure is a line in Herdr's plugin log and the persistent Herdr error log, and exit 1.

**Tab status.** The same painter uses `SeatInspector` and incremental transcript reads to decorate sole-pane chat tabs through `tab.rename`. `LabelSoleTab` shares its per-endpoint/tab flock and durable base/rendered label record with every chat name writer. Each status observation is validated against terminal, pane, tab, session and revision, plus the native durable owner/process or actual tmux client generation, before renaming. It does not subscribe to its own `tab.renamed` events. `chat.herdrTabStatus` selects the default colored markers, text fallback or disable; the exact policy is in [pfm-home](../engines/pfm-home.md#chatherdrtabstatus). An `agent_not_found` during native status inspection is benign only when a fresh, successful `pane.list` confirms the pane disappeared after the tick's snapshot: no decoration or error is emitted, and the next tick's fresh pane list excludes it. A pane still listed, another refusal, or a failed confirmation remains a visible diagnostic; enumeration failure is never read as absence.

## Agent-attached hooks (not machine-global)

A hook can also be wired only into one agent's own frontmatter instead of every launch's payload — it is never in `claudelaunch.HookTemplates`, never in spawn-audit's expected set, and pfm install/doctor never mention it. `orchestrator-wait` is the one: a `PreToolUse` hook on `Bash` that denies a call whose whole command only waits (`echo`/`printf` with plain literal arguments, `true`, `:`, or `sleep N` — matched as a whole string; `isNoOpWaitCommand`, `pfm/internal/hookentry/orchestrator_wait.go`) and a call that loops on a file's existence under a `returns/` path (`until [ -s … ]`, `while [ ! -f … ]`; `isReturnFileWatch`), so a wait-looping orchestrator ends its message instead of spending a call proving nothing changed or placing a watcher on a sub-agent, whose completion notice wakes it. It is fail-open the same way every pfm hook is: a read or decode failure logs to stderr and returns 0 (`OrchestratorWait`). It is registered as an internal verb (`pfm/cmd/pfm/main.go`'s `internalSubcommands` list and its `runInternal` dispatch) so `pfm internal orchestrator-wait` runs and the subcommand is never mistaken for unknown residue, but it is deliberately absent from `claudelaunch.HookTemplates` — it is attached only through the frontmatter of this repo's `releaser` (`.claude/agents/releaser.md`), which spends calls waiting on its spawned children, and never runs for any other agent. No machine-global agent carries a frontmatter hook. The frontmatter names bare `pfm`, never a machine path; the Codex compile drops an agent's hooks, so the hook is Claude-only.

## The ownership rule

- **pfm owns** exactly the hooks in `claudelaunch.HookTemplates`, which live only in the launch payload, the Codex `resume-unkill` handler it writes into each `hooks.json`, and the retired shapes above. In a Codex `hooks.json` its record is the ownership ledger, and pfm removes exactly what the ledger records. In an account `settings.json` left by an older install, ledger-recorded commands count only when their first space-separated field is `~/.local/bin/pfm`; every hook whose command is a `claudelaunch.HookTemplates` command or a retired shape also counts. Doctor names these leftovers for the operator to remove.
- **The operator owns** every other hook in a settings file: a notification script, a memory sync, anything hand-wired. pfm never rewrites, reorders or removes one, and doctor never reports one. The Codex writer's contract says the same (`pfm/internal/installer/codex_hooks.go:85`).
- **An operator's hook that calls pfm stays the operator's.** A hook naming a subcommand this binary implements, such as `pfm doctor`, is never treated as residue (`pfm/internal/installer/settings.go:174-179`, `:213-215`). Only an unknown subcommand in pfm's own shape is.
- **Project-tier hooks are the adopter's.** pfm scaffolds them once; later changes flow through `pfm doctor --project-updates` and an upstream diff the project ports by judgment, never a rewrite.

## The pfm doctor checks

Four checks prove pfm's hooks. The launch hooks are proven per live chat, because that is the only place they exist; account files are checked for leftovers that would double-fire beside the launch; Codex homes are checked for the `resume-unkill` handler, its recorded trust and retired residue; the Herdr bundled integrations that would compete with the reporter are checked on the host ([Herdr reporter](#herdr-reporter)). Doctor checks only pfm's own hooks and prints nothing about the operator's — no count line either. The project tier has no doctor coverage.

### Launch hooks: spawn-audit

`pfm doctor` spawn-audit reads each live `cc-` chat's Claude argv from `/proc` and decodes it with `claudelaunch.Parse`, the inverse of `Render` ([claude-launch.md](../engines/claude-launch.md#pfm-doctor-spawn-audit)). A chat is `INJECTED` only when its `--settings` payload carries the registry's hook set: every `claudelaunch.HookTemplates` registration present exactly once, under its own event and matcher, with the exact command. No current template sets `async`; the renderer keeps the field only as `Parse`'s round-trip twin.

| Verdict | Hook meaning | Reports |
| --- | --- | --- |
| `INJECTED` | the payload's `hooks` equals the registry's set | the chat's row, no finding |
| `VIOLATION` | a fresh launch with no registry payload — a spawn site bypassed `Render`, so the chat runs no pfm hook | failure, naming the chat and pid |
| `PREDATES-LAYER` | the payload's hook set differs from the current registry: the process started before it changed | warning, naming the chat; `pfm chat reload` carries the new set |

A probe that cannot read `/proc` or decode an argv reports `CHECK FAILED to run … — live chats unaudited`, never "no chats". Hook values are read from argv, never from `/proc/{pid}/environ`.

The same check stats the first word of every template command, following a symlink, and reports `DRIFT what=executable want=$HOME/.local/bin/pfm got={absent|not-executable|not-regular-file|stat-failed(…)} — run pfm install` (`executableVerdict`, `pfm/internal/installer/hook_probe.go:308`), since every rendered hook would fail to start.

### Account files: pfm-settings

`pfm-settings` reads each physical `settings.json` in the store and configured account dirs once, against the ownership ledger and pfm command shapes. Its items are distinct `hook "{command}"` entries sorted by command, then `statusLine`, then `subagentStatusLine`, joined with `, `. Doctor prints `host-check: BLOCK pfm-settings {file} — carries pfm's {items} — pfm supplies its own hooks and status lines through --settings at launch, so these entries are leftovers of an earlier install`, followed by `host-check:   fix: remove {items} from {file} (each hook entry running that command and each named key; keep every other entry)`. Install refuses until the operator fixes the file.

An absent file or a file without pfm-owned keys produces no row. An unreadable file or ownership ledger produces a BLOCK `UNREADABLE` row with its cause and remedy; failed inspection is never clean. A custom status line and unrelated hook commands remain the operator's settings.

### Codex hooks.json

The Codex probe (`probeCodexHooks`, `pfm/internal/installer/hook_probe.go`) opens every configured Codex home's `hooks.json`, drawn from the machine config's Codex accounts, named `codex[{id}]`, de-duplicated by physical path. Each row keeps the prefix `doctor: hook {target} {file} {event} {name}`. It expects all eight pfm-owned handlers per Codex home (`resume-unkill` on `SessionStart` with matcher `resume`, plus the seven `herdr-*` handlers), each trusted, and validates the source file before querying native `hooks/list` through Codex app-server. This read-only query starts no model turn and writes no configuration. A matching receipt alone cannot prove current trust. It prints these states:

| State | When | Prints | Tally |
| --- | --- | --- | --- |
| MISSING | `hooks.json` is absent, or holds no `resume-unkill` handler under a `SessionStart` entry with matcher `resume`, or lacks one of the seven Herdr reporter handlers (`SessionStart`, `UserPromptSubmit`, `PostToolUse`, `PermissionRequest`, `Stop`, `Interrupt`, `SessionEnd`) | `… MISSING — run pfm install --yes` | failure |
| UNTRUSTED | Missing receipt, changed fingerprint, or native trust not trusted, for any of the eight pfm-owned handlers | `… UNTRUSTED {cause} — run pfm install --yes` | failure |
| NATIVE-TRUST-UNKNOWN | Native `hooks/list` could not run | `… NATIVE-TRUST-UNKNOWN {cause}` | warning |
| STALE | A retired or unknown pfm hook is registered; the Codex-only retired shapes (the old `clear-kill` `SessionStart` hook and the retired appendix hook) are flagged only under `SessionStart` | `… STALE {name} — run pfm install` | failure |
| UNREADABLE | The file or the ownership ledger exists but cannot be read or parsed, is a dangling symlink, or its `hooks` value has the wrong shape (a non-object `hooks`, a non-array event, a non-object entry, a non-string `matcher`, a non-array `hooks` list, a non-object hook, a missing or empty `command`) | one line per file, no per-hook rows: `doctor: hook {target} {file} UNREADABLE error={cause}`; for the ledger, target `ownership` | failure |
| DRIFT (timeout) | An installed Herdr handler's `timeout` is not the one `pfm install` writes for its event (`codexHerdrHookRows`: 3 s for `Interrupt` and `SessionEnd`, 5 s for the others; `codexHerdrTimeoutDrifts`, `pfm/internal/installer/codex_hooks_herdr.go`) | `… DRIFT what=timeout want={seconds} got={found\|absent} — run pfm install --yes` | failure |
| DRIFT (ledger) | The ledger owns an entry the file lacks, or one the installer no longer expects | `… DRIFT ledger ownership={n} file={m}`, `m` also `absent` or `not-expected` | warning |
| (unknown) | An internal state this printer does not recognize | `… UNKNOWN-STATE state=…` | failure |

UNREADABLE is an error, never absence: it carries no rows for that file's hooks, because nothing was proven. An unreadable ledger prints its own UNREADABLE row and every file's STALE and UNREADABLE rows still print, without the ledger comparison. OpenCode prints nothing.

### Exit

Each check returns its warnings and failures to the doctor tally (`pfm/internal/doctor/doctor.go:252-254`). `pfm doctor` exits 3 on any failure, 1 on warnings only, 0 when clean (`pfm/internal/doctor/doctor.go:398-410`). A deterministic stub stays available through `HookProbeOverride` (`pfm/internal/installer/hook_probe.go:490`).

### What the checks' own broken state reports

- Spawn-audit that cannot run: `CHECK FAILED to run … — live chats unaudited`, never "no chats".
- An unreadable ownership ledger: its own UNREADABLE row; ledger-recorded entries read as unjudged, never clean, while command-shape leftovers still report.
- An empty machine config (no accounts): one line saying no Claude config dir is configured, never a silent pass.
- A probe that cannot resolve `$HOME`: doctor stops before the checks.
